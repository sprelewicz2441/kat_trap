# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). You control a cat chasing a mouse around an arena, while a dog wanders randomly and catches the cat if they collide. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step.

## Architecture

**Entry point:** `js/main.js`
- Grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, and starts on `SetupScreen`.
- Runs a single `requestAnimationFrame` game loop that calls `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — a simple state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render` to whichever screen is active. Screens are swapped via `setScreen()`, which calls the new screen's `init()`.
- `SetupScreen.js` — animated title/start screen. Draws a background image over an animated gradient, defines a clickable "Start Game" hit-box (`startButtonArea`) computed as a percentage of the background image's position, and transitions to `GameScreen` on click.
- `GameScreen.js` (**~765 lines — by far the largest file, and the one most likely to need review before extending**) — owns the actual gameplay: creating the cat/mouse/dog/escapes/furniture, the input-driven cat movement, dog-vs-cat and cat-vs-mouse collision checks, the punch/toot/meow input reactions and punch shockwave animation, procedural kitchen-furniture layout, sound playback, win/lose messaging, and a "play again" button. Also kicks off cutscenes at the start via `CutsceneManager`.

**Entities** (`js/classes/`) — each is a small, mostly self-contained class with `update()`/`draw(ctx)`:
- `Cat.js` — player-controlled; `move(direction)` is called from `GameScreen` based on `InputHandler` state. Handles its own sprite-sheet animation.
- `Dog.js` — moves randomly on a timer (`moveInterval`), respects an obstacle list (currently the `furniture` array, still named `boundaries`/`this.boundaries` internally, a naming leftover from before furniture existed) and `escapes` when deciding valid moves, barks on a random interval, and exposes `isColliding(entity)`.
- `Mouse.js` — moves with pseudo-random velocity, bounces off canvas walls, fires a `wallHitCallback` on bounce. Intentionally **not** blocked by furniture (mouse has no pathfinding, so a real collision would risk it getting stuck against furniture corners); instead `GameScreen.render()` draws the mouse *before* furniture so furniture visually paints over it wherever they overlap, giving the effect of the mouse ducking under furniture while passing through unobstructed.
- `Escape.js` — a static rectangle ("mouse hole"); `isMouseInside()` for collision.
- `Furniture.js` — kitchen/dining obstacle (counter modules, dining set, trashcan). Takes `(x, y, type, spriteSrc, rotation = 0, spriteWidth = 32, spriteHeight = 64, scale = 1.5)`; every kitchen piece today passes explicit width/height/scale overrides rather than relying on those defaults, since none of the current sprites match them (the defaults are a leftover from an earlier asset generation). Rotation (0/90/180/270) swaps width/height and is applied via canvas transform in `draw()`, centered on the same pivot the collision box uses — currently unused (nothing in the kitchen rotates; see Kitchen furniture below for why) but kept working. Sets `ctx.imageSmoothingEnabled = false` before drawing so small pixel-art sprites stay crisp when scaled up rather than blurring. Draws a type-colored placeholder rect while the sprite loads. `isWallItem` is computed in the constructor but never read anywhere — dead property.
- `InputHandler.js` — tracks currently-held keys via `window` keydown/keyup listeners, exposes `getDirection()`; also dispatches custom `'toot'` (spacebar), `'punch'` (`p`), and `'meow'` (`m`) events for `GameScreen` to react to.

**Cutscenes** (`js/classes/cutscenes/`):
- `Cutscene.js` / `CutsceneManager.js` — sequenced intro scenes shown before gameplay starts, triggered from `GameScreen.startCutscenes()`.

**Utilities** (`js/utils/`):
- `collision.js` — exports `aabbOverlap(ax, ay, aWidth, aHeight, bx, by, bWidth, bHeight)`, the single shared axis-aligned bounding box overlap test. Used by `Escape.isMouseInside`, `Dog.isColliding`, `Furniture.isColliding`, and `GameScreen.checkCollision`. Takes raw coordinates rather than entity objects so each caller stays explicit about which field it's using per side (e.g. `Dog` uses its own `frameWidth`/`frameHeight` for itself but `entity.size` for whatever it's checking against) — don't refactor it to accept entities and guess the right field, since the same object (e.g. `Dog`) legitimately uses different box dimensions depending on which side of the check it's on.

## Floor background (`GameScreen.drawFloor`)
`render()` fills the whole canvas with a repeating two-tone checker pattern before drawing anything else. The pattern is generated on an offscreen canvas at draw time (two `fillRect` calls in `COLORS.FLOOR_LIGHT`/`FLOOR_DARK`, cached on `this.floorPattern` via `ctx.createPattern(..., 'repeat')`) rather than loaded from an image — there's no async load to wait on, and picking the colors directly guarantees they sit behind the furniture sprites' palette without a texture mismatch. This replaced an earlier photographic floor crop (`floor_tile.png`, cropped from the same AI-generated kitchen photo the furniture used to be cropped from) once that furniture was replaced — see Kitchen furniture below for why the photographic art direction was dropped entirely, floor included.

## Kitchen furniture (`GameScreen.generateKitchenFurniture`)
Procedurally lays out `Furniture` instances each game reset from `assets/ptpt_*.png` — a free pixel-art pack ("Cute Pixel Cooking Game Starter Pack" by itch.io user PtPt; see Asset source below). This is the **second complete art direction** for kitchen furniture, not a tweak of the first — see "Why the art direction changed entirely" below before reaching for anything photographic or RPG-Maker-style here.

**Why the art direction changed entirely (read this before touching kitchen art):** the first direction (all still in git history, several rounds of it) cropped furniture from `assets/kitchen_reference_scene.jpg`, a single AI-generated photorealistic top-down kitchen scene — first as individually-cropped appliances reassembled with computed offsets (cut edges didn't align to real object boundaries), then as one whole strip per wall (fixed alignment, but a strip can never have a gap, so a mouse hole on that wall was always hidden behind solid furniture — `Mouse.js` isn't blocked by furniture and draws *under* it, so a solid wall hides the mouse whenever it's under that wall), then as natural-seam tiles per wall (restored the gap, kept the alignment). All of that iteration was solving alignment/gap problems within a photorealistic style — but the user (a game engineer, building this for his daughter, explicitly not wanting to "vibe code" the art) eventually stepped back and asked the more fundamental question: does a photorealistic AI-generated scene even belong next to `cat.png`/`dog_medium.png`? Looking at those sprites directly settled it: `cat.png` is a bold, flat, front-facing cartoon mascot (thick outlines, flat colors, like a kids'-app icon) and `dog_medium.png` is a simple side-view pixel sprite — neither is photorealistic, and neither is a strict top-down/bird's-eye view. A tileset pack was tried next (LimeZu's "Modern Interiors," a well-reviewed RPG Maker-style pack) and rejected for a different reason: RPG Maker tilesets draw wall furniture (fridges, cabinets) *front-facing*, like a dollhouse with the front wall removed, which clashes with a strict top-down floor and characters. The PtPt pack that's actually wired in now was chosen because it draws furniture with real dimensional depth (both the top surface and a bit of the front face visible, like Overcooked/Stardew Valley) — the user's own reference point was FarmVille/FrontierVille's tilted board, and this is the more modest version of that: angled *sprites* on an otherwise flat top-down board, not a full isometric engine rewrite (that distinction — art-only vs. real engine change — was explicitly checked with the user before starting, since a tilted-board rewrite would touch collision math and rendering order, not just assets).

Layout, per reset:
1. **Top and bottom walls are built from small modular counter pieces** (`counter`, `cabinet`, `stove`, `sink` — see `MODULE_SPECS`), not photo crops. `TOP_WALL_FEATURED`/`BOTTOM_WALL_FEATURED` give each wall a fixed "featured" sequence (e.g. cabinet/stove/sink/cabinet), and `buildWallTypes()` fills out however many additional module slots the canvas width has room for with plain `counter` pieces. Because these are genuinely modular tiles — small, individually-authored, meant to repeat — rather than crops of one specific photo, they can repeat or reorder freely with zero alignment risk. This is the actual fix for the "partial table, cut-off fruit bowl" complaint that sank the photorealistic direction: modular tiles can't be cut off mid-object, because nothing is ever cropped mid-object to begin with.
2. **Baseline alignment, not top alignment:** modules share a native width (64px) but not height — the stove's hood and the sink's faucet stick up further than a plain counter or cabinet front. `makeModule()` aligns every module to a shared baseline (the floor line) by computing `y = baselineY - height`, the same way real counters of different heights still stand on one floor. Aligning by a shared top instead would float the shorter pieces above the floor.
3. **One random gap, same mechanic as the photo-crop era:** each reset, one wall is picked at random (`gapWall`), then one module slot within it is left empty instead of drawn — recorded as `this.wallGap` (`{x, y, width, height, wall}`). `generateEscapes()` reads it (furniture generation always runs first — see `resetGameObjects()`) and places the *first* escape exactly centered in that gap, on the correct edge, so there's a real hole in the wall with a guaranteed-visible mouse hole in it rather than an escape square that might land behind solid furniture. This part of the design survived the art-direction change unchanged, since it was never a photo-cropping problem — it works even better with genuinely modular tiles, since there's no risk of the gap falling at an awkward mid-object seam.
4. **Dining set**: a table with a chair on each side (`chair_reverse` back-to-viewer on the far side, `chair` facing the viewer on the near side), placed in the open interior via the existing `overlaps`/`blocksSpawn` random-search, same pattern used by every furniture-placement round this game has had. Rendered at a separate `DINING_SCALE` (`MODULE_SCALE * 0.85`) rather than the walls' `MODULE_SCALE` — at full wall scale, two stacked chairs plus the table came out taller than the interior floor band and only found a valid spot about 1 game in 4 (confirmed live via a debug hook); the trim fixed it to 100%. A floor piece reading slightly smaller than the wall pieces isn't unusual in this style of game.
5. **A small trashcan accent**, placed the same way, skipped silently if no spot is found (as is the dining set) — a piece that can't find a free spot in its attempt budget just doesn't appear that game rather than being forced to overlap.

**Spawn points must stay clear of wall collision boxes:** `TOP_WALL_HEIGHT`/`BOTTOM_WALL_HEIGHT` are derived from the tallest module (the sink, 42px native) at `MODULE_SCALE`, and `SPAWN_CLEARANCE` keeps the cat/dog spawn points (`resetGameObjects()`) clear of them — this is the same spawn-clearance mechanism the photo-crop era needed (there, the walls were much deeper — 215px/205px — and a fixed `canvas.height - 50` cat spawn once landed entirely inside the bottom wall's collision box, an instant stuck/loss bug). The mouse's fixed spawn (100, 100) stays exempt since it doesn't collide with furniture at all (see `Mouse.js` above).

**Asset source:** `assets/ptpt_*.png` are individual sprites from PtPt's "Cute Pixel Cooking Game Starter Pack," free/pay-what-you-want on itch.io (`pt-pt.itch.io/cute-pixel-cooking-game-starter-pack`), used under its license which permits commercial and personal use with credit to PtPt. The pack has no fridge — `FRIDGE` was dropped entirely rather than mixed in from a different-styled pack (that mixing is exactly what made the very first furniture attempt, before any of this session's rework, read as "scattered mismatched furniture" — see git history). Everything from the earlier photorealistic direction (`kitchen_reference_scene.jpg`, the `kitchen_top_*`/`kitchen_bottom_*`/`kitchen_island_*` crops, `dining_set.png`, `kitchen_fridge.png`, `kitchen_v1_source_sheet.png`, `floor_tile.png`) was removed in the same commit that wired in PtPt's assets, not left around for provenance — there are no pieces left in the current build descended from that lineage, so there was nothing left to preserve provenance for.
- The `tabletop_*`/`*_corner`/`wallframes`/`wallknife` assets from the very first WIP commit are **not a dining table** — closer inspection shows they're a pool table (green felt top, wood rail) plus a wall knife/dart rack and framed art. Still unused; don't reach for these for kitchen/dining furniture.

## Punch mechanic
- `p` → `InputHandler` dispatches a `'punch'` custom event on `document`.
- `GameScreen` listens for `'punch'` in `init()`, plays `SOUND_KEYS.PUNCH`, and calls `handlePunch()`, which knocks the dog `PUNCH_DISTANCE` (40px) away from the cat (clamped to canvas bounds) and starts a purple `shockwave` ring centered on the cat, drawn by `drawShockwave()` for `PUNCH_SHOCKWAVE_DURATION` (200ms).
- `m` → dispatches a `'meow'` event, which just plays the meow sound (no gameplay effect).

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this pattern rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB (axis-aligned bounding box) checks via the shared `aabbOverlap` helper — no physics library.

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage currently exists for any collision, movement, or game-state logic.
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, and procedural level generation in one ~725-line class — a strong refactor candidate.
- `styles.css` exists but is currently empty — all styling is Tailwind utility classes in `index.html`.

## Planned work
- **Furniture asset rework — kitchen redone with a modular pixel-art pack, other rooms still to do.** See Kitchen furniture above for the current approach and the full history of why it changed art direction twice (photorealistic AI crops → RPG Maker-style tileset → PtPt's angled cartoon pack). Remaining for the kitchen specifically: no fridge in the current asset set (dropped rather than mixed in from a mismatched pack); the PtPt pack is a single small hobbyist set (68 sprites total across all categories), so variety is limited — only 4 counter-module types exist, and the "featured" wall sequences (`TOP_WALL_FEATURED`/`BOTTOM_WALL_FEATURED`) are fixed rather than randomized among alternatives. Future rooms (living room, bathroom, etc. for later stages) will need their own asset source in a matching style — nothing kitchen-specific here carries over, though the *mechanism* (modular baseline-aligned wall tiles with a random gap for a mouse hole) generalizes to any room.
- **Mobile responsiveness.** Not addressed yet. Canvas sizing (`resizeCanvas` in `js/main.js`) and all movement/collision math currently assume keyboard input (`InputHandler` only listens for arrow keys, space, `p`, `m`) — touch input and layout would both need work. This should also cover making entity/furniture positions re-derive from canvas size on resize instead of going stale — furniture (like everything else in `GameScreen`) computes its position once from `canvas.width`/`canvas.height` at generation time and never re-lays-out if the canvas resizes afterward (e.g. a browser window resize mid-game); positions go stale and can end up rendering partially off-canvas. Not new to furniture specifically — cat/mouse/dog spawn points have the same assumption.

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- `GameScreen.cleanup()` centralizes teardown of document/canvas listeners and the `InputHandler` — call it (or extend it) rather than adding new listeners without a matching removal path.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest), not assume one is already there.
