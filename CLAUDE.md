# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). Before each game, you choose which character to control — Cat (chase the mouse), Mouse (escape the cat), or Dog (pause the cat to help the mouse escape) — while whichever of the other two you're not playing behaves autonomously. Colliding with the dog always pauses the cat, regardless of who's playing. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step. **To exercise real login/economy features locally, serve on port 8080** (e.g. `python3 -m http.server 8080`) — `kpground-api`'s local dev `CORS_ALLOWED_ORIGINS` default (`config/settings.py`) only allows `localhost:8080`/`127.0.0.1:8080`, and a blocked cross-origin fetch fails silently (see Lessons learned).

## Deployment & hosting
This is one game in a family site for my daughter; the landing page (`kpground.com`) is a sibling repo at `../kpground`, which is the hub for the overall hosting/auth architecture. **Deployed and live**: this repo (`github.com/sprelewicz2441/kat_trap`) is a Render Static Site named `kattrap` (publish directory `.`, no build command), auto-deploying on every push to `main`. Live at `https://kattrap.onrender.com` and `https://kattrap.kpground.com` (Cloudflare CNAME). **`git push origin main` is the deploy step.** See `../kpground/CLAUDE.md` for the full hosting plan and DNS/Render account details — shared accounts/auth across the site is planned but not built here yet.

**The currency/economy backend is also live** (deployed 2026-08-25): `kpground-api` (sibling repo `../kpground-api`) is a separate Render Web Service on the free tier at `https://kpground-api.onrender.com`, backed by a Neon Postgres project named `kat_trap`. `js/utils/api.js`'s `API_BASE_URL` points there in production (localhost still targets `127.0.0.1:8000`). No custom domain (`api.kpground.com`) was set up for it — that would be a 3rd custom domain on Render's free workspace tier, a real $0.25/month cost (see `../kpground/CLAUDE.md`'s cost note); revisit if that tradeoff changes. See `../kpground-api/CLAUDE.md`'s own Deploy section for exactly how it's configured (build/start commands, env vars, why migrations run inside the Build Command rather than a Pre-Deploy Command).

## Architecture

**Entry point:** `js/main.js` — grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, starts on `SetupScreen`. Runs a single `requestAnimationFrame` game loop calling `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render`. `setScreen()` calls the outgoing screen's `cleanup()` (if present) before swapping, then the new screen's `init()`.
- `SetupScreen.js` — animated title/start screen; own `cleanup()` stops its background-animation loop and removes its `mousemove` listener. Its one functional button ("Play Now", `SHOW_LOGIN_BUTTON=false` hides a second real "Login" button that's still fully wired via `loginModal.js`) races `kathrynQuickLogin()` (`api.js`) against `QUICK_LOGIN_TIMEOUT_MS` (8s as of 2026-08-25, down from an original 20s — short enough that a normal, already-warm login doesn't feel stuck, at the cost of usually missing `kpground-api`'s free-tier Render instance cold-starting from a full spin-down, ~50s worst case) and **always proceeds to character select regardless of outcome** — a failed/timed-out login just means economy features stay hidden, matching every other economy touchpoint's "no login, no economy UI" degrade pattern, rather than stranding the player on the title screen (see Known rough edges' history on this below). A spinning-arc indicator (`drawConnectingIndicator()`, angle driven off `performance.now()` via `SPINNER_PERIOD_MS`, repainted for free by `animateBackground()`'s already-running rAF loop) renders next to the "Connecting..." text for the whole wait, so the shorter timeout doesn't read as the screen doing nothing. `GameScreen.init()` retries the login once more in the background if it never succeeded here.
- `CharacterSelectScreen.js` — lets the player pick Cat, Mouse, or Dog. Canvas-drawn "animal-ear card" per option (`EAR_SHAPES` maps each entity to its `{card, inner}` shape pair from `canvasShapes.js`); each card fills with a saturated per-character gradient (`THEMES`) and shows a live crop of that character's sprite sheet (`PORTRAITS`). Backdrop is a teal-to-gold diagonal gradient matching `Cutscene.js`. `effectiveScale = uiScale * fitScale` drives all sizing — `fitScale` shrinks the row proportionally whenever three cards side by side would overflow the canvas. **Each portrait swaps to that character's actually-equipped cosmetic** once a fire-and-forget `getEquipped()` fetch resolves per character — a purchased look shows up here too, not just in gameplay (reassigning an already-loading `Image.src` re-fires its own `onload`, so no separate re-render call was needed).
- `GameScreen.js` (**~1000+ lines, largest file, review before extending**) — owns gameplay: entity creation, cat movement (player or AI), collisions, punch/toot/meow reactions, procedural kitchen layout, sound, win/lose, "play again," the mouse-escape danger indicator, and cutscene kickoff.

**Entities** (`js/classes/`) — small, self-contained classes with `update()`/`draw(ctx)`. Every character class takes both `scale` (movement speed) and `sizeScale` (display/collision size, defaults to `scale`) — kept separate so a display-size change can never accidentally change movement speed. Each exposes `displayWidth`/`displayHeight` getters for real on-screen size.

- `Cat.js` — player-controlled in Cat mode, else AI-driven; all paths call `move(direction, speed = this.speed)` — `speed` genuinely overrides (an earlier version silently ignored the override, see Lessons below). Tracks `facingDirection`, used by the Mouse-mode AI's line-of-sight check and by `draw()`'s directional lean (`applyDirectionalTransform()` fakes turning via small rotation/stretch since `cat_v2.png` is a symmetric front-facing portrait, not directional art). **Furniture collision uses a separate "legs" hitbox** (`hitboxWidth`/`hitboxHeight`, 35%/30% of display size) rather than the full sprite — `this.size` is bigger than the visible sprite and is now used *only* for the AI's line-of-sight lane width, not collision. `GameScreen.tryMoveCat()` calls `aabbOverlap()` directly with the legs rect rather than `Furniture.isColliding()` (which assumes a square `entity.size`). Current asset: `cat_v2.png` (native res 256×296; `baseFrameWidth`/`baseFrameHeight` 118/150 drive display size, `frameWidth`/`frameHeight` 256/296 drive source-rect slicing only). `cat.png` (v1) stays on disk unreferenced (deprecate-don't-delete precedent).

- `Dog.js` — in Cat/Mouse mode, wanders continuously (re-picks direction every 1500ms or on a blocked move); in Dog mode, `GameScreen.movePlayerDog()` drives it directly per-tick, bypassing its own wander, and calls a `stand()` method (resets `currentFrame`/`frameCounter`) whenever no direction is held or the move was blocked — an earlier version animated the walk-cycle continuously even at rest. Player-driven walk-cycle uses its own `playerFrameSpeed` (10, matching `Cat`), separate from the autonomous wander's `frameSpeed` (20) — the two need independent cadences since they drive completely different movement patterns. Barks on a random interval via a self-rescheduling `setTimeout` chain; `pauseBarking()`/`resumeBarking()` suspend/restart it. **Wall/furniture containment is strict** (`proposedX` clamped fully inside `[WALL_OFFSET, canvasWidth - WALL_OFFSET - frameWidth]`), not the older "can dip below offset by up to `size`" convention, which broke once `frameWidth`/`frameHeight` exceeded `WALL_OFFSET`. `facingLeft` starts `true` (source art is leftward-facing only) and mirrors via canvas transform when facing right. Current asset: `dog_v2.png`, native res 473×296 (`BASE_FRAME_WIDTH`/`HEIGHT` 72×45.6 for display). **Dog speed is split**: `Dog.speed` (autonomous wander feel, tuned independently) vs. `GameScreen`'s `layout.dogPlayerSpeed` (`BASE_DOG_PLAYER_SPEED = 10`, matches `Cat.speed`) for player control — one field can't safely serve both roles (see Lessons). **Known open issue**: at the current (20%-bumped) size the dog visibly clips furniture/walls a bit too often; revisit by nudging base size down rather than reopening the clamp math.

  **Dog outfit cosmetics — 4 of 5 planned tutu colors (pink/teal/orange/green) ship with real per-color walk-cycle art**, `assets/dog_v2_tutu_{color}.png`, native 473×296 per-frame geometry matching `dog_v2.png` exactly. Purple repeatedly came back from generation with a frozen-pose defect and stays a placeholder (`sprite_src` still `dog_v2.png`, `is_active=False` in `kpground-api`'s `seed_store`) pending its own regeneration. **Getting these sprite sheets out of the browser losslessly needed a real download (`canvas.toBlob` + `<a download>`), not a screenshot** — a screenshot always flattens alpha and recompresses as JPEG, and a first chroma-key-workaround pass (used before the lossless path was available) shipped sprites ~4.5x blurrier by Laplacian-variance sharpness than the rest of the game's art. The lossless download itself hit a real macOS wall: Chrome-downloaded files carry a `com.apple.macl` per-file ACL restricting them to the downloading app, blocking every command-line read (`cat`, `python open()`, even `rm`) regardless of Full Disk Access, while `ls -la` succeeds fine (the tell that it's this ACL, not a broader permissions problem) — **not fixable from the command line at all**; the only fix is a Finder-mediated copy (drag-and-drop, Cmd+C/Cmd+V) needing the user's own hands. Extraction itself: label connected components across the *whole* source column at once (not per pre-sliced row band — an early attempt assumed poses were evenly grid-aligned and clipped/drifted them, since they weren't), sort by vertical center to recover frame order, crop each to its own true bbox, bottom-anchor, resize to native size. `Dog.js`'s `this.rows = 6` is hardcoded, not derived from sheet height — the generation only produced 5 poses per color, so the 6th row duplicates the 5th for a clean loop wrap.

- **Module-level cache-busting**: `GameScreen.js` imports `Cat.js`/`Dog.js` as `?v=N` — a query string on an ES module import specifier bypasses browser module caching, which cache-busting the *image* URL alone doesn't do. **The version number must be bumped by hand on every edit to that file** — no automated safeguard, this has been missed before, and a stale module is often mistaken for a logic bug (see Lessons). `js/utils/scale.js`, `js/utils/audio.js`, `js/utils/storeModal.js` carry the same `?v=` convention on every importer. `styles.css` (a plain `<link>`, not a JS import) needed its *own* separate `?v=` convention — bump `styles.css?v=N` on every future edit to that file too. `index.html`'s own `<script src="./js/main.js">` is deliberately unversioned, mirroring the "version the inner import, not the entry script" pattern — but that means a plain reload can silently serve a stale `main.js` from HTTP cache even after every imported module's own `?v=` was bumped correctly (see Lessons).

- `Mouse.js` — moves with pseudo-random velocity, bounces off walls, fires `wallHitCallback` on bounce; in Mouse-controlled mode, `GameScreen.movePlayerMouse()` drives it directly and calls `wallHitCallback` itself. Calls its own `stand()` (same idle-animation-bug class as `Dog.js` above) whenever no direction is held. **Intentionally not blocked by furniture** in either mode (no pathfinding); instead `GameScreen.render()` draws the mouse *before* furniture so furniture paints over it for a "ducking under" effect, with a faint translucent silhouette (`drawMouseSilhouette()`/`isHiddenByFurniture()`) keeping it visible. Current asset: `mouse_v2.png`, kept v1's exact 3-col×4-row (walk-cycle × facing) true top-down grid rather than the cat/dog's single-direction-plus-mirror approach — a mouse must stay visibly quadruped/on-all-fours (see Lessons re: image-gen bipedal bias). `mouse.png` (v1) stays on disk unreferenced.

- `Escape.js` — a mouse hole. `isMouseInside()` is a loose AABB overlap test, used to exempt the cat/dog wall clamp near the gap. The actual "mouse escaped" trigger uses the stricter `hasMouseEntered()` instead (see Hitbox tightening below) — don't conflate the two.
- `Furniture.js` — `(x, y, type, spriteSrc, rotation, spriteWidth, spriteHeight, scale, cropX, cropY)`. `cropX`/`cropY` account for transparent padding baked into every `kitchen_*.webp`, and are what keeps adjacent wall modules flush. Rotation (0/90/180/270) swaps width/height, applied via canvas transform centered on the collision-box pivot. Does **not** set `imageSmoothingEnabled = false` — current furniture art is high-res photorealistic drawn at a downscale (see Lessons: that flag is only correct for upscaled/pixel-art sprites).
- `InputHandler.js` — tracks held keys via `window` listeners, exposes `getDirection()`; dispatches custom `toot`/`punch`/`meow` events.

**Cutscenes** (`js/classes/cutscenes/`):
- `Cutscene.js`/`CutsceneManager.js` — sequenced intro scenes before gameplay, triggered from `GameScreen.startCutscenes()`. Fills the canvas with the same teal-to-gold gradient as `CharacterSelectScreen`, a rounded gradient card (`drawRoundedRect`) with a pop-in ease-out-cubic animation. `getButtonRect()` is shared by `render()` and click handling so the drawn button and its hit box can't drift. Character sprite sizing is decoupled from in-game scale (`CUTSCENE_CHARACTER_FILL_RATIO = 0.9`), computed per-frame from the available vertical band.
  - **`render()` must call `advanceAnimationOnly()`, not `update()`, on the character sprite** — a small duck-typed helper calling each class's frame-only method (`updateAnimations()`/`updateAnimation()`) directly. Routing through the real `update()` with no timestamp previously let `Dog`'s full autonomous-wander logic and `Mouse`'s wall-bounce logic run on `undefined`/overwritten coordinates, visibly drifting characters across the cutscene card. Cutscenes must never be able to trigger movement/AI logic regardless of what a class's `update()` does with no arguments.
  - **`CutsceneManager` must cancel the previous cutscene's `requestAnimationFrame` handle before starting the next one** — every loop shared the same `isPlaying` flag (only false once *all* cutscenes finish), so without an explicit cancel, multiple loops end up redrawing the canvas concurrently.
  - **Known open bug**: cutscenes construct their own throwaway `Cat`/`Mouse`/`Dog` preview instances entirely separate from `this.cat`/`this.mouse`/`this.dog`, so a cutscene always shows each character's *default* look regardless of what's actually equipped (confirmed live: Dummy's cutscene showed the default tutu even with a different color equipped everywhere else). Fix direction: pass `equippedOutfits` in and set each preview entity's sprite via `getSpriteSrc()` before constructing the `Cutscene`.
- `playModalPopSound()` (`js/utils/audio.js`) — a synthesized filtered-noise "pfff" whoosh, fired from `Cutscene.init()` and the Credits button. Gated on `isSfxMuted()`. Not used by the game-over modal (which has its own win/lose sounds) or the store modal (which has its own bigger console-style whoosh, see Currency & economy system below).

**Utilities** (`js/utils/`):
- `collision.js` — exports `aabbOverlap(ax, ay, aWidth, aHeight, bx, by, bWidth, bHeight)`, the single shared AABB test used throughout. Takes raw coordinates, not entity objects — the same object (e.g. `Dog`) legitimately uses different box dimensions on different sides of a check, so don't refactor it to accept entities and guess the right field.
- `characterNames.js` — `CHARACTER_NAMES` (`{ CAT: 'Mia', MOUSE: 'Poop', DOG: 'Dummy' }`), single source of truth.
- `canvasShapes.js` — `drawRoundedRect()` plus `drawCatEarCard`/`drawMouseEarCard`/`drawDogEarCard` (+ their `Inner` variants), each animal's ear card shape used by `CharacterSelectScreen`.
- `audio.js` — `isMusicMuted()`/`setMusicMuted()`/`toggleMusicMuted()` (starts `true`) and `isSfxMuted()`/`setSfxMuted()`/`toggleSfxMuted()` (starts `false`) — deliberately different defaults: an unprompted looping track is worse than silence, but muting player-action SFX by default makes actions feel like they do nothing. Also exports the game's synthesized one-shot SFX (`playWinSound()`/`playLoseSound()`, `playPlantKnockOverSound()`, `playDooberSound()`, `playCoinLandSound()`, `playStoreWhooshSound()`, `playSellChaChingSound()`, etc.), each gated on `isSfxMuted()`.
- `settingsMenu.js` — wires the in-game hamburger menu (`#settingsMenu`). Opening it pauses gameplay via `GameScreen.pauseForOverlay()` (see Currency & economy system below).
- `api.js` — thin wrapper around `kpground-api`'s REST endpoints (`getWallets()`, `submitRound()`, `purchaseItem()`, `sellItem()`, `equipItem()`, `unequipItem()`, `getEquipped()`, `getDailyGiftStatus()`, `claimDailyGift()`, etc.). Also owns the offline round-result queue — `queuePendingRound()`/`flushPendingRounds()`, `localStorage`-backed (`kattrap_pendingRounds`, capped at `MAX_PENDING_ROUNDS=20`) — see Currency & economy system below for how `GameScreen` drives it.
- `storeModal.js` — wires up the Bloomingtails/Pawgreens store DOM modal — see Currency & economy system below.
- `outfits.js` — `getSpriteSrc(character, equippedItem)` resolver (falls back to each character's default sprite when nothing's equipped) plus the shared `PORTRAITS` source-rect crop map, used by both `CharacterSelectScreen` and the store's pedestal preview so the two "here's what this character looks like" spots can't drift into different crops.

## Floor, walls, and mouse holes
`GameScreen.render()` draws, in order: `drawFloor()` (a repeating 24px two-tone tile pattern, cached via `ctx.createPattern`, plain white/off-white — deliberately *not* matched to furniture's warm palette, which read as blending in rather than as a distinct floor), then `drawWalls()` (a 16px band flush against all four edges, purely presentational, unrelated to `WALL_OFFSET` which is the actual movement clamp), then escapes/mouse/furniture. `Escape.draw()` renders a rounded-arch mouse-hole silhouette rotated to face into the room per its `wall` param; `isMouseInside()` collision stays a plain AABB rect regardless of the visual rotation. Furniture's back edge aligns flush against the wall band's front face on all four walls (not the raw canvas edge).

## Kitchen furniture (`GameScreen.generateKitchenFurniture`)
Procedurally lays out `Furniture` instances each reset from `assets/kitchen_*.webp` (`cabinet`/`sink`/`stove`/`fridge`/`table`, plus `plant`/`cart`/`shelf`) — WebP conversions of the original PNGs at identical dimensions, ~550KB total vs ~4MB. This is the fourth full art direction for kitchen furniture (a flatter, near-orthographic top-down camera angle is what makes modules tile edge-to-edge with no seam — rendering fidelity was never the actual variable, see Lessons).

**Layout, per reset:**
1. Top/bottom walls built module-by-module (`buildWall()`) from `TOP_WALL_ORDER`/`BOTTOM_WALL_ORDER` (sink/stove appear once each, cabinet is filler) — `pickWallDensity()` picks a random subsequence of each wall's order per reset so kitchens vary in fullness. Floor of half the wall's own full length, rounded up.
2. Left/right walls (`buildWallVertical()`) place `LEFT_WALL_ORDER`/`RIGHT_WALL_ORDER` (cabinet reused twice each) rotated 90°/270°, confined strictly between `TOP_WALL_HEIGHT` and `canvas.height - BOTTOM_WALL_HEIGHT`.
3. Every module's back edge aligns flush to the wall band's front face (not a floor baseline).
4. One random gap: a random top/bottom wall slot is left empty each reset (`this.wallGap`), and the first escape is centered there. Left/right walls are never in the gap pool.
5. Cabinet's render has a double-sided trim; `MODULE_SPECS.cabinet`'s crop excludes the unused edge, with rotation chosen per wall so the remaining trim faces the room.

**Decorated counters** (`counterBlender`/`counterMicrowave`/`counterToaster`/`counterFlowers`/`counterMail`) substitute opportunistically into cabinet slots on top/bottom walls via a shuffled offer pool (`COUNTER_ONE_OFF_TYPES` once each + `counterFlowers` up to `COUNTER_FLOWERS_MAX_APPEARANCES=2`) that now takes a slot outright rather than coin-flipping into it — under the current pool size this means blank cabinet effectively never appears on top/bottom anymore; shrink the pool if that reads as too much decoration. Default filler is a dedicated blank-counter render (`FURNITURE_SPRITES.CABINET`), sized via `MODULE_SCALE_MULTIPLIERS`/`CABINET_TARGET_HEIGHT` like any other module (no longer an implicitly-exempt baseline).

**Fridge** placement varies by wall (`fridgeWall`, checked via `fridgeFitsWall` before picking). `FRIDGE_ROTATIONS = {top:0, bottom:180, left:270, right:90}` — the *opposite* mapping from cabinet's, since a tall appliance's image-top (door seam) and image-bottom (vent band) detail read oppositely from a flat countertop. `LEFT_WALL_ORDER_WITH_FRIDGE`/`RIGHT_WALL_ORDER_WITH_FRIDGE` use 1 cabinet each (vs. the normal 2) since the side walls' full order plus the fridge never fits the board's vertical band at any canvas size.

**Dining set**: a single all-in-one table render (table + 4 chairs + place-setting baked in) rather than separate pieces — `kitchen_chair.webp` stays on disk unreferenced. `TABLE_SCALE_MULTIPLIER = 0.55` (its own dedicated multiplier, since this render adds real height unlike the old two-piece layout). Passable for the cat with a shake reaction (`'table'` in `CAT_NON_BLOCKING_FURNITURE_TYPES`, not `DOG_NON_BLOCKING_FURNITURE_TYPES`).

**Plant, cart, shelf** — freestanding corner/wall decor, prefer a room corner (tries all 4, shuffled) falling back to a randomized wall search; no placement is a normal no-op. Passability is deliberate per piece: plant is passable for both cat and dog; cart/shelf are cat-passable, dog-solid (`CAT_NON_BLOCKING_FURNITURE_TYPES` includes `plant`/`cart`/`shelf`/`table`; `DOG_NON_BLOCKING_FURNITURE_TYPES` is just `['plant']`). The *autonomous* dog's own wander (`Dog.js`'s `tryMove()`) has no opt-out list and treats cart/shelf/plant as solid regardless — a known, harmless inconsistency vs. the player-controlled dog path. Placement order is biggest-footprint-first: shelf → cart → plant (see Lessons — this was a real, live-reported bug for cart before the ordering was fixed).

`tabletop_*`/`*_corner`/`wallframes`/`wallknife` from the very first WIP commit are an unused pool table/knife rack/framed art — not dining furniture, don't reach for these.

## Plant knock-over, cart bump, shelf bump, table shake (`Furniture.js`, `GameScreen.js`)
The cat or dog running into the **plant** tips it over with a replayable ease-out-cubic fall to `KNOCK_OVER_ANGLE` (75°, not 90° — a full right-angle fall reads as a broken transform snap) plus a synthesized thump/scatter sound. Edge-triggered on a `WasHit` flag (not continuous overlap) so standing on it doesn't restart the animation every tick. **Cart** bump sound (`sounds/cart_bump.mp3`, a real recording — three rounds of synthesized attempts were all rejected, see Lessons) is driven directly rather than fire-and-forget: playing while the cat is in the zone *and* moving (resumed, not restarted, if already paused), paused-in-place if in the zone but not moving, reset to 0 once fully out of the zone. "Moving" is `this.catMovedThisTick`, set from `tryMoveCat()`'s own return value (works for both player and AI control; a "key held" check would not). **Shelf** bump (`sounds/shelf_bump.wav`, cat-only, the shelf fully blocks the dog) is a plain fire-and-forget one-shot, edge-triggered the same way as the plant. **Table** gets a shake, not a knock-over (`Furniture.startShake()` — small decaying-sine oscillation), extended later to cart/shelf too; cart needed its own independent edge-detection flag since its sound already has a continuous play/pause model that would otherwise restart the wobble every tick. `playSound()` wraps `currentTime`/`play()` in `try`/`catch` — a missing/unsupported audio source throws *synchronously* on `sound.currentTime = 0`, not just on the `.play()` promise.

## Punch mechanic
`p` → `InputHandler` dispatches `punch`; `GameScreen` plays `SOUND_KEYS.PUNCH` and knocks the dog `PUNCH_DISTANCE` (40px) away from the cat, clamped to canvas bounds, with a purple `shockwave` ring (`drawShockwave()`, `PUNCH_SHOCKWAVE_DURATION=200ms`). `m` → `meow` (sound only, no gameplay effect). Space bar → `toot`, same dog-shoving effect at a smaller `MOVE_DISTANCE`. Both punch and toot no-op their positional effect (sound still plays) when `controlledEntity === 'dog'` — shoving the dog away from the cat doesn't make sense when the player *is* the dog trying to reach it on purpose.

## Settings menu & audio (`js/utils/audio.js`, `js/utils/settingsMenu.js`)
Hamburger button (`#settingsToggle`) opens `#settingsPanel` with independent Music/Sounds toggles (see `audio.js` above for default asymmetry). `GameScreen.playSound()` checks `isSfxMuted()`; the background track's start and a live `musicmutechange` listener check `isMusicMuted()`. Opening the menu calls `GameScreen.pauseForOverlay()` (see Currency & economy system below for what that actually does and why it's shared with the store modal).

**Background music** (`sounds/you_can.mp3`) is a page-lifetime singleton `Audio` element (`getBackgroundMusic()` in `audio.js`), not per-`GameScreen` — it starts only from `startGame()` (not cutscenes), survives "Play Again" untouched, and only a real page refresh restarts it.

**Credits** (`#creditsBtn`/`#creditsModal`) reuse the cream-gradient-card-plus-cat-ears visual language from `Cutscene.js`. Swaps for the settings panel rather than stacking; closing calls the shared `setOpen(false)` helper that resumes gameplay. The card's ear shape (`.credits-ear` in `styles.css`) uses `clip-path: polygon(...)`, not `border-radius` (see Lessons), with three stacked layers (fill, an inset `::before` body, a further-inset `::after` highlight) to fake a stroke around a non-rectangular shape.

## Character selection & playable modes (`CharacterSelectScreen.js`, `GameScreen.js`)
`controlledEntity` (`'cat'`/`'mouse'`/`'dog'`, default `'cat'`) is chosen pre-game and threaded into `GameScreen`. **"Play Again" returns to character select**, not a replay with the same entity — `restartGame()` hands off to a fresh `CharacterSelectScreen`. Intro cutscenes are skipped on that replay path via `isReplay` → `skipCutscenes`. Exactly one entity reads player input at a time; the cat AI runs the same in both Mouse and Dog mode, the mouse's passive wander runs the same in both Cat and Dog mode.

- **Cat mode**: `moveCat()`/`tryMoveCat()` from `InputHandler`; mouse and dog wander autonomously.
- **Mouse mode**: `movePlayerMouse()` from `InputHandler` (ignores furniture, same as autonomous); cat runs `updateCatAI()`; dog wanders.
- **Dog mode**: `movePlayerDog()`/`tryMoveDog()` (same per-tick furniture/wall rules as the cat, stricter wall clamp — see `Dog.js`); cat runs `updateCatAI()`; mouse wanders. The dog-pauses-cat collision rule itself is unchanged — playing as the dog doesn't change the rule, just who's steering into it.

**Player-controlled speed is unified across all three** — `tryMoveDog()`'s `layout.dogPlayerSpeed`, `movePlayerMouse()`'s `layout.mousePlayerSpeed`, and `tryMoveCat()`'s `Cat.speed` are all the same per-tick value, deliberately, so piloting any character feels identical. Only *player-controlled* speed is unified; each character's *autonomous* speed is tuned independently.

**Win/lose semantics don't change between modes — only which outcome is good news does, and the dog is on team mouse.** `checkCollision(cat, mouse)` → cat catches mouse; `checkMouseEscaped()` → mouse reaches an `Escape`. `endGame()` computes `isWin` from `controlledEntity` at both trigger sites: cat catches mouse → win iff playing Cat; mouse escapes → win iff *not* playing Cat (Mouse and Dog succeed together, even though the dog never touches the mouse).

### Game-over modal (`displayGameOverModal`, `endGame`)
Dimming scrim, then a rounded gradient card popping in over `MODAL_POP_IN_DURATION` (250ms) — gold gradient for a win, teal/blue for a loss, both playful rather than somber. `playWinSound()`/`playLoseSound()` (synthesized) play *in addition to* the meow/squeak event sound. The transient in-round pause message (dog-pauses-cat) is a separate `displayMessage()` call, not a modal, since gameplay is still visibly running underneath.

**Reward breakdown** (`drawRewardsBreakdown`, `this.roundRewardBreakdown`) — once `this.wallet` has loaded, the modal grows to show coins earned plus a level-up or XP line. The backend (`kattrap/services.py`'s `submit_round()`) only ever returns the updated wallet, never a breakdown — the frontend diffs `this.walletAtRoundStart` (a snapshot captured once, the moment `getWallets()` first resolves) against what `submitRound()` returns; `baseCoinsGained = totalCoinsGained - dooberCoins` isolates the flat win/loss reward. XP only shows when no level-up happened that round (a raw diff would be wrong across a level boundary). `this.roundRewardBreakdown = { status: 'pending' }` is set **synchronously** in `endGame()`, before the async response, so the card's height is reserved on first paint and doesn't jump once real numbers fill in. Each item renders in its own bordered/filled compartment (`drawRewardChipBox()`) with a real gap between — a shared box with floating text was tried and explicitly rejected ("ice cubes in a tray"). Title/subtitle/button positions are derived relative to the card's actual top edge (`modalY`), not `centerY` — a `centerY`-relative position doesn't track the top edge as the card grows taller (see Lessons).

### Dog-pauses-cat stun moment (`handleDogCollision`, `displayMessage`, `drawStunBurst`/`drawStunStars`)
`DOG_PAUSE_DURATION` is 4000ms (net 2x an earlier baseline; a "Longer Cat Pause" perk multiplies it further, see Currency & economy system below). The pause message is a pill-shaped banner (`drawRoundedRect`, sized to actual text width, purple gradient, drop shadow, white text with a light stroke) rather than plain floating text — floating text at the mercy of whatever's drawn behind it read as amateurish. `drawStunBurst()` (400ms, amber/orange filled 8-point star, adapted from `drawShockwave()`'s expanding-ring technique, colored differently from the punch shockwave so the two moments don't read as the same effect recolored) draws behind the cat; `drawStunStars()` (small yellow 5-point stars circling the head, angle driven directly off elapsed time, no stored per-star state) draws after, for the whole pause duration. `SOUND_KEYS.GOTCHA` layers on top of the existing dog-bark sound, not a replacement.

### Cat AI (`updateCatAI`, `catHasLineOfSightToMouse`, `moveCatTowardMouse`, `wanderCat`)
Runs whenever the cat isn't player-controlled. Each tick: if there's line of sight to the mouse, move one cardinal step toward it; otherwise (or if blocked) wander. No memory of the mouse's last-known position — losing sight means pure wander until facing happens to line up again.

- `catHasLineOfSightToMouse()` — true only if the mouse is strictly in the cat's cardinal facing direction and no wall-mounted furniture crosses the line (freestanding table/plant never block). Uses `cat.size` (the wider AI-perception lane), not `displayWidth`/`displayHeight` — deliberately unchanged even after those switched everywhere else (see Hitbox tightening) since a wider perception box only means the AI notices sooner, not that it catches from further away.
- `wanderCat()` — moves every tick, re-picking direction every `CAT_WANDER_DIRECTION_INTERVAL` (1200ms) or on a blocked move, at `cat.speed * CAT_WANDER_SPEED_MULTIPLIER` (0.5).

### Mouse disappearing on escape (`GameScreen.mouseEscaped`)
`checkMouseEscaped()` sets `this.mouseEscaped = true`, which stops the mouse from being drawn at all, rather than leaving it visible at the hole through the frozen game-over screen.

### Cat silhouette under passable furniture (`drawCatUnderFurnitureEffect`/`drawCatSilhouette`)
Cat counterpart to the mouse's "ducks under furniture" treatment, for `plant`/`cart`/`shelf`/`table`. Unlike the mouse, the cat draws normally in `drawGameObjects()`, then `drawCatUnderFurnitureEffect()` re-draws the overlapping piece(s) on top and calls `drawCatSilhouette()` — a rounded head with two pointed ears (deliberately distinct from the mouse's plain ellipse), same faint translucent-black (`globalAlpha=0.35`) treatment.

### Spawn safety (`resolveClearSpawn`, `isHiddenByFurniture`)
Cat/mouse/dog fixed spawns aren't inherently safe from wall-mounted furniture landing on top of them. `resolveClearSpawn(preferredX, preferredY, size)` returns the preferred spot unless `isHiddenByFurniture()` says it's covered, in which case it random-searches `this.playableArea`. All three characters' spawns are routed through this (see Lessons re: the cat spawn being left out originally). The mouse's fixed spawn (100, 100) is exempt — it never collides with furniture at all.

### Character size scale (`js/utils/scale.js`, `getCharacterScale`)
A no-op on touch, `DESKTOP_CHARACTER_SIZE_MULTIPLIER = 1.95` on desktop. Deliberately not folded into `getScale()` (which also drives movement speed — see the `scale`/`sizeScale` split above). `GameScreen.computeLayout()` exposes this as `characterScale`, also used for spawn-clearance approximations.

### Hitbox tightening — catching, walls, furniture, mouse-hole entry (`GameScreen.js`, `Dog.js`, `Escape.js`)
Four related fixes, all confirmed by direct pixel-gap measurement:
1. **Catching from too far away** — `checkCollision()`/`Dog.isColliding()` now use `cat.displayWidth`/`displayHeight` instead of the oversized `cat.size`. `catHasLineOfSightToMouse()`'s own use of `cat.size` was deliberately left alone (different bug class).
2. **Cat's wall clamp could clip into the wall** — switched to the same strict-containment shape `Dog.js` already used (see `Dog.js` above).
3. **Dog clipped furniture horizontally, stopped short vertically** — its collision check used a square `this.size` against a non-square sprite; fixed by calling `aabbOverlap()` directly with `frameWidth`/`frameHeight` (bypassing `Furniture.isColliding()`, same reason `Cat.js` bypasses it).
4. **Mouse escape triggered on mere proximity** — `Escape.isMouseInside()` stays a loose "any overlap" test (still needed for the wall-clamp exemption near the gap); a separate `hasMouseEntered()` requires the mouse's box to fully *cover* the hole (checking the mouse's *center* was geometrically impossible — the hole is shallower than the mouse's half-width), tied to the mouse's `wallHitCallback` rather than a continuous per-tick check, widened via `BASE_ESCAPE_HITBOX_MARGIN=20` on the *mouse's* effective box (not the hole — widening the hole would make containment harder), and gated behind an actual stop (`MOUSE_STOP_DEBOUNCE_MS=150`, plus an exception for pressing directly into the wall the mouse rests against) so a fast pass-by or rapid direction-tapping can't trigger it. The autonomous mouse uses its own `escapeCheckCallback` from `Mouse.js`'s bounce blocks — it never had the "running by" exploit since it bounces immediately rather than sliding.

## Currency & economy system (`kpground-api`, `js/utils/api.js`, `GameScreen.js`, `js/utils/storeModal.js`)
Backed by a separate Django REST API (`kpground-api`, sibling repo, OAuth2 bearer-token auth, **deployed and live** — see Deployment & hosting above). **One `CharacterWallet` row per `(user, character)`** — Cat/Mouse/Dog each earn and spend independently, gated on `isLoggedIn()`. **Levels are also per-character** and independently gate that character's store catalog. A **future "aggregate" store** spendable against the *sum* of all three wallets (not a fourth currency) is planned but not built. `GameScreen.loadEconomyData()` fetches the controlled character's wallet, owned perks, and every character's equipped cosmetic, fire-and-forget (`this.wallet` stays `null` — HUD/store button/reward breakdown all skip drawing — if never logged in or the fetch fails); refreshed from `submitRound()`'s own response after a round rather than re-fetching.

**Login is never allowed to block gameplay** (see `SetupScreen.js` above for the title-screen side of this). `init()` calls `loadEconomyData()` two ways depending on whether the quick-login already succeeded: if `isLoggedIn()`, it first calls `flushPendingRounds()` (replays any round results queued from a past offline stretch, see `api.js` above) and *then* `loadEconomyData()`, so the freshly-loaded wallet already reflects those - if not logged in, it retries `kathrynQuickLogin()` once more in the background, and on success does the same flush-then-load sequence; a second failure just stays offline for the rest of the session. `endGame()` mirrors this: a successful `submitRound()` still updates the wallet/reward-breakdown as before, but any failure (never logged in, or the request itself fails mid-flight) calls `queuePendingRound()` instead of just logging a warning, so the round's coins/XP aren't lost - they're replayed automatically the next time a connection succeeds, same session or a later one. Known tradeoffs of this queue, accepted deliberately rather than solved: no idempotency key, so a request that reaches the server but whose *response* is lost gets retried and could double-credit that one round; and the 20-round cap means a very long outage silently drops the oldest queued rounds rather than growing `localStorage` unboundedly.

**HUD** (`drawHud`, `HUD_STATS`, `getHudLayout`) — a wide, horizontally-centered bar at the top of the board: one emoji+value chip per stat (🪙 Coins, ⭐ Level, ✨ XP) over a full-width XP bar, with a centered Store button below. `getHudLayout()` computes shared geometry once, backing `drawHud()`, `getHudCoinTargetPosition()` (the doober popup's flight target), and hover hit-testing. The coin chip draws a small crop of `assets/doober_coin.png` instead of an emoji. Hover tooltips (`drawHudTooltip()`) word-wrap against a width clamped to a fraction of live canvas width.

**In-gameplay "doobers"** (`spawnDoober`/`updateDoobers`/`drawDoober`, `DOOBER_TYPES`) — collectible coin drops on the board during a round, separate from the round-completion reward (term borrowed from FrontierVille). `MAX_ACTIVE_DOOBERS=1` at once, visible up to `DOOBER_CATCH_DURATION` (10s), `DOOBER_SPAWN_INTERVAL` (7s) minimum gap before the next can appear — **the cooldown timer resets only at a genuine disappearance (expiry/collection), not on every tick the interval check passes**, or doobers reappear faster than configured (a real bug that shipped once). Collected only by the player-controlled character; tallied in `this.coinsCollectedThisRound`, sent once via `submitRound()` at round end. Generalized via a `DOOBER_TYPES` registry so a new type is one registry entry with its own `draw()`/`onCollect()`. A glowing arrow (`drawDooberArrow()`) points at a landed doober only the first time a player sees each *type* per page session. Collection flies a "+N" popup from the doober to `getHudCoinTargetPosition()` over `DOOBER_POPUP_DURATION` (700ms); **the HUD coin count increments only when the popup lands, not at pickup** — deliberate, timed to the animation. Landing fires an expanding gold-ring impact (`spawnHudCoinImpact()`) and `playCoinLandSound()`, deliberately a different sound from the pickup ding since pickup and landing are ~700ms apart.

### Store — "Bloomingtails" (cosmetics) and "Pawgreens" (perks), one modal shell (`js/utils/storeModal.js`, `#storeModal`)
A real DOM modal (not canvas-drawn) opened from the HUD's Store button — dynamic owned/locked/affordable states are much simpler as DOM than hand-rolled canvas hit-testing. `#storeTabs` (`switchTab()`) toggles which of `#bloomingtailsPanel`/`#pawgreensPanel` is visible; both read from the *same* `getStore(character)` fetch (`currentState`) filtered client-side by `item_type` — switching tabs is a pure local redraw, no extra network call. `openStoreModal()` always resets to the Bloomingtails tab and clears `previewedSlug` on a fresh open. Sized to the intro cutscene's own modal footprint on desktop (`applyModalSizing()`); see Mobile store layout below for the touch-specific branch.

**Bloomingtails is a "dressing room"** — cosmetics only, a bridal-boutique-fitting-room pedestal scene (`assets/store_dressing_room.webp`, `#storePedestalScene`'s backdrop, filling the entire card edge-to-edge) rather than a department-store list. `#storePrevOutfitBtn`/`#storeNextOutfitBtn` cycle `cycleOutfit()` through the character's cosmetic items only, wrapping at either end. `#storePedestalActionBtn` is a single Buy/"Try It On"/"Wearing It"/locked button for whichever cosmetic is currently previewed, driven by the shared `wireItemButton()` helper (equip-toggle labels read "Try It On"/"Wearing It," not generic "Equip"/"Equipped," to match the dressing-room framing). `drawPedestalPortrait()` composites the previewed cosmetic onto `#storePedestalCanvas` via `getSpriteSrc()`, reusing `outfits.js`'s shared `PORTRAITS` crop map so this and `CharacterSelectScreen` can't drift into different crops. `previewedSlug` (which cosmetic) and `currentState` (the last real fetch) are both module-level and independent — an arrow click only changes the preview and redraws locally, no network call; only a purchase/equip/sell re-fetches via `renderItems()`.

**Pawgreens is a plain shopping list, deliberately not another pedestal** — perks are invisible gameplay effects, not something to try on. Every row gets its own inline buy/sell button pair (`buildPawgreensRow()`) rather than one shared action button, since there's no character preview to focus a single button's target on the way Bloomingtails has. `#pawgreensBackdrop` is a placeholder flat green-tinted banner; real art is meant to eventually read like a convenience-store checkout counter. `wireItemButton()` is the one shared helper behind both Bloomingtails' single pedestal button and every Pawgreens row's button, so purchase/equip behavior can't drift between the two very differently-laid-out stores.

**Perks have real gameplay effects**, gated to `controlledEntity` matching the perk's own character (a perk is that character's wallet-funded upgrade — Poop never inherits an upgrade Mia paid for): Cat's "Bigger Punch Knockback" (`PUNCH_KNOCKBACK_PERK_MULTIPLIER=1.5` on `layout.punchDistance`), Dog's "Longer Cat Pause" (`LONGER_PAUSE_PERK_MULTIPLIER=1.5` on `DOG_PAUSE_DURATION`), Mouse's "Mouse Hole Radar" (`drawEscapeRadar()`, a bobbing arrow on the nearest escape, sharing its shape/animation with the doober system's own pointer-arrow helper but recolored cool blue so a coin callout and an escape-route callout can never be confused). `this.ownedPerkSlugs` (from `getStore()`) drives all three; only the *controlled* character's perks are checked, no separate endpoint needed.

**Cosmetic equip system is fully wired**: `getSpriteSrc()` existed from the `v2` art era but was never actually called with a real equipped item until this — `init()` fires one `getEquipped(character)` fetch per character (not just `controlledEntity`, since a purchased look belongs to that character whenever it's on screen). Each resolving fetch calls `applyEquippedOutfit()`, which reassigns the entity's live `spriteSheet.src` immediately *and* records the pick on `this.equippedOutfits` so `resetGameObjects()`'s second call (once cutscenes finish) re-applies it instead of reverting to default. A second callback, `onOutfitChangeCallback` (threaded through `openStoreModal(character, wallet, onWalletUpdate, onOutfitChange)`), fires `applyEquippedOutfit()` directly after a successful equip/unequip/sell so the live in-game sprite updates immediately rather than only on next reload.

**Sell button** — a second, independent "Sell — {icon}{price}" button next to whatever `wireItemButton()` is driving, shown for any *owned* item (cosmetic or perk) via its own `wireSellButton()`, since selling is orthogonal to that button's own state. Sell price is `Math.round(item.cost * SELL_REFUND_FRACTION)` (0.2, duplicating `kpground-api`'s own constant — needs client-side since the button must show its price before any click). `kpground-api`'s `sell_item()` refunds that amount, deletes the `OwnedItem` row, and reverts any matching `EquippedItem` first (a sale can't leave that pointing at something no longer owned) — the frontend fires `onOutfitChangeCallback(character, null)` locally for a currently-equipped sale, same as unequip. A successful sell fires a "+N" coin popup (`spawnCoinPopup()`, positioned off the *specific* button clicked via `getBoundingClientRect()`, a plain `document.body` child so `#storeCard`'s own `overflow:hidden` can't clip it) and a synthesized `playSellChaChingSound()` (a noise click for "cha," two ascending bell notes for "ching") — both fire before `refreshAfterChange()` redraws the panel and potentially replaces the very button being measured.

**Bloomingtails wordmark logo** (`assets/bloomingtails_logo.png`) — a single generated image of "bloomingtails" in glossy metallic-gold script with a furry curled tail flowing directly out of the final "s" as one continuous stroke, replacing two earlier attempts (a CSS cartoon-bubble text treatment, then a live script-font-plus-emoji combo) that could never make a separately-placed tail read as *the word's own* tail. Reused in two places (`#storeHeading img` on the pedestal, `.store-tab-logo` inside the Bloomingtails tab button) so there's one source of truth for the mark. Both store tabs are icon-on-top-label-below rather than single-line pills (Pawgreens gets a matching 🐾 icon) — a detailed logo or bold text squeezed into one line had to shrink to fit and stopped being legible well before a phone-sized tab needed it to; the text label stays a fixed readable size regardless of how small the icon shrinks. `#storeHeading img` is sized with `max-width`/`max-height` together (not width-only, which ignored available vertical space and let it squish the rest of the overlay on short viewports — see Lessons), tighter still on touch.

**Store modal pause/close robustness** — opening the store calls `GameScreen.pauseForOverlay()`, a method shared with the settings-menu toggle (both used to hand-roll their own copy of "pause `this.running`, silence the dog's bark/poop timers"; the store's copy had silently drifted and was missing the bark handling entirely, reported live as "a stray dog bark" audible with the store open — see Lessons on duplicated pause logic). Uses a counter, not a boolean, so two overlapping overlays can't let the first one's close prematurely resume gameplay. Closing plays a whoosh (`playStoreWhooshSound()`) and mirrors the card's own entry pop-in animation in reverse (`.store-card-closing`, `animation-direction: reverse`) before actually hiding the modal — gated behind a hard `setTimeout` fallback racing the `animationend` listener, not the event alone, after the event apparently failing to fire once left the modal's full-screen backdrop stuck forever, blocking the entire board (see Lessons: never gate something this critical on one DOM event).

**Mobile store layout** — `applyModalSizing()` branches on `isTouch()`: touch sizes `#storeCard` off the true `window.innerWidth`/`innerHeight`, not `canvas.width`/`height` (the desktop formula), since the canvas itself already excludes the side gutters the touch controls live in — sizing off the canvas alone left a strip where the controls showed through the modal's translucent backdrop ("looks awful on mobile"). The margin subtracted from that full viewport uses the *same unscaled* formula desktop uses (not `getUIScale()`'s touch multiplier, which was doubling it) — an initial flush-to-edge, zero-margin, square-corner version was walked back per follow-up direction to keep a proportional margin and rounded corners, matching desktop's own scale rather than either extreme. The tab bar and the pedestal's name/button both get their own touch-only shrink pass (smaller padding/font, not smaller readability priority — the icon shrinks far more than the text label), and the pedestal character's own vertical position nudges up on touch for clearance from the now-shorter bottom chrome band.

**Daily gift** — backend fully built (`kpground-api`'s `claim_daily_gift()`, `DailyGiftClaim` model, flat `DAILY_GIFT_COINS_PER_CHARACTER` split across all three wallets on one claim) and `api.js` has the wrapper functions (`getDailyGiftStatus()`/`claimDailyGift()`), but **nothing in the UI calls them yet** — no claim button or notification exists anywhere in `GameScreen`/`storeModal.js`. Next step is purely frontend.

## Mobile responsiveness (`js/utils/scale.js`, `orientationGate.js`, `touchControls.js`)
Milestone-scope: landscape-only (a full-screen gate blocks portrait), but scales correctly at any canvas size within landscape.

**Four separate scale functions**, all derived from `base = canvasWidth / REFERENCE_WIDTH` (1280), each with its own touch-vs-desktop multiplier via `isTouch()` (`window.matchMedia('(pointer: coarse)').matches`, the single source of truth reused everywhere):
- `getScale()` — character speed, wall/floor chrome, spawn clearance. `MOBILE_ASSET_MULTIPLIER=1.5` on touch, no-op on desktop.
- `getUIScale()` — buttons/messages/cutscene modal. `MOBILE_UI_MULTIPLIER=2` on touch, no-op on desktop.
- `getFurnitureScale()` — furniture only. `DESKTOP_FURNITURE_MULTIPLIER=2` on desktop; the touch multiplier is *derived* from it (`/1.5 ≈ 1.333`) so furniture occupies the identical fraction of canvas width on both device classes.
- `getCharacterScale()` — character size only, not speed. `DESKTOP_CHARACTER_SIZE_MULTIPLIER=1.95` on desktop; `MOBILE_CHARACTER_SIZE_MULTIPLIER≈1.977` on touch — if a future "N% bigger" request lands, apply it to whatever the constant currently is, not back to the original baseline derivation, which no longer holds exactly.

Two of these boost *desktop* rather than touch (`getFurnitureScale`, `getCharacterScale`) — easy to reach for the wrong one; check whether a new `BASE_*` constant is a character-speed/wall/floor thing, a button/message thing, furniture, or character size before picking.

`GameScreen` computes `this.layout = computeLayout(canvas.width)` once in its constructor (canvas size is fixed for a `GameScreen`'s lifetime — live mid-game resize is a known gap) and every `BASE_*` constant is multiplied by whichever scale fits its category; methods read `this.layout.X`, never a bare module constant.

**Landscape gate** (`orientationGate.js`) — a full-screen overlay shown whenever `window.innerHeight > window.innerWidth` (a real aspect-ratio check, not a device breakpoint). The game loop keeps running underneath.

**Canvas width** reserves more side margin on touch (`resizeCanvas()`: `0.8` vs `0.9` of `window.innerWidth`), and separately caps `maxCanvasWidth` further — but *only* when the device is actually width-constrained (checked via the natural fraction-only fit first) — to guarantee `MIN_TOUCH_CONTROL_GUTTER` for the d-pad; a blanket cap regressed height-constrained phones once before (see Lessons).

**Touch controls** (`touchControls.js`) — an on-screen D-pad (`#dpad`, background is an actual reference photo `assets/dpad_cross.png`, four invisible absolutely-positioned hit-zone buttons) plus punch/toot/meow action buttons, all dispatching real `KeyboardEvent`s on `window` (`InputHandler.js` is unaware touch controls exist). Positioned by `layoutTouchControls()` (load/resize/orientationchange): edge-anchored (`edgeAnchoredOffset()`, fixed thumb-reach margin from the nearest edge, falling back to gutter-splitting only when the gutter's too tight), shrink-to-fit via CSS custom properties (`--dpad-scale`/`--action-scale`). **The d-pad has a hard floor the action buttons don't** (`MIN_DPAD_SCALE=0.62`, 130px) — a d-pad divides one disc into 4 direction zones, so over-shrinking makes hitting a specific direction unreliable, unlike one-shot action taps. `MIN_TOUCH_CONTROL_GUTTER` (used by `resizeCanvas()`) is derived from this same floor so they can't drift apart. `layoutTouchControls()` also pushes the action-button cluster down (never up) from vertical center whenever true centering would put it within `ICON_GROUP_GAP` (24px) of the hamburger settings icon.

**`#settingsMenu` positioning differs by device.** Desktop anchors via pure CSS (`<main>` is `relative inline-flex`, shrink-wraps around the canvas; `#settingsMenu` is `position: absolute; top: 20px; right: -60px`) — the third attempt, after two JS-measured approaches were each flagged as still overlapping the board in an environment this project couldn't reproduce (leading theory: Tailwind's CDN stylesheet loads `async`, so the canvas's flex-centered position can shift after a JS measurement was already taken, with no `resize` event to correct it). A pure-CSS position has no measurement to go stale. Mobile shares horizontal center/scale with `#actionButtons` (both from `layoutTouchControls()`), fixed `SETTINGS_TOP_MARGIN` (20px) from the viewport top.

**Not covered**: actual portrait layout, and live-resize (furniture/spawn positions are computed once at generation time and never re-laid-out on resize).

## iOS "Add to Home Screen" hint (`js/utils/homeScreenHint.js`)
A dismissible top banner for iPhone/iPod on iOS browsers not already launched from a home-screen icon — WebKit has no `beforeinstallprompt`-style API, and only implements the Fullscreen API on iPadOS (never iPhone), so a home-screen launch is the only way to reclaim toolbar space on an iPhone. Detection: `/iPhone|iPod/` on `navigator.userAgent` (deliberately not "any iOS device" — iPadOS 13+ reports a Mac-style UA and already has the real Fullscreen API), covers Chrome/Firefox/Edge/Opera on iOS too, not just Safari. `isStandalone()` checks both `navigator.standalone === true` and `matchMedia('(display-mode: standalone)')` since the former isn't reliably set by every iOS browser's own standalone launch. Hidden once gameplay starts. Dismissal count (`kattrap_homeScreenHintDismissCount` in `localStorage`, wrapped in `try`/`catch`) rather than a single flag — reappears until `MAX_DISMISSALS` (10).

## Viewport frame & mouse-escape danger indicator (`styles.css`, `GameScreen.updateEscapeDangerIndicator`)
A retro handheld-console bezel (`body::after`) plus a "power LED" dot (`body::before`), fixed and non-interactive, gated behind `@media (pointer: coarse)` — real layout border would eat into `resizeCanvas()`'s raw-viewport sizing budget. The LED is a live mouse-escape-danger meter: `updateEscapeDangerIndicator()` (called every frame from `updateMouse()`) measures distance to the nearest `Escape` center and sets `document.body.dataset.mouseDanger` to `low`/`medium`/`high` against `BASE_ESCAPE_DANGER_DISTANCE`/`BASE_ESCAPE_WARNING_DISTANCE` (90/220, scaled). `styles.css` recolors green/amber/red with a CSS transition. `GameScreen.cleanup()` deletes the dataset attribute so a fresh game doesn't inherit a stale color.

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB via the shared `aabbOverlap` helper — no physics library.

## Lessons learned (apply before repeating)
- **A rendering-looking bug should be checked against the actual asset pixels before assuming it's code/GPU** — several stray-pixel sprite-sheet bugs were found via `scipy.ndimage.label` connected-component analysis (keep only the dominant component) after code-side fixes didn't help.
- **Any new furniture/decor render needs its alpha-channel content bbox measured before wiring in `width`/`height`/`cropX`/`cropY`** — every `kitchen_*.webp` module has baked-in transparent padding. Verify `Image.mode == 'RGBA'` first (an opaque RGB image silently reports "the whole canvas is content"), and sample per-row/column opacity *fraction*, not just presence (a vignette can give faint-but-nonzero alpha well past the real edge).
- **A re-shot module must be checked against the original's aspect ratio, not just matched on height** — a wider-at-matched-height replacement can overflow a wall row that fit the original fine. Cap the new scale multiplier to `Math.min()` of the width-preserving and height-preserving ratios vs. the original.
- **A "reserve space for the worst case" calculation must run after the randomization/substitution it's reasoning about, not before** — computing it too early let later substitutions become strictly larger than the assumed baseline, silently breaking the reservation (bit the counter-flowers width fit and, separately and more severely, the fridge's per-wall fit check).
- **For freestanding decor placed by a corner/wall search, whichever piece has the biggest footprint must place first** — cart lost the fight for corners ~1 in 4 layouts before its placement block was moved ahead of the plant's.
- **A size-scale change to any character needs a re-check of spawn-clearance assumptions that were "safe" only because of the old, smaller size** — `getCharacterScale()` making desktop characters ~2x bigger broke the cat's spawn, which had skipped `resolveClearSpawn()` on the assumption its position was inherently clear.
- **Any function that unconditionally reassigns a field holding an object with its own timers/listeners needs a cleanup guard before the reassignment**, not just at eventual teardown — same class of bug `ScreenManager.setScreen()`'s automatic `cleanup()` exists to prevent, one level down.
- **Two call sites hand-rolling their own copy of the same "pause gameplay for an overlay" logic will drift** — the store modal's own copy silently ended up missing the dog-bark-pausing half the settings menu's copy already had, reported live as a bark audible with the store open. Fixed by extracting one shared `pauseForOverlay()`/`resumeForOverlay()` pair; route any future overlay through it instead of writing a third copy.
- **Never gate something critical on a single DOM event firing reliably** — the store modal's close animation waited only on `animationend` before actually hiding the modal; when that event apparently didn't fire on some device, the modal's full-screen backdrop stuck around forever, blocking the whole board. Pair any such wait with a hard `setTimeout` fallback.
- **Conflating movement speed with display/collision size is a real, easy-to-make bug** — always decide whether a new size constant is `sizeScale` (display/collision) or `scale` (speed) territory before wiring it in.
- **`Cat.move()`'s speed-override bug**: several rounds of AI-wander-multiplier tuning had zero effect until it was discovered `move()` validated a proposed move at the passed-in speed but then always applied `this.speed` regardless — always sanity-check that a tuning knob actually reaches the code path it's supposed to affect if retuning "isn't working."
- **A single field can't safely serve two different roles that need independent tuning** — `Dog.speed` originally drove both the autonomous wander *and* the player-controlled move, and no single value worked for both.
- **Every JS module import needs its `?v=` cache-bust bump by hand on every edit**; a plain `<link>` stylesheet is invisible to that convention and needs its own separate `?v=` bump. A deeper trap: a plain reload can't verify a fix to any *unversioned* entry-point file (`index.html`'s `<script src="./js/main.js">`) — bumping an imported module's own `?v=` doesn't help if the file importing it is itself served stale from HTTP cache; use a cache-bypassing hard reload, and check a console log's own script-URL in its stack trace as the tell.
- **Image-gen prompts for a "ballerina"/dance-themed outfit strongly bias toward a bipedal dancer pose even against explicit "quadruped"/"on all fours" instructions** — locking the camera angle and repeating the quadruped constraint explicitly is what worked for the mouse redesign. Separately: an instruction that explicitly rules something *out* (e.g. "not an illustrated animal tail," meant only to kill unwanted photoreal texture) can kill every *wanted* shape cue along with it — a generated tail flourish came back reading as generic decorative calligraphy for exactly this reason. State the positive target explicitly rather than only the negative.
- **Baking a decorative element directly into one piece of combined art beats overlaying it separately near live text or another element** — a standalone tail icon placed next to the Bloomingtails wordmark never read as *the word's own* tail regardless of positioning; only generating the whole wordmark-plus-tail as one continuous stroke worked.
- **Don't iterate indefinitely on synthesized SFX** — after ~2-3 rejected synthesis attempts for one sound (the cart bump), sourcing a real AI-generated recording was faster and better than a 4th attempt.
- **`border-radius` cannot taper to an actual point** — no matter how the horizontal/vertical radii are tuned it only ever curves. Use `clip-path: polygon(...)` for a real vertex. A plain CSS `border` doesn't survive a non-rectangular `clip-path` — fake a stroke with stacked layers instead (base fill, an inset `::before` body, a further-inset `::after` highlight).
- **Don't guess a fixed-fraction split for side-by-side text/content (canvas or DOM)** — measure each block's actual rendered width and center the *group*. The same root mistake independently broke the reward-modal layout and an early credits-ear attempt.
- **A size rule needs to bound every dimension that actually matters, not just the one that seems obvious** — a width-only percentage on the store's wordmark logo ignored the vertical space actually available, and squished the rest of the overlay on short landscape-phone viewports. Use `max-width`/`max-height` together (with `width`/`height: auto`) whenever both dimensions are genuinely constrained.
- **When a backend only returns final state, not a computed delta, diff a snapshot captured before the mutating call** rather than requesting a backend change or duplicating its reward-calculation constants client-side.
- **Reserve a UI element's height synchronously, before an async response arrives**, if its final content will be roughly known in shape — avoids a layout jump once real data fills in.
- **`imageSmoothingEnabled = false` is only correct for upscaled/pixel-art sprites** — once art is high-res and displayed at a downscale, nearest-neighbor sampling drops detail; leave smoothing at the canvas default (on) for downscaled photorealistic assets.
- **A fix scoped to one device regime (e.g. "width-constrained only") must check the device is actually in that regime before applying**, or it silently regresses the other regime — a canvas-width cap for narrow-gutter tablets once shaved width off ordinary height-constrained phones too. The same shape of bug hit the store modal's mobile card sizing: fixing the "controls visible behind the modal" bug by going flush-to-edge overcorrected past what was actually asked, and had to be walked back to a proportional margin.
- **A file downloaded via Chrome carries a macOS `com.apple.macl` per-file ACL** restricting command-line reads regardless of Full Disk Access (`ls -la` still succeeds — that's the tell it's this ACL, not a broader permissions problem). Not fixable from the command line; needs a Finder-mediated copy. Prefer a real lossless download (`canvas.toBlob` + `<a download>`) over a screenshot for any in-browser image capture regardless — a screenshot always flattens alpha and recompresses as JPEG.
- **When extracting individual poses from an AI-generated sprite sheet, don't assume poses are pre-aligned to equal grid cells** — find each pose's own bounding box from the full uncropped source (connected-component labeling across the whole strip, sorted by position) rather than slicing into row/column bands first.
- **A `fetch()` blocked by CORS looks identical, in this app, to a real backend outage** — both fail as a plain `TypeError: Failed to fetch` in the console, and both make the frontend silently degrade to its designed "no login, no economy UI" fallback (see `SetupScreen.js`/Currency & economy system above) rather than throwing anything diagnostic. Confirmed live: serving `kat_trap` locally on a port other than 8080 (5500, e.g.) against a locally-running `kpground-api` produced a game with no HUD and no Store button, which read exactly like a stale build — the actual cause was `kpground-api`'s default `CORS_ALLOWED_ORIGINS` (`config/settings.py`) only allowing `localhost:8080`/`127.0.0.1:8080`. Before assuming stale code or a real server-down state, check the Network tab for the request's actual HTTP status (or `curl` the same URL, which sidesteps CORS entirely and shows the true response).

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage for any collision, movement, or game-state logic. No test runner configured — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest).
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, layout scaling, and procedural level generation in one ~1000-line class — a strong refactor candidate.
- `styles.css` holds the orientation-gate/touch-controls/viewport-frame/store CSS; everything else is still Tailwind utility classes in `index.html`.
- **Four scale functions, two of which (`getFurnitureScale`, `getCharacterScale`) boost *desktop* rather than touch** — easy to reach for the wrong one.
- **Touch-vs-desktop detection is purely `window.matchMedia('(pointer: coarse)')`** — a touchscreen convertible used with a mouse reads as desktop, and vice versa. Accepted as good enough for this audience.
- **The offline round-result queue has no idempotency key** (see Currency & economy system above) — a `submitRound()` request that reaches the server but whose response is lost to the client gets retried and could double-credit that one round's coins/XP. Accepted for now given how unlikely a response-specifically-lost failure is; the real fix would be a client-generated round UUID plus a matching unique constraint on `kpground-api`'s side.

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- Every screen (`SetupScreen`, `CharacterSelectScreen`, `GameScreen`) that adds `document`/`canvas` listeners or a `requestAnimationFrame` loop should expose a `cleanup()` — `ScreenManager.setScreen()` calls it automatically before swapping, so this is the one teardown path that's actually invoked on every transition.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly, not assume one is already there.
- Reuse `isTouch()` (`js/utils/scale.js`) for any new mobile-vs-desktop behavior rather than inventing another device-detection heuristic.
- Before shipping a mobile/responsive-layout change, check the actual `resizeCanvas()`/`computeLayout()` math by hand across a real spread of device dimensions, not just a few manually-resized desktop-browser windows — narrower testing has missed real bugs multiple times in this project's history.
- If you add a new size for a character (`Cat`/`Dog`/`Mouse`), decide whether it's *display/collision size* (`sizeScale`/`getCharacterScale()`) or *movement speed* (`scale`/`getScale()`) before wiring it in — conflating the two cost several rounds of tuning a constant that had no actual effect until caught (see Lessons).
- Any new economy-mutating action (a purchase/sell/equip-style flow) should go through `kpground-api`'s `services.py` pattern (its own exception type, `transaction.atomic()` + `select_for_update()`) — see that repo's own CLAUDE.md — and, on the frontend, a shared button-wiring helper (`wireItemButton()`/`wireSellButton()`) rather than one-off click handlers per call site, so behavior can't drift between Bloomingtails and Pawgreens.
