# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). Before each game, you choose which character to control — Cat (chase the mouse), Mouse (escape the cat), or Dog (pause the cat to help the mouse escape) — while whichever of the other two you're not playing behaves autonomously. Colliding with the dog always pauses the cat, regardless of who's playing. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step.

This is one game in a family site for my daughter; the landing page (`kpground.com`) is a sibling repo at `../kpground`, which is the hub for the overall hosting/auth architecture. **Deployed and live**: this repo (`github.com/sprelewicz2441/kat_trap`) is a Render Static Site named `kattrap` (publish directory `.`, no build command — plain static files), auto-deploying on every push to `main`. ## Architecture

**Entry point:** `js/main.js`
- Grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, and starts on `SetupScreen`.
- Runs a single `requestAnimationFrame` game loop that calls `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — a simple state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render` to whichever screen is active. Screens are swapped via `setScreen()`, which calls the outgoing screen's `cleanup()` (if it has one) before swapping, then the new screen's `init()` — added after `SetupScreen`'s animated-background loop and a stray listener were found running forever with nothing tearing them down.
- `SetupScreen.js` — animated title/start screen. Draws a background image over an animated gradient, defines a clickable "Start Game" hit-box (`startButtonArea`, a percentage of the background image's position), and transitions to `CharacterSelectScreen` on click. Has its own `cleanup()` (stops the `animateBackground()` loop via a `running` flag, removes its `mousemove` listener).
- `CharacterSelectScreen.js` — lets the player pick Cat, Mouse, or Dog before gameplay starts, all three enabled. Canvas-drawn, same `init`/`render`/`cleanup` shape. Picking one constructs `GameScreen` with `controlledEntity` of `'cat'`/`'mouse'`/`'dog'` (see Character selection & playable modes below). Each option renders as an "animal-ear card" — a rounded rect with two ears poking up from the top edge, reading as a head silhouette. `EAR_SHAPES` maps each `option.entity` to its own `{card, inner}` pair from `canvasShapes.js` (cat/mouse/dog each have distinct ear shapes — see `canvasShapes.js` below for their design history), sharing the same render-loop call sites so a 4th character would only need a one-line `EAR_SHAPES` addition. Each card is filled with its own full saturated gradient (`THEMES`: cat gold-to-orange, mouse lilac-to-purple, dog sky-blue-to-blue) — a shared neutral/cream fill was tried and rejected since it crowded out the backdrop's own color and made the *cards* resemble the cutscene modal rather than the *backdrop* matching it ("the cards should look like they were... the BACKGROUND should look like the cut scenes"). Dog is blue rather than amber/brown — confirmed live that orange and brown/amber read as too close to tell apart. White text with a dark drop shadow (not dark text) for legibility across each gradient's range. The screen's backdrop (not the cards) is a teal-to-gold diagonal gradient sampled off `assets/start_screen.jpg` (`#2fa8b8` to `#ffb238`), matching `Cutscene.js`'s own backdrop — this is the screen right after the title screen, so it picks up that screen's candy-bright palette rather than the game board's kitchen palette. Each card shows a small live crop of that character's actual sprite sheet (`PORTRAITS`, native source-rect coordinates) rather than text alone. `hoveredIndex`/`pressedIndex` drive a lift-on-hover/settle-on-press effect; hit-testing always uses each card's original (un-lifted) `buttonAreas` entry so the hover lift can't push a card out from under the cursor. **`effectiveScale`, not `getUIScale()` directly, drives every size in this screen** — the naive 3-card row overflowed the canvas on touch devices, since `getUIScale()`'s touch multiplier (2x, tuned for a single centered button elsewhere) applied to three side-by-side cards doesn't leave room. `effectiveScale = uiScale * fitScale`, where `fitScale` shrinks the whole layout proportionally whenever the naive row width would exceed the canvas (checked against `BASE_CARD_WIDTH`/`BASE_CARD_GAP`) — a no-op (`fitScale = 1`) in the common desktop case. This clamp is what keeps a future 4th `OPTIONS` entry from overflowing again.
- `GameScreen.js` (**~1000+ lines — by far the largest file, and the one most likely to need review before extending**) — owns the actual gameplay: creating the cat/mouse/dog/escapes/furniture, cat movement (player-driven or autonomous, depending on `controlledEntity`), dog-vs-cat and cat-vs-mouse collision checks, the punch/toot/meow input reactions and punch shockwave animation, procedural kitchen-furniture layout, sound playback, win/lose messaging, a "play again" button, and the live mouse-escape-danger indicator (see Viewport frame & mouse-escape danger indicator below). Also kicks off cutscenes at the start via `CutsceneManager`.

**Entities** (`js/classes/`) — each is a small, mostly self-contained class with `update()`/`draw(ctx)`:

- `Cat.js` — player-controlled in Cat mode; otherwise (Mouse or Dog mode) driven autonomously by AI instead, but all paths call the same `move(direction, speed = this.speed)`. `speed` is an optional override so `GameScreen`'s AI wander path can move at a different speed than the default. **Gotcha (already fixed, worth knowing): an earlier version silently ignored any override** — validated a proposed move at one speed, then always applied `this.speed` regardless of what was passed — so tuning the AI wander-speed multiplier had no real effect for several iterations before this was caught; `Cat.move()` now genuinely honors the passed-in `speed`. Tracks `this.facingDirection` (`'up'`/`'down'`/`'left'`/`'right'`), updated on every `move()` call — used by the Mouse-mode cat AI's line-of-sight check and by `draw()`'s directional lean. Takes both a `scale` (movement speed) and a `sizeScale` (on-screen/collision size, defaults to `scale`) — kept separate so a display-size change can never accidentally change movement speed (see Mobile responsiveness below). `cat.png`/`cat_v2.png` is a symmetric, front-facing portrait (not a directional side-view sprite like `Dog.js`'s), so `applyDirectionalTransform()` fakes direction: a small rotation leaning into the turn for left/right, a small vertical stretch/squash for up/down — deliberately small (`TILT_ANGLE`/`STRETCH_AMOUNT` constants), since a literal 90° rotation of a round mascot head reads as broken. Gated behind `this.hasMoved` (set on the first real `move()` call) so a freshly-constructed-but-undriven `Cat` (e.g. `Cutscene.js`'s preview) doesn't inherit a phantom squash from the arbitrary `'down'` default facing. Exposed as its own method (not inlined in `draw()`) so `GameScreen.drawRedOutline()` can apply the identical transform to its outline silhouette. **Furniture collision uses a separate, much smaller "legs" hitbox, not the full sprite** — `cat.png` is a big round head over a much narrower body/legs section, and `this.size` (a square, `(originalWidth/3)*sizeScale`) is actually bigger than the full display sprite, which left a visible gap between the cat and furniture corners. `hitboxWidth`/`hitboxHeight` (35%/30% of `displayWidth`/`displayHeight`, measured off the asset's alpha channel) and `getHitboxAt(x, y)` give the legs' actual footprint, horizontally centered under the sprite and anchored to its bottom edge. `GameScreen.tryMoveCat()` calls `aabbOverlap()` directly with this rect rather than `Furniture.isColliding()` (which assumes a square `entity.size`). `this.size` is now only used for the AI's line-of-sight lane width (deliberately unchanged — a wider perception box isn't the same bug as catching from too far away; see "Hitbox tightening" below).

  **`cat_v2.png` — a redrawn, "Disneyfied" sprite sheet, replacing the original `cat.png` art**, per explicit direction to cartoon/modernize it and put it in a pink ballerina dress. Same character identity (white fur, coral/pink inner ears, purple hair-tuft/whisker accents, big grin), glossier cartoon style. Generated as a direct 6-frame sprite-sheet request (one frame per row) rather than stitched single-frame generations — worked cleanly, with the model keeping the character column-aligned across all 6 frames without being told to. Frame geometry (118×150 per frame, 6 frames, single column) was initially kept identical to v1 so `Cat.js`'s dimensions/hitbox ratios didn't need to change. **Later rebuilt at native resolution** (256×296, ~8x more detail) once source images were re-supplied — the original crop-to-legacy-dimensions build was an *upscale* from little source detail and read visibly softer than the source. This required splitting "pixel dimensions used to slice the source rect" from "the logical on-screen size is computed from": `Cat.js` now has `baseFrameWidth`/`baseFrameHeight` (118/150, driving `displayWidth`/`displayHeight`) separate from `frameWidth`/`frameHeight` (now 256/296, native slicing only) — reusing native size directly for display would have rendered the character ~8x too big. `ctx.imageSmoothingEnabled = false` was removed from `draw()` once the resolution bump made every real draw a downscale, where nearest-neighbor sampling looks aliased instead of crisp (smoothing left at the canvas default). A few stray disconnected pixel fragments baked into some frames (found via `scipy.ndimage.label` connected-component analysis, not a rendering bug) were cleaned up by keeping only the largest connected component per frame. `assets/cat.png` (v1) stays on disk, unreferenced, per this project's "deprecate, don't delete" precedent for every asset swap — `Cat.js`'s `spriteSheet.src` and `CharacterSelectScreen.js`'s `PORTRAITS.cat.src` both point at `cat_v2.png`.

- `Dog.js` — in Cat/Mouse mode, wanders continuously (re-picking a random direction every `wanderDirectionChangeInterval` = 1500ms, or immediately on a blocked move via `tryMove(direction, speed)`), the same per-tick pattern `GameScreen.wanderCat()` uses, not the old once-every-2000ms-hop design (see below). In Dog mode, `GameScreen.movePlayerDog()` drives it directly from arrow-key input instead (per-tick, same granularity as `tryMoveCat()`), and `Dog.update()`'s own autonomous wander is bypassed (only `updateAnimation()`/`isColliding()` are still used). Barks on a random interval regardless of mode via `setNextBark()`'s self-rescheduling `setTimeout` chain; `pauseBarking()`/`resumeBarking()` suspend/restart it (a fresh random delay on resume, not a saved remainder) — see "Dog bark persisting past pause/game-over" below for why plain `cleanup()` alone wasn't enough. Takes both `scale` (`speed`/`wallOffset`) and `sizeScale` (`size`/`frameWidth`/`frameHeight`, defaults to `scale`); `wallOffset` deliberately stays tied to `scale` since it's a board-margin concept, not a function of visual size. **Wall/furniture containment is strict** (`proposedX >= WALL_OFFSET && proposedX <= canvasWidth - WALL_OFFSET - frameWidth`, same for Y) rather than the cat/mouse clamps' old "position can dip below `WALL_OFFSET` by up to `size`" convention — that convention assumed `size` exceeded the true visual footprint enough to never push the sprite past the edge, which broke once the dog's `frameWidth`/`frameHeight` (larger than `WALL_OFFSET`) let it hang off the canvas edge entirely. The cat's wall clamp later switched to this same strict shape (see "Hitbox tightening" below). `dog_medium.png`'s 6x6 grid is entirely leftward-facing (confirmed by inspecting the pixels directly — no right-facing source art), so `facingLeft` starts `true` and `draw()` mirrors the sprite via canvas transform only when facing right. Vertical-only movement leaves `facingLeft` unchanged (no dedicated up/down art).

  **`dog_v2.png` — a redrawn, "Disneyfied" walk-cycle sheet**, replacing `dog_medium.png` — same husky identity redrawn in the glossier cartoon look, wearing a purple ballerina tutu, now a single column of 6 frames matching exactly what the game reads (v1 was a 6x6 grid where only column index 1 was ever used). **Getting real per-frame pose variation took three prompt rounds**: a direct 6-frame ask and then an explicit 6-phase gallop-cycle breakdown both produced near-identical "hero pose" frames; scaling back to an ordinary walk cycle (smaller pose deltas between frames to begin with) is what actually let the model vary them — worth remembering if another character gets this treatment: lower the ambition rather than adding more explicit phase description. Processing used a uniform crop box across all 6 frames (so legitimate stride-width variation didn't jitter the character left/right) and bottom-anchored padding (a walking character's feet should sit at a consistent height across frames). **A real bug slipped through two rounds of code-side "fixes" (padding, `imageSmoothingEnabled=false`) before being traced to the asset itself**: 3 frames had tiny disconnected stray pixels baked into the file (a sliver of an adjacent pose's paw/ear landing in the wrong row-band), found via `scipy.ndimage.label` connected-component analysis and fixed by keeping only the largest component per frame — the lesson being that a rendering-looking bug should be checked against the actual asset pixels before assuming it's a code/GPU issue. **Later rebuilt at native resolution** (473×296, same reasoning/approach as the cat's own native-resolution redo above — `BASE_FRAME_WIDTH`/`BASE_FRAME_HEIGHT` (60/38) now drive on-screen size while `nativeFrameWidth`/`nativeFrameHeight` (473/296) drive only source-rect slicing); a second, stricter cleanup pass (alpha>3 threshold instead of alpha>128) was needed to catch faint sub-threshold stray fragments the first pass missed. `assets/dog_medium.png` (v1) stays on disk, unreferenced. **Dog later sized up 20%** on request, once native resolution left headroom for a bigger on-screen draw as a comfortable downscale — `BASE_FRAME_WIDTH`/`BASE_FRAME_HEIGHT` went from 60×38 to 72×45.6. **Flagged live, not yet addressed:** at this size the dog now visibly clips/gets cut off a bit too often ("almost over-compensated") — likely `tryMoveDog()`'s wall/furniture containment (still keyed off the same, now-larger `frameWidth`/`frameHeight`) leaving less clearance, or a UI container sized for the old smaller dog. Revisit by nudging the base size back down slightly rather than reopening the wall-clamp math, unless diagnosed as UI-container-specific.

**Module-level cache-busting** (`GameScreen.js`'s `import Cat from '../Cat.js?v=3'` / `import Dog from '../Dog.js?v=3'`): a query string on an ES module *import specifier* forces the browser to treat it as a distinct module URL, bypassing any cached copy — added after cache-busting the *image* URLs alone wasn't sufficient to resolve a live "still seeing the old bug" report (a stale cached `Dog.js`, not just a stale `dog_v2.png`, reproduces the same symptoms since the fix code itself never runs). **The version number has to be bumped by hand on every edit to the file** — this was missed once mid-session (`Dog.js` edited again without bumping its `?v=2`), silently reintroducing the caching risk. No automated safeguard against forgetting; bump the query string on any further edit. `js/utils/scale.js` got the same treatment (`?v=1` on every importer) when `MOBILE_CHARACTER_SIZE_MULTIPLIER` was tuned and shipped without on-device testing first. `index.html`'s own `<script src="./js/main.js">` tag is deliberately **not** versioned — mirrors `Cat.js`/`Dog.js`/`Mouse.js`'s precedent of versioning the *inner* import, not the entry script. **`styles.css` went uncovered for a long time** — it's a plain `<link>` in `index.html`, not a JS module import, so this convention never touched it until a CSS-only fix (the credits modal's ear shape) appeared not to change anything live even after editing the file — the exact "stale cached copy" symptom this convention exists to prevent elsewhere. Fixed with `<link rel="stylesheet" href="./styles.css?v=2">`; bump it on every future edit to that file too.

  **Dog speed & movement history.** Originally `this.speed` (20 × `scale`) served *both* the autonomous wander (a 2000ms hop) *and*, via `GameScreen.tryMoveDog()` reading `this.dog.speed` directly, the player-controlled per-tick move — one field serving two incompatible roles ("the dog is too fast when playing as it, and too slow when playing as the others"). Fixed by splitting them: `GameScreen.tryMoveDog()` now uses its own `layout.dogPlayerSpeed` (`BASE_DOG_PLAYER_SPEED = 10`, matching `Cat.speed`/`BASE_MOUSE_PLAYER_SPEED` — see Character selection & playable modes below), while `Dog.speed` tunes the autonomous hazard feel independently. The autonomous retune went through two real mistakes worth knowing: (1) the once-every-2-seconds hop cadence itself read as "freezing then teleporting" regardless of hop distance, fixed by switching to continuous per-tick wander; (2) a naive per-tick speed picked in `Cat`'s numeric range was ~50x too fast, since going from "once per 2 seconds" to "every tick" (~60/sec) is itself roughly a 120x multiplier. Fix: derive `this.speed` from the original system's *effective* speed (20×scale px per 2000ms ≈ 10×scale px/sec average) times the actual ask ("twice as fast"), divided by tick rate — `this.speed = 20/60 × scale ≈ 0.33×scale` per tick.

- `Mouse.js` — moves with pseudo-random velocity, bounces off canvas walls, fires a `wallHitCallback` on bounce; in Mouse-controlled mode, `GameScreen.movePlayerMouse()` drives it directly from arrow-key input and calls `wallHitCallback` itself on wall contact, so the sound stays consistent either way. Intentionally **not** blocked by furniture in either mode (no pathfinding, so real collision risks getting stuck against corners); instead `GameScreen.render()` draws the mouse *before* furniture so furniture visually paints over it wherever they overlap, giving a "ducking under furniture" effect — see `drawMouseSilhouette()`/`isHiddenByFurniture()` below for the faint on-top silhouette that keeps it visible. `currentDirection` (`'north'`/`'south'`/`'east'`/`'west'`) is set from player input in Mouse-controlled mode; in autonomous mode `update()` derives it from `speedX`/`speedY` each tick, computed *after* the wall-bounce check so a bounce updates facing the same tick it turns around (previously never updated after construction — stayed `'south'` the whole game). Takes both `scale` (speed) and `sizeScale` (`size`, defaults to `scale`).

  **`mouse_v2.png` — a redrawn, "Disneyfied" sprite sheet**, replacing `mouse.png` — same identity (small round brown/tan mouse, big pale-pink-inner ears, curling tail), glossier cartoon style, now a green ballerina tutu with a bow. **Kept v1's exact 3-col × 4-row grid (walk-cycle × facing direction, true top-down camera) rather than switching to the cat/dog's single-direction-plus-mirroring approach** — a first attempt following that playbook produced a bipedal upright dancer, rejected twice as wrong ("I want the angle and movements of the mouse the same as the current sprite sheet"; "the mouse should remain on all fours"). The prompt that worked locked the camera angle, matched v1's per-row pose order exactly, and repeated "quadruped/on all fours/NOT bipedal" explicitly — "ballerina" alone carries a strong bipedal-dancer association most image models default to even against quadruped instructions. Processing used row-uniform cropping (each direction's 3 frames cropped to their row's shared union bbox, not per-frame-tightest) so frames don't jitter frame-to-frame, then padded all 12 frames into one shared global square cell (327×327) since `Mouse.js`'s `draw()` already forces every direction into the same square destination regardless of source aspect. `frameWidth`/`frameHeight` (native slicing) went from 32×32 to 327×327; `this.size` (on-screen/collision, `32 * sizeScale`) untouched, so gameplay feel didn't change, only crispness. `assets/mouse.png` (v1) stays on disk, unreferenced.

- `Escape.js` — a mouse hole; collision (`isMouseInside()`) is a plain AABB rectangle, but `draw()` renders a rotated arch shape (see Wall band & mouse holes below). `isMouseInside()` is the *loose* check only — used to exempt the cat/dog's wall clamp near the gap this escape leaves in the wall — while the actual "mouse escaped" trigger uses the stricter `hasMouseEntered()` instead (see "Hitbox tightening" below).
- `Furniture.js` — kitchen/dining obstacle (counter modules, fridge, dining set). Takes `(x, y, type, spriteSrc, rotation = 0, spriteWidth = 32, spriteHeight = 64, scale = 1.5, cropX = 0, cropY = 0)`; every kitchen piece today passes explicit width/height/scale overrides (the defaults are a leftover from an earlier asset generation). `spriteWidth`/`spriteHeight` describe the sprite's actual visible *content* size, not the file's full pixel dimensions — `cropX`/`cropY` (every current `kitchen_*.webp` has several px of transparent padding baked in) tell `draw()`'s `drawImage()` where the real content starts, which is what makes adjacent wall modules sit flush. Rotation (0/90/180/270) swaps width/height and is applied via canvas transform, centered on the same pivot the collision box uses — used by the left/right wall cabinet runs (rotation 180 unused anywhere). **No longer sets `ctx.imageSmoothingEnabled = false` before drawing** — a leftover from when kitchen sprites were small pixel art; every current `kitchen_*.webp` is a large photorealistic render drawn at much smaller on-screen size (a downscale), and nearest-neighbor downscaling drops detail rather than blending it — reported live as furniture looking "nowhere near" the source render's quality. Removed; left at the canvas default (smoothing on). **Lesson: `imageSmoothingEnabled = false` is only correct for upscaled/pixel-art sprites — once art is high-res and displayed at a downscale, turn it back on.** Draws a type-colored placeholder rect while the sprite loads. `isWallItem` is computed in the constructor but never read anywhere — dead property.
- `InputHandler.js` — tracks currently-held keys via `window` keydown/keyup listeners, exposes `getDirection()`; also dispatches custom `'toot'` (spacebar), `'punch'` (`p`), and `'meow'` (`m`) events for `GameScreen` to react to.

**Cutscenes** (`js/classes/cutscenes/`):
- `Cutscene.js` / `CutsceneManager.js` — sequenced intro scenes shown before gameplay starts, triggered from `GameScreen.startCutscenes()`. `Cutscene.render()` fills the whole canvas with the same teal-to-gold diagonal gradient `CharacterSelectScreen` uses (previously left uncleared, showing the canvas's own white CSS background) and draws a rounded gradient card (`drawRoundedRect` — a plain rounded rect, not the cat-ear shape, since this modal carries a full paragraph plus a portrait and button) with a purple-accent border and a pop-in animation (ease-out-cubic scale+fade). `getButtonRect()` is shared by `render()` and `handleNextClick()` so the drawn "Next" button and its click hit box can't drift apart. The cutscene text's font size has a fixed minimum (`Math.max(16, 32 * this.scale)`) but `render()` also measures text width and shrinks further (down to an absolute floor of 10px) only when it would overflow the card — a fixed floor alone let long lines ("Say hello to Dummy, the dumb dog!") overflow at small canvas scales. **`render()` calls `this.characterAnimation.update()` with no arguments** (only wants the walk-cycle frame to advance) — safe for `Cat`/`Mouse` but was a real bug for `Dog`, whose `update(timestamp, cat, onCatCollision)` ran its full autonomous-wander logic on `undefined` input, visibly drifting the dog across the cutscene card. Fixed in `Dog.update()` by bailing to animation-only when `timestamp` is `undefined`. **Character sprite sizing is decoupled from `GameScreen`'s in-game `characterScale` entirely** (`CUTSCENE_CHARACTER_FILL_RATIO = 0.9`) — the in-game scale left sprites under 10% of the modal's height, so `render()` computes the vertical band available above the text each frame and derives a `spriteScale` from the character's own aspect ratio, applied via `ctx.translate`+`ctx.scale` (temporarily overwriting `characterAnimation.x`/`y` each frame) rather than reconstructing at a different `sizeScale`.

  **The bigger-character pass surfaced two real, previously-invisible bugs, both fixed in the same round.** (1) **`CutsceneManager.playCutscene()` never stopped the previous cutscene's own self-scheduling `requestAnimationFrame` loop** — every loop checked the same shared `this.isPlaying` flag, which only goes `false` once *all* cutscenes finish, not on advance. By the 3rd cutscene, three loops were all clearing+redrawing the canvas every frame, each painting a different cutscene's card/character in whatever order callbacks fired — invisible at the old small character size, reported live as the mouse "bugging out" and the dog's ears looking duplicated once characters got bigger. Fixed by tracking the active loop's handle and calling `cancelAnimationFrame()` before starting a new one. (2) **The no-argument `update()` call was never actually safe for `Mouse`** — `Mouse.update()` has no timestamp guard and unconditionally moves/bounces off canvas walls every call; once the sizing rework started overwriting `characterAnimation.x`/`y` every frame to a small local origin, `Mouse.update()` read that as hitting a wall on every single frame, flipping direction constantly. Fixed with `Cutscene.advanceAnimationOnly()`, a small duck-typed helper that calls each class's own frame-only method directly (`updateAnimations()`/`updateAnimation()`) instead of routing through `update()` at all — cutscenes can never trigger movement/AI logic regardless of what `update()` does with no arguments.
- **Modal pop-in sound** (`playModalPopSound()`, `js/utils/audio.js`): a short synthesized "pfff" whoosh — filtered white noise with a fast attack/decay envelope and a downward filter sweep, not a supplied file like every other sound in this game — nothing in `sounds/` fit, and a one-shot effect this simple was straightforward to synthesize via Web Audio. Fires from `Cutscene.init()` (alongside, not instead of, the existing per-cutscene `soundCallback`) and from the Credits button's click handler in `settingsMenu.js`. Gated on `isSfxMuted()`. **Deliberately not used by `GameScreen.displayGameOverModal()`** — that has its own dedicated `playWinSound()`/`playLoseSound()` instead (see Game-over modal below).

**Utilities** (`js/utils/`):
- `collision.js` — exports `aabbOverlap(ax, ay, aWidth, aHeight, bx, by, bWidth, bHeight)`, the single shared AABB overlap test. Used by `Escape.isMouseInside`/`hasMouseEntered`, `Dog.isColliding`/`tryMove`, `Furniture.isColliding`, `GameScreen.checkCollision`/`tryMoveCat`/`tryMoveDog`, and `GameScreen`'s cat-AI line-of-sight and spawn-safety checks. Takes raw coordinates rather than entity objects so each caller stays explicit about which field it's using per side — don't refactor it to accept entities and guess the right field, since the same object (e.g. `Dog`) legitimately uses different box dimensions on different sides of a check. `Cat`'s and `Dog`'s own furniture-collision checks call this directly rather than `Furniture.isColliding()` (which assumes a square `entity.size`) — see "Hitbox tightening" below.
- `characterNames.js` — exports `CHARACTER_NAMES` (`{ CAT: 'Mia', MOUSE: 'Poop', DOG: 'Dummy' }`), the single source of truth for both `GameScreen.js` and `CharacterSelectScreen.js`.
- `canvasShapes.js` — exports `drawRoundedRect(ctx, x, y, width, height, radius)`, a rounded-rect path builder (doesn't fill/stroke itself). Shared by `GameScreen`'s game-over modal/button, `Cutscene`'s modal/button, and `CharacterSelectScreen` (before it switched to the cat-ear shape). Also exports `drawCatEarCard`/`drawCatEarInner` (a `drawRoundedRect`-shaped body with two ears above the top edge, tips via `quadraticCurveTo` for a soft "kitten ear" curve rather than a sharp triangle) and matching `drawMouseEarCard`/`drawMouseEarInner` and `drawDogEarCard`/`drawDogEarInner`. Used by `CharacterSelectScreen`'s cards via `EAR_SHAPES`.

  **Mouse ears** landed on the first attempt: big, perfectly round Mickey-style domes via a true `ctx.arc()` (traces the upper half of a circle centered *on* the top edge line, so the arc's endpoints already land on that line with no extra join math needed) rather than the cat's `quadraticCurveTo` approximation.

  **Dog ears took three rejected attempts before landing** — worth knowing if this ever needs a fourth: (1) a symmetric lean poking up from the top edge read as "a lopsided round ear," i.e. a mouse-ear variant, not a distinct animal; (2) side-hanging ears bulging off the left/right edges (tried as both a symmetric petal and a tapered teardrop) were rejected as "hard to tell they are ears" — a shape stuck onto the *side* of a rectangle doesn't read as "attached to a head" the way something poking up from the top does; (3) **current**: back to poking up from the top edge, built from a `dogEarFlopCurve()` helper — a single cubic Bézier per ear whose two independently-weighted control points let one side rise steeply (inner/attachment-facing) while the other droops low (outer/corner-facing), a genuine asymmetric "flop" a quadratic's single symmetric control point can't produce. **Note if retuning:** the nominal `peakHeight` parameter is not the curve's actual rendered peak — a cubic Bézier pulled by two control points falls well short of either control point's raw offset, so peak height needs to be checked by simulating the curve numerically, not by reading the parameter. Currently `height * 0.4`, rendering to ~51px, matching the cat ear's ~52px peak while staying under `BASE_TITLE_GAP` (70). The shape is a smooth single rise-then-droop, not a true two-stage fold — flagged as the best reasoned attempt at ship time, not guaranteed-final.
- `audio.js` — two independent module-level mute flags (not per-screen state, so they survive "Play Again"): `isMusicMuted()`/`setMusicMuted()`/`toggleMusicMuted()` (starts `true`) and `isSfxMuted()`/`setSfxMuted()`/`toggleSfxMuted()` (starts `false`) — see Settings menu & audio below for why the two default differently. Each setter fires a `document` event (`musicmutechange`/`sfxmutechange`) so an already-playing looping sound can react immediately. Also exports the game's synthesized one-shot SFX (`playModalPopSound()`, `playWinSound()`/`playLoseSound()`, `playPlantKnockOverSound()`, `playDooberSound()`, `playCoinLandSound()`), all gated on `isSfxMuted()` and called directly by their trigger sites rather than through `GameScreen.playSound()` (which only knows the file-backed `SOUND_KEYS` map). See Currency & economy system below for `playDooberSound()`/`playCoinLandSound()` — two deliberately different cues for two different moments (a doober being picked up vs. its "+N" landing in the HUD), not the same sound twice.
- `settingsMenu.js` — wires up the in-game hamburger menu (`#settingsMenu` in `index.html`) — see Settings menu & audio below.
- `api.js` — thin wrapper around `kpground-api`'s REST endpoints (`getWallets()`, `submitRound()`, `purchaseItem()`, etc.) — see Currency & economy system below for the wallet model this talks to.
- `storeModal.js` — wires up `#storeModal` (the DOM "Store" list opened from the HUD) — see Currency & economy system below.

## Floor background (`GameScreen.drawFloor`)
`render()` fills the whole canvas with a repeating two-tone tile pattern before drawing anything else — canvas-drawn, not CSS, generated on an offscreen canvas at draw time (`drawFloor()`, cached on `this.floorPattern` via `ctx.createPattern(..., 'repeat')`), so there's no async load to wait on. Currently a small 24px flat white/off-white tile (`COLORS.FLOOR_LIGHT` `#ffffff`/`FLOOR_DARK` `#f9f8f4`), sized like a fine modern kitchen floor tile relative to the furniture. Colors are deliberately **plain and neutral, not matched to the `kitchen_*.webp` furniture's warm cream/tan/honey-oak palette** — two earlier warm-toned floor versions were tried and rejected live for blending into the furniture instead of reading as floor beneath it; white/off-white reads as a distinct surface regardless of furniture palette.

## Wall band & mouse holes (`GameScreen.drawWalls`, `Escape.js`)
`render()` draws `drawWalls()` right after `drawFloor()` and before escapes/mouse/furniture — a `WALL_BAND_THICKNESS` (16px) band flush against all four canvas edges, filled with `COLORS.WALL_FILL` and outlined with two `COLORS.WALL_TRIM` strokes so it reads as wall thickness rather than a flat stripe. This is purely presentational — unrelated to `WALL_OFFSET` (40px, used by `moveCat()` to clamp how close the cat can get to the edge).

Furniture's *back* (the edge facing the wall) is aligned flush against the wall band's *front* face — `WALL_BAND_THICKNESS` in from the canvas edge, not the raw edge — on all four walls. This is a deliberate fix after an earlier version placed furniture flush to the raw canvas edge, which painted over the wall band's inner border wherever furniture existed while non-furniture stretches showed the full band — an inconsistent "sometimes there's a wall margin, sometimes not" look.

`Escape.draw()` renders a small rounded-arch cutout (flat bottom, domed top — classic cartoon mouse-hole silhouette) filled with a black-to-dark-brown radial gradient, instead of a flat filled rectangle. `Escape` takes a `wall` param (`'top'`/`'bottom'`/`'left'`/`'right'`, default `'top'`) and rotates the shape around its own center so the opening always faces into the room regardless of wall. Collision (`isMouseInside`) is untouched — still a plain AABB rect, since the visual rotation doesn't change the (square) bounding box.

## Kitchen furniture (`GameScreen.generateKitchenFurniture`)
Procedurally lays out `Furniture` instances each game reset from `assets/kitchen_*.webp` (`cabinet`/`sink`/`stove`/`fridge`/`table`, plus `plant`/`cart`/`shelf`). This is the **fourth complete art direction** for kitchen furniture — earlier rounds tried crops from one whole AI-generated scene (alignment problems since cut edges didn't match real object boundaries), a free flat-cartoon sprite pack (matched the mascot characters but the user explicitly wanted photorealism instead — "I want the game board kitchen to look as realistic as possible"), and individually-generated photorealistic objects at a 3/4 camera tilt (rejected live: objects didn't connect edge-to-edge, each baked in its own clashing camera angle). **The core lesson carried forward from that history: modularity is a property of the camera angle and crop, not the rendering fidelity** — a flatter, near-orthographic top-down angle is what lets modules tile edge-to-edge with no seam, regardless of how photorealistic the individual render is. A later attempt to reshoot the cabinet in a more-tilted, more-detailed style (to match freestanding pieces like the cart/plant/table) was tried and reverted for the same reason ("they still dont connect"). Current: `assets/kitchen_*.webp`, same flatter working angle, same modular wall-building/gap mechanism (never actually a rendering-style problem) extended to all four walls.

These files were originally raw PNGs (~4MB total), converted to WebP (quality 90) at the same pixel dimensions with no visible quality loss (~550KB total) — only the file extension and sprite paths changed, not any dimension constants.

**Every `kitchen_*.webp` module has a few px of transparent padding baked in around its actual content** — `MODULE_SPECS`/`FRIDGE_SPEC`/`TABLE_SPEC` all store the trimmed content size plus a `cropX`/`cropY` offset (`Furniture.draw()` source-rect-crops to just that region), since without this two modules placed bounding-box-to-bounding-box would show a visible gap. **Any new render added should be checked for this same padding issue before wiring in `width`/`height`/`cropX`/`cropY`** — measure the alpha-channel content bbox, don't assume a new file is tightly cropped.

**Decorated counter variants** (`counterBlender`, `counterMicrowave`, `counterToaster`, `counterFlowers`, `counterMail`) — small appliances/items on an otherwise-plain counter, opportunistically substituted into cabinet slots on the top/bottom walls. Each was a separate re-shoot in the same true top-down angle, individually cropped/verified for real RGBA alpha and a clean content edge before wiring in. **Two real bug classes worth knowing if more decor variants are added:**
1. **Some early exports were flat opaque RGB with no alpha channel at all** (baked-in solid studio background), which no amount of alpha-bbox cropping could ever find a tight edge for — **verify `Image.open(...).mode == 'RGBA'` before trusting any alpha-bbox crop measurement**, since a bbox scan on an opaque RGB image silently reports "the whole canvas is content" with no error.
2. **A vignette effect on some raw exports gave faint-but-nonzero alpha well beyond the real content**, inflating a naive full-image `alpha.getbbox()` scan. Fixed by sampling per-row/column opacity *fraction* (not just presence) across the content's own coordinate range to find the real sharp edge.

`counterFlowers` (the one repeatable decor type) surfaced a deeper bug: **all four decorated-counter renders are wider than plain cabinet at matched on-screen height** (their aspect ratio is wider), so a fridge-fit width calculation that summed plain cabinet's width for every 'cabinet' slot (computed *before* decor substitution ran) could under-reserve space on a wall that later got a wide decor swap — a real, small (~3px) overlap confirmed in sampling. Fixed by computing the fit check against the *actual resolved* wall arrays (after density-trim and decor substitution) rather than a static worst-case guess computed too early — **general lesson: any "reserve space for the worst case" calculation needs to run after the randomization/substitution it's reasoning about, not before, once the substituted content can be strictly larger than the baseline.**

**Default filler is now a matching blank counter** (`FURNITURE_SPRITES.CABINET` → a re-shot blank counter in the same style, replacing the original marble-slab `kitchen_cabinet.webp` as the default filler), with the appearance mechanism unified into one shuffled "offer pool": `COUNTER_ONE_OFF_TYPES` (each type once) plus `'counterFlowers'` repeated `COUNTER_FLOWERS_MAX_APPEARANCES` (2) times, one pass offering each pool entry one shot at one pooled cabinet slot. **This swap needed two related fixes, both from the same root cause — reservation/placement math reading raw, un-scaled dimensions instead of going through the type's actual render multiplier:** (1) `computeLayout()`'s wall-height reservations read `MODULE_SPECS[type].height` raw rather than scaled by the new blank tile's own multiplier, over-reserving wall depth and starving the interior playable area (500-sample test found 642 overlaps before the fix, 0 after); (2) `buildWallVertical()` (left/right walls) still built modules with plain `moduleScale` instead of `moduleScaleFor(type)`, a pre-existing gap that only mattered once cabinet itself needed scaling. **`MODULE_SCALE_MULTIPLIERS`/`CABINET_TARGET_HEIGHT`** (470, the original cabinet render's own content height) is the structural fix: cabinet is now a normal entry in the scale map rather than an implicitly-exempt baseline — worth remembering if another "always-baseline" type ever gets its own art swap.

**Fridge**: placement now varies by wall (`fridgeWall`, randomized among top/bottom/left/right, checked via `fridgeFitsWall` before picking so a bad fit doesn't just get clamped/overlapped after the fact). `FRIDGE_ROTATIONS = {top:0, bottom:180, left:270, right:90}` — **the opposite mapping from cabinet's own per-wall rotation** — because a flat countertop recedes uniformly toward the wall (image-top = back is correct), but a tall appliance's image-top detail (a door seam) and image-bottom detail (a vent band) read the opposite way; positioning math didn't need to change, only which rotation constant is used. **A structural bug worth remembering for any future per-wall fit-check**: the top/bottom fridge-fit check originally reasoned about a worst-case guess (every 'cabinet' slot in the static wall order assumed to become the single widest possible decorated variant), computed *before* density-trim/decor-substitution had run — once 5 decorated variants existed, that guess became so pessimistic it made top/bottom *permanently* fail their own fit check at every canvas size, so the fridge stopped landing there at all (0/500 sampled layouts). Same "reorder to reason about ground truth, not a too-early guess" fix as the `counterFlowers` bug above. `LEFT_WALL_ORDER_WITH_FRIDGE`/`RIGHT_WALL_ORDER_WITH_FRIDGE` (1 cabinet each, vs. the normal 2) exist because the side walls' normal order plus the fridge never fits the vertical band's height at *any* canvas size (the board's fixed ~4:3 aspect always makes the vertical band proportionally shorter than horizontal walls' width).

**Stove and sink re-shoots exposed the same aspect-ratio pitfall, worth remembering for any future module re-shoot**: matching only the *height* of a replacement render to the original (the pattern that worked fine for cabinet/fridge) isn't safe if the new render's aspect ratio is wider than the original's — a wider-at-matched-height render can overflow a wall row that fit the original fine. **Fix pattern: cap the new module's scale multiplier to `Math.min()` of the width-preserving and height-preserving ratios**, guaranteeing the new render never exceeds the original's on-screen footprint in either dimension — check the new render's aspect ratio against the original's before wiring in, not just its height.

**Dining set**: a single table render (with all four chairs and a full place-setting baked into the image) rather than a separate table+chair pair — the project owner reviewed a newer table render that happened to include its own chairs/setting, liked it as-is, and asked to drop the separate chair piece entirely. `assets/kitchen_chair.webp` stays on disk, unreferenced, per the deprecate-don't-delete precedent, even though nothing references it. `TABLE_SCALE_MULTIPLIER = 0.55` (tuned by eye) — the all-in-one render's raw height dwarfed other furniture at the wall-module scale, since (unlike the old two-piece layout, which only ever added width) this adds real height too; needed its own dedicated multiplier on top of `diningScale` rather than touching `diningScale` itself (every wall module depends on that shared value). **Table is passable for the cat with a shake reaction** (`'table'` in `CAT_NON_BLOCKING_FURNITURE_TYPES`, not `DOG_NON_BLOCKING_FURNITURE_TYPES`) — see Furniture shake reaction below.

**Plant, cart, shelf** — small freestanding corner/wall decor pieces (`assets/kitchen_plant.webp`/`kitchen_cart.webp`/`kitchen_shelf.webp`), placement prefers a room corner (tries all 4, shuffled, checked against the shared `overlaps()`/`blocksSpawn()` helpers the dining set already uses), falling back to a randomized search along a wall if every corner is occupied; no placement at all is a normal no-op. **Per-entity passability differs and is deliberate, not an oversight**: the plant is passable for *both* cat and dog (`CAT_NON_BLOCKING_FURNITURE_TYPES`/`DOG_NON_BLOCKING_FURNITURE_TYPES` both include `'plant'`); cart and shelf are passable for the cat/mouse but solid for the dog (`CAT_NON_BLOCKING_FURNITURE_TYPES` includes `'plant'`/`'cart'`/`'shelf'`/`'table'`, `DOG_NON_BLOCKING_FURNITURE_TYPES` stays `['plant']`) — a believable "cat can duck past, dog has to route around" split. Note: the *autonomous* dog wander (`Dog.js`'s own `tryMove()`, used in Cat/Mouse mode) has no opt-out list of its own and already collides against every furniture piece unconditionally, so it treats cart/shelf/plant as solid regardless of `DOG_NON_BLOCKING_FURNITURE_TYPES` — a known, harmless inconsistency versus the player-controlled dog path, not something ever fixed.

- **Cart's placement order and size both had real bugs, caught by live use ("I tried 5 times and never saw it"), not by code review.** At its first-shipped scale (`0.45`, tuned by eye) and with the plant's own corner-search running first, the cart lost the fight for the 4 corners/wall gaps roughly 1 in 4 layouts. Fixed by (a) moving the cart's placement block to run *before* the plant's, so the bigger piece gets first pick, and (b) dropping `CART_SCALE_MULTIPLIER` to `0.32`. **General lesson for any future freestanding decor piece: whichever has the biggest footprint needs to place first**, and an eyeballed scale that "looks right in isolation" can still be too big to place reliably — check actual placement success rate via sampling, not just visual review.
- **Cart also needed its own rotation map** (`CART_ROTATIONS = {top:0, bottom:180, left:270, right:90}`, matching cabinet's convention, not fridge's) once it shipped with no rotation at all and its detail (lower shelf, wheels) only faced correctly into the room on the top wall.
- **Shelf learned the cart's lessons proactively rather than repeating them live**: `SHELF_SCALE_MULTIPLIER = 0.35` was picked conservatively from the start, and since the shelf's native content is even bigger than the cart's, its placement block runs before the cart's (order: shelf → cart → plant, biggest-first). Passability shipped fully-blocking-for-both first, then was reversed to match the cart's cat-passable/dog-solid split on request.
- **Placement priority was later flipped: decorated counters fill first, blank cabinet is the leftover filler** — per explicit direction, the substitution loop no longer coin-flips each pool entry into an available slot, it takes the slot outright. Under current pool size (6 tickets: 4 one-offs + flowers×2) vs. max possible cabinet slots (also 6), this means blank cabinet effectively never appears on top/bottom walls anymore — flagged directly in the code as the lever to pull (shrink the pool) if this reads as too much decoration.

Layout, per reset:
1. **Top and bottom walls are built from wall-module renders** (`cabinet`, `sink`, `stove`) placed edge-to-edge via `buildWall()`, each computing its own scaled width off its own native size (not a shared grid). `TOP_WALL_ORDER`/`BOTTOM_WALL_ORDER` give each wall a fixed sequence, kept deliberately conservative (sink/stove appear exactly once each on top, cabinet doubles as filler) to avoid two identical sinks/stoves visible at once — a real problem the very first version of this round hit before being fixed.
   - **Density varies per game** (`pickWallDensity()`) — every wall used to always build its entire static order, which read as every kitchen looking equally "full" ("Some kitchens have a lot of counter space, some don't"). `pickWallDensity(fullOrder)` picks a random subsequence of each wall's order per reset. Deliberately **not** threaded into the fridge-fit check or `computeLayout()`'s wall-height reservations — both intentionally keep reasoning about the full static arrays, since a thinner wall only ever leaves more room than assumed, never less. Floor is half of each wall's own full length, rounded up (raising an initial too-low floor of 1/0 that read as "furniture now too few" when live-tested).
2. **Left and right walls**: `buildWallVertical()` places `LEFT_WALL_ORDER`/`RIGHT_WALL_ORDER` (cabinet reused twice each) edge-to-edge vertically, rotated 90°/270°. Confined strictly between `TOP_WALL_HEIGHT` and `canvas.height - BOTTOM_WALL_HEIGHT` so they can never overlap the top wall's fridge or the bottom wall's run.
3. **Back-to-wall alignment on all four walls** (not a floor baseline) — each module's back edge is flush against the wall band's front face. An earlier baseline-aligned-by-front-edge version let a shorter piece's back stop short of the wall, leaving a visible gap once the wall band was added. Tradeoff accepted: front (room-facing) edges vary slightly per piece since renders have different native heights.
4. **One random gap**: each reset, one of the top/bottom walls is picked at random (`gapWall`), one module slot is left empty, recorded as `this.wallGap`, and `generateEscapes()` places the first escape centered there. Left/right walls are never in the gap pool (that math only handles horizontal walls today). Survived all four art-direction changes unmodified — never actually a rendering-style problem.
5. **Cabinet's trim is single-sided, not the raw render's own double-sided edge** — the raw `kitchen_cabinet.webp` has an identical wood ledge on both top and bottom edges of the image, which (drawn unrotated on every wall) left a second, purposeless-looking shelf floating on whichever wall's room-facing edge didn't naturally line up. Fixed by tightening `MODULE_SPECS.cabinet`'s crop to exclude the top band, then adjusting rotation so the remaining trim faces the room on every wall (`makeModule()` draws bottom-wall cabinets at `rotation: 180`; `LEFT_WALL_ROTATION`/`RIGHT_WALL_ROTATION` = 270/90).

**Spawn points must stay clear of wall collision boxes:** `TOP_WALL_HEIGHT`/`BOTTOM_WALL_HEIGHT`/`LEFT_WALL_WIDTH`/`RIGHT_WALL_WIDTH` are each `WALL_BAND_THICKNESS` plus the max scaled height among whatever's actually placed on that wall, **including `FRIDGE_SPEC.height`** (since the fridge can land on any of the 4 walls, and this layout is computed before that per-reset pick happens). `SPAWN_CLEARANCE` is what `resetGameObjects()` uses on top of the wall-height constants — this is the same class of bug (a spawn landing inside a wall's collision box) hit more than once in this project's history; check it whenever wall dimensions or character/fridge sizing changes. The mouse's fixed spawn (100, 100) is exempt since it doesn't collide with furniture at all.

The `tabletop_*`/`*_corner`/`wallframes`/`wallknife` assets from the very first WIP commit are **not** dining furniture — they're an unused pool table/wall knife rack/framed art. Don't reach for these.

## Plant knock-over reaction (`Furniture.startKnockOver`, `GameScreen.updatePlantBump`, `playPlantKnockOverSound`)
The cat or dog running into the plant tips it over with a short animated fall and a synthesized thump/scatter sound, replayable every time either one touches it — not a one-shot flag. `Furniture.startKnockOver(timestamp)` always (re)starts the fall from upright even mid-animation; `draw()` computes the current tilt from an ease-out-cubic from 0 to `KNOCK_OVER_ANGLE` (75°, not a full 90° — landing perfectly flat reads as a broken transform snap), added on top of the piece's own base rotation. `GameScreen.updatePlantBump()` is a read-only overlap check against the cat's and dog's full display boxes, run every tick — **edge-triggered on `this.plantWasHit`, not fired on every tick of continuous overlap**, since standing on the plant for a few frames would otherwise restart the animation/sound every tick and read as a stutter. `playPlantKnockOverSound()` is synthesized (a low pitch-dropping sine "thud" layered simultaneously with a brief high-passed noise burst for scattering dirt/leaves) rather than a supplied file, since nothing in `sounds/` fit.

### Cart bump sound (`GameScreen.updateCartBump`, `sounds/cart_bump.mp3`)
**Three synthesized attempts (square-wave knock, oscillator "clink," bandpass-noise "rustle") were each reworked live and rejected** ("still awful" after three tries) — rather than guess a fourth time, a real AI-generated sound recording was sourced and supplied directly, matching how every other sound in this game already works; the synthesized attempts were deleted as dead code once the file replaced them. **General lesson: don't keep iterating synthesized SFX indefinitely — a real recording is often the faster and better path once a couple of synthesis attempts have already been rejected.**

**Not a fire-and-forget one-shot — the playback model is driven directly, not through `playSound()`**: "it should only play for the duration of the cat being 'on' the shelf or in the hit zone... only advance sound if the cat is moving while inside the hit zone." Three states: in the zone and moving → playing, resumed (not restarted) if already paused; in the zone but not moving → paused in place, `currentTime` held; out of the zone entirely → paused and reset to 0. "Moving" is `this.catMovedThisTick` (`GameScreen.js`), OR'd (not overwritten) and set from inside `tryMoveCat()` itself — deliberately not "is a direction key held," since a cat pressed into a wall with nowhere to go isn't actually moving, and the AI-driven cat has no "key held" concept at all; `tryMoveCat()`'s own return value is the one signal both control modes share.

### Shelf bump sound (`GameScreen.updateShelfBump`, `sounds/shelf_bump.wav`)
Sourced as a real recording from the first request (skipping synthesis entirely, given the cart's rejected attempts above). **Unlike the cart, a plain fire-and-forget one-shot** — first shipped mirroring the cart's play/pause/`currentTime` model, then simplified on request ("let's just play the full sound once on entry") since that duration-tracking model was tuned for the cart's own feel specifically, not a universal requirement. Edge-triggered on `this.shelfWasHit`, same shape as `updatePlantBump()`. Cat-only (the shelf blocks the dog outright, so there's nothing for the dog side to react to).

### Furniture shake reaction (`Furniture.startShake`, `updateTableBump`/`updateCartBump`/`updateShelfBump`)
Table joined `CAT_NON_BLOCKING_FURNITURE_TYPES` with a dedicated shake reaction, not the plant's knock-over — a full dining set tipping over would read as broken, not charming. `Furniture.startShake(timestamp)`/`this.shaking`/`this.shakeStartTime` mirror `startKnockOver()`'s shape (replayable, every bump restarts it) but `draw()` computes a small decaying sine oscillation (`SHAKE_DURATION` 400ms, `SHAKE_MAX_ANGLE` 5°, `SHAKE_CYCLES` 3) instead of an ease-out fall to a fixed angle. `GameScreen.updateTableBump()` is cat-only, edge-triggered on `this.tableWasHit`, calling both `table.startShake()` and `playSound(SOUND_KEYS.TABLE_SHAKE)`. **Extended to cart and shelf later on request.** Shelf's was trivial (same edge-trigger already gates its sound, shake call sits right next to it). Cart needed its own independent edge-detection flag (`this.cartWasHit`) since its sound already has a continuously-driven play/pause model — reusing that same continuous signal to drive `startShake()` would restart the wobble every tick the cat is moving in the zone, reading as a stutter rather than one rattle per approach.

**`SOUND_KEYS.TABLE_SHAKE`/`sounds/table_shake.mp3` were wired before the recording was supplied, surfacing a real gap**: a missing/unsupported audio source makes `playSound()` throw *synchronously* (`sound.currentTime = 0` itself throws, not just the `.play()` promise) rather than failing silently. `playSound()` now wraps the `currentTime`/`play()` pair in `try`/`catch` as a general safeguard, kept even after the file arrived — the next sound wired ahead of its recording will hit the same gap otherwise. The recording itself took two prompt rounds: a first attempt with "wood creak" language in the prompt came back sounding like a creaky door, not dishware — fixed by dropping that entirely and leading with the actual target (ceramic/metal/glass dishware clinking) while explicitly ruling out wood creak/door/crash/breaking-glass in the prompt.

## Punch mechanic
- `p` → `InputHandler` dispatches a `'punch'` custom event on `document`.
- `GameScreen` listens for `'punch'` in `init()`, plays `SOUND_KEYS.PUNCH`, and calls `handlePunch()`, which knocks the dog `PUNCH_DISTANCE` (40px) away from the cat (clamped to canvas bounds) and starts a purple `shockwave` ring centered on the cat, drawn by `drawShockwave()` for `PUNCH_SHOCKWAVE_DURATION` (200ms).
- `m` → dispatches a `'meow'` event, which just plays the meow sound (no gameplay effect).
- Both `handlePunch()` and `handleToot()` (space bar — same dog-shoving effect, smaller `MOVE_DISTANCE`) no-op their positional effect (sound still plays) whenever `controlledEntity === 'dog'` — shoving the dog away from the cat makes sense as protecting a bystander from an autonomous hazard, but not when the player *is* the dog trying to reach the cat on purpose.

## Settings menu & audio (`js/utils/audio.js`, `js/utils/settingsMenu.js`, `index.html`, `styles.css`)
A hamburger button (`#settingsToggle`, inside `#settingsMenu`) opens a dropdown (`#settingsPanel`) with two independent toggles — Music and Sounds. They default differently on purpose: music starts muted (a looping track starting unprompted is worse than silence), SFX starts unmuted (punch/toot/meow are tied directly to a player's own action — muting by default would make actions feel like they do nothing). `GameScreen.playSound()` checks `isSfxMuted()`; the background track's start and a live `musicmutechange` listener check `isMusicMuted()`.

### Background music persistence (`js/utils/audio.js`, `GameScreen.startGame`/`restartGame`)
The track (`sounds/you_can.mp3`) is a **page-lifetime singleton Audio element** in `js/utils/audio.js` (`getBackgroundMusic()`/`getBackgroundMusicElement()`), not something each `GameScreen` owns and recreates — per explicit request: *"can you have the song keep playing? It should run through even after a game over. The only thing that should start it over is a refresh. Dont start it until in game though."* Three things changed together: (1) starts from `startGame()` (when `this.running` actually flips true) rather than `GameScreen.init()`, so it can't start during intro cutscenes; (2) `restartGame()` no longer pauses it before tearing down the old `GameScreen` — the track just keeps playing through "Play Again"; (3) `loadSounds()`'s `SOUND_KEYS.BACKGROUND` aliases `getBackgroundMusicElement()` directly rather than constructing a new `Audio` per `GameScreen` instance. Only an actual page refresh (fresh module evaluation) starts it over.

- **Positioning differs by device.** Desktop anchors to the board via pure CSS — `<main>` is `relative inline-flex` so it shrink-wraps tightly around the canvas, and `#settingsMenu` (a DOM child of `<main>`, right after the canvas) is `position: absolute; top: 20px; right: -60px`, tracking the board through the browser's own layout engine rather than any JS measurement. **This is the third attempt** — two earlier JS-measured approaches (gutter-centering, then a `resize`-recomputed fixed offset) were each flagged live as still overlapping the board in an environment this project couldn't fully reproduce; a leading theory was that Tailwind's CDN stylesheet loads `async` (deliberately, so it doesn't block `main.js`), so the canvas's flex-centered position can shift *after* a JS measurement was already taken, with no `resize` event to correct it. The current pure-CSS version has no measurement to go stale by construction. `resizeCanvas()` still reserves `MIN_DESKTOP_SETTINGS_GUTTER` (80px) of clearance on every side unconditionally as a backstop.
  - **Mobile**: `#settingsMenu` shares the exact horizontal center and shrink-to-fit scale as `#actionButtons` (both computed in `touchControls.js`'s `layoutTouchControls()`), sitting a fixed `SETTINGS_TOP_MARGIN` (20px) from the viewport top rather than vertically centered — its own thing above the action column, not a 4th member of it. `layoutTouchControls()` pushes the action-button cluster down (never up) from its default vertical-centered position whenever true centering would put it within `ICON_GROUP_GAP` (24px) of the hamburger, fixing a real overlap that appeared once the action-button cluster grew.
- **Opening the menu pauses gameplay.** `settingsMenu.js` dispatches a `settingsmenutoggle` event (`{open: bool}`); `GameScreen` stashes `this.running` into `this.wasRunningBeforeMenu` on open and restores it on close (not unconditionally resuming), so opening the menu mid-cutscene or after game-over can't accidentally start gameplay. Also calls `this.dog.pauseBarking()`/`stopDogBarkSound()` on open and `resumeBarking()` (only if play is actually resuming) on close.
- **Dog bark persisting past pause/game-over — two separate bugs.** First: `Dog.js`'s bark `setTimeout` chain was never tied to `this.running` at all — fixed with `pauseBarking()`/`resumeBarking()` (fresh random delay on resume) plus `GameScreen.stopDogBarkSound()`. **Second, the real root cause of it persisting even after that fix**: `resetGameObjects()` is called *twice* per fresh game (constructor, then again from `startGame()` once cutscenes finish) and unconditionally did `this.dog = new Dog(...)` with no cleanup of whatever `this.dog` already was — the *first* Dog instance's already-started bark timer got silently orphaned the moment the second call replaced `this.dog`, invisible to `this.running`/the settings pause/game-over, since nothing pointed at it anymore. **Same class of bug `ScreenManager.setScreen()`'s automatic `cleanup()` exists to prevent, one level down**: `resetGameObjects()` replaces `this.dog` the same way `setScreen()` replaces `currentScreen`, so it needed the same "clean up what you're about to replace" guard. Fixed with `if (this.dog) this.dog.cleanup();` at the top of `resetGameObjects()`. **General lesson: any function that unconditionally reassigns a field holding an object with its own timers/listeners needs a cleanup guard before the reassignment, not just at the eventual teardown site** — caught only by instrumenting and watching two independent bark-timer chains running concurrently, not visible from a normal playtest since both the reachable and orphaned dog render/bark identically.
- **Credits** (`#creditsBtn`/`#creditsModal`): styled unlike the plain dark `#settingsPanel` — reuses the cream-gradient-card-plus-purple-border-plus-cat-ears visual language from `Cutscene.js`/`CharacterSelectScreen` since this is a genuine cute moment, not utility chrome. Text: "Created by, Imagineered by & Produced by / **Kathryn Hodges**" then a smaller "Engineered by Daddy (Scott Prelewicz)" line. Swaps for the settings panel rather than stacking on top — clicking Credits hides `#settingsPanel` and shows `#creditsModal` directly (game stays paused until credits itself closes); closing calls the shared `setOpen(false)` helper that actually resumes gameplay.

  **The card's ear shape (`.credits-ear` in `styles.css`) took several attempts to actually look like an ear.** `border-radius` (even the aggressive `horizontal / vertical` slash syntax, pushing the vertical radius well past the horizontal on the top corners) can only ever curve — it cannot taper to an actual point, confirmed live across two rejected attempts that both still read as "square"/rounded-rectangle rather than pointy. Fixed with `clip-path: polygon(...)`, mostly-straight sides with the curve concentrated in a short stretch right at the tip only, for the classic "triangle with a slightly rounded point" cat-ear silhouette. A plain `border` doesn't work with a non-rectangular `clip-path` — it clips the whole rectangular border to the new outline rather than redrawing along it, so most of it just disappears. Fixed with three stacked layers instead (the same "layer flat shapes to fake a stroke" technique `drawCatEarInner` already uses on the canvas side): the base `.credits-ear` (purple fill, full size) is the outline color, `::before` (inset 3px, the card's own cream gradient literally duplicated — `background: inherit` only reaches one level up, not past the purple parent) is the visible body, and `::after` (inset further, pink) is the inner-ear highlight — all three sharing the same polygon so they stay concentric as the card scales.

## Character selection & playable modes (`CharacterSelectScreen.js`, `GameScreen.js`)
Before gameplay starts, `CharacterSelectScreen` asks the player to choose Cat, Mouse, or Dog — all three enabled. The choice becomes `GameScreen`'s `controlledEntity` (default `'cat'`). **"Play Again" returns to character select rather than replaying with the same `controlledEntity`** — `restartGame()` hands off to a fresh `CharacterSelectScreen` instead of directly constructing another `GameScreen`. **Intro cutscenes are skipped on that replay path, but not moved** — re-watching them every round was flagged as unwanted, but relocating them to before character select (so they'd show once per session) was explicitly deferred. Threaded through as `isReplay` (on `CharacterSelectScreen`) → `skipCutscenes` (on the `GameScreen` it constructs) — a deliberately different name at that boundary since it specifically controls cutscenes, not "is this a replay" broadly. Exactly one entity reads player input at a time; the cat (whenever not played) runs the same AI in both Mouse and Dog mode, and the mouse (whenever not played) runs the same passive autonomous wander in both Cat and Dog mode.

- **Cat mode** (default): `moveCat()` reads `InputHandler` and calls `tryMoveCat(direction)`; mouse and dog both wander autonomously.
- **Mouse mode**: `movePlayerMouse()` reads `InputHandler` directly (ignoring furniture, same as autonomous mode); the cat runs `updateCatAI()`; the dog still wanders autonomously.
- **Dog mode** (the 8-year-old-designed one): the dog's job is to run into the cat on purpose and pause it, buying the mouse time to escape. `movePlayerDog()` reads `InputHandler` and calls `tryMoveDog(direction)` (same per-tick furniture/wall rules as `tryMoveCat()`, stricter wall-clamp math — see `Dog.js` above); the cat runs `updateCatAI()` (has to actually be chasing for "pause it" to mean anything); the mouse wanders autonomously. The dog-pauses-cat collision check is unchanged from Cat/Mouse mode — playing as the dog doesn't change the *rule*, just who's steering into it on purpose. Punch/Toot both no-op their positional effect when `controlledEntity === 'dog'` (see Punch mechanic above).

**Player-controlled speed is unified across all three characters** — `tryMoveDog()` uses `layout.dogPlayerSpeed` (`BASE_DOG_PLAYER_SPEED = 10`), `movePlayerMouse()` uses `layout.mousePlayerSpeed` (`BASE_MOUSE_PLAYER_SPEED`, raised from 8 to 10 in the same pass), `tryMoveCat()` uses `Cat.speed` (`10 * scale`) — all three now the same per-tick value, deliberately, so piloting any character feels identical. Only the *player-controlled* speed is unified; each character's *autonomous* speed is untouched and tuned independently.

**Win/lose semantics don't change between modes — only which outcome is good news for the player does, and the dog is on "team mouse."** `checkCollision(cat, mouse)` → cat catches mouse; `checkMouseEscaped()` → mouse reaches an `Escape`. `endGame(message, soundKey, isWin)` computes `isWin` at both trigger sites from `controlledEntity`: cat catches mouse → win iff playing Cat (loss for Mouse *and* Dog); mouse escapes → win iff *not* playing Cat (both Mouse and Dog succeed together, even though the dog never touches the mouse directly).

### Game-over modal (`displayGameOverModal`, `endGame`)
A dimming scrim over the whole canvas, then a rounded gradient card that pops/scales in over `MODAL_POP_IN_DURATION` (250ms). `this.gameOverIsWin` picks both the headline ("You Win!"/"You Lose!") and the card's color scheme (gold gradient for a win, bright teal/blue for a loss — deliberately playful either way, not somber, since this is a kids' game). The transient (non-game-over) pause message during active play is drawn separately via `displayMessage()`, since gameplay is still visibly running underneath there and a full modal takeover would feel wrong mid-round.

- **Win/loss sound** (`playWinSound()`/`playLoseSound()`): synthesized (oscillators + note envelopes), played *in addition to* the existing event sound (meow/squeak), since that event sound alone sounded identical on a win and a loss (same event, opposite meaning depending on `controlledEntity`). Win: ascending major arpeggio into a held note with a soft shimmer. Loss: three descending pitch-bent sawtooth notes through a lowpass filter — a cartoon "womp womp womp," deliberately not somber.
- **Reward breakdown** (`drawRewardsBreakdown`, `this.roundRewardBreakdown`): once `this.wallet` has loaded, the modal grows to show a "here's everything you earned" section — coins, plus a level-up or XP line if applicable — see Currency & economy system below for the full design (why it's diffed from a snapshot rather than returned by the backend, the "own bordered box per item" layout, and the top-spacing fix needed once the card started growing taller for this).

### Dog-pauses-cat stun moment (`handleDogCollision`, `displayMessage`, `drawStunBurst`/`drawStunStars`)
Replaced a plain `fillText` message plus a static red silhouette outline with a bolder message treatment plus an animated "impact, then daze" effect. `DOG_PAUSE_DURATION` was retuned twice on request: 2000ms → 8000ms (4x, giving the mouse a real window to use the pause), then → 4000ms (halved — net 2x original). `drawStunStars()`'s orbit and `displayMessage()`'s banner just run for however long `this.catPaused` stays true, so neither retune needed any other change; the burst (`DOG_COLLISION_BURST_DURATION`, still 400ms) is deliberately unaffected — it's meant to read as a quick hit, not stretch with the pause.

- **Message pop-in**: pops/scales in via the same ease-out-cubic pattern as the game-over modal. **First version (a bold purple `fillText`, no backdrop) was flagged live as amateurish/hard to read** — floating text at the mercy of whatever the board happens to be drawing behind it. Fixed with a pill-shaped banner (`drawRoundedRect`, sized to the actual text plus proportional padding, not a fixed width) filled with a purple gradient and a soft drop shadow, white text with a *lighter* stroke than the original attempt (once the banner carries the contrast, a heavy black outline on an already-bold face reads muddy). `BASE_MESSAGE_FONT_SIZE` bumped 24 → 36.
- **Stun visuals**: replaces the old static red silhouette with two effects picked as one cohesive language rather than stacking every effect discussed — a one-shot spiky amber/orange "POW" starburst (`drawStunBurst()`, 400ms, adapting `drawShockwave()`'s expanding-ring/fade technique as a filled 8-point star, colored differently from the punch shockwave's purple so the two moments don't read as the same effect recolored) drawn *behind* the cat, plus a "seeing stars" cue (`drawStunStars()`) — small yellow 5-point stars circling the cat's head for the entire pause, angle driven directly off elapsed time (no stored per-star state, so it needs no explicit stop beyond `this.catPaused` going false) — drawn *after* the cat.
- **"Gotcha!" sound** (`SOUND_KEYS.GOTCHA`, `sounds/gotcha.mp3`): a dedicated cue layered on top of the existing `SOUND_KEYS.DOG_BARK`, not a replacement — same "layer a dedicated cue on top of the existing event sound" pattern as `playWinSound()`/`playLoseSound()`. A supplied recording, not synthesized.

### Cat AI (`updateCatAI`, `catHasLineOfSightToMouse`, `moveCatTowardMouse`, `wanderCat`)
Runs whenever the cat isn't player-controlled. Each tick: if the cat has line of sight to the mouse, it moves one cardinal step directly toward it (`moveCatTowardMouse`); otherwise (or if that move is blocked) it wanders (`wanderCat`). No memory of the mouse's last-known position — once sight is lost it's pure wander until facing direction happens to line up again, by design.

- **`catHasLineOfSightToMouse()`**: true only if the mouse is strictly in the cat's facing direction (cardinal, not a cone) *and* no wall-mounted furniture crosses the straight line between their centers (freestanding table/plant never block sight). Uses `cat.size`, not `cat.displayWidth`/`displayHeight` — **this is now the one place `cat.size` still governs anything perceptible to the player** (the wall clamp and win-check both switched to `displayWidth`/`displayHeight`, see "Hitbox tightening" below); the wider lane here was left alone on purpose, since a bigger perception box only means the AI notices sooner, not that it catches from further away.
- **`moveCatTowardMouse()`**: picks whichever axis has the larger gap and moves one step that way; if blocked (e.g. a table in the path), `updateCatAI()` falls back to `wanderCat()` that tick instead of stalling.
- **`wanderCat()`**: moves every tick in a chosen direction, re-picking every `CAT_WANDER_DIRECTION_INTERVAL` (1200ms) or immediately on a blocked move. Speed is `this.cat.speed * CAT_WANDER_SPEED_MULTIPLIER` (currently `0.5`). **History worth knowing**: several rounds of tuning this multiplier had zero actual effect until `Cat.move()`'s speed-override bug (see `Cat.js` above) was fixed — the "too fast" feeling during that tuning came entirely from wandering having just switched from a 2-second hop to continuous per-tick movement, unrelated to the multiplier at all.

### Mouse disappearing on escape (`GameScreen.mouseEscaped`)
`checkMouseEscaped()` sets `this.mouseEscaped = true`, which `render()`/`drawMouseSilhouette()` check to stop drawing the mouse entirely, rather than leaving it visibly sitting at the hole through the frozen game-over screen.

### Cat silhouette under passable furniture (`GameScreen.drawCatUnderFurnitureEffect`/`drawCatSilhouette`)
Cat counterpart to the mouse's "ducks under furniture" treatment, for the small set of non-blocking types only (`plant`/`cart`/`shelf`/`table`) — unlike the mouse (which draws once, before all furniture), the cat's own `draw()` call stays in its normal spot in `drawGameObjects()`, and `drawCatUnderFurnitureEffect()` re-draws just the specific overlapping piece(s) on top of the cat's already-drawn sprite, then calls `drawCatSilhouette()`. `drawCatSilhouette()` is deliberately **not** a copy of the mouse's plain ellipse (per explicit direction to make the two distinguishable) — a rounded head with two pointed ears drawn first, then the head ellipse on top so the ear bases blend in. Same faint translucent-black (`globalAlpha = 0.35`) treatment as the mouse's.

### Spawn safety (`resolveClearSpawn`, `isHiddenByFurniture`)
The cat's, mouse's, and dog's fixed spawns aren't checked against wall-mounted furniture the way the freestanding dining set is — on some layouts a cabinet/fridge can land right on top of one. `resolveClearSpawn(preferredX, preferredY, size)` returns the preferred spot unless `isHiddenByFurniture()` says it's covered, in which case it random-searches `this.playableArea` for a clear spot. **The cat's spawn was originally left out of this protection** on the assumption its bottom-center spawn, away from wall furniture runs, was inherently safe — broke once `getCharacterScale()` made desktop characters ~2x bigger (a board-margin-independent change), so the cat's now-larger box could spawn already overlapping furniture with `tryMoveCat()` rejecting every move out of it from frame one. **General lesson: any size-scale change to a character needs a re-check of spawn-clearance assumptions that were "safe" only because of the character's old, smaller size** — fixed by routing the cat's spawn through `resolveClearSpawn()` too.

### Character size scale (`js/utils/scale.js`, `getCharacterScale`)
`getCharacterScale()` is a fourth scale function: a no-op on touch, `DESKTOP_CHARACTER_SIZE_MULTIPLIER = 1.95` on desktop (built up in two live-tuning passes). Deliberately **not** folded into `getScale()` itself, because `getScale()` also drives movement *speed* — bumping that blanket value would have silently sped characters up along with resizing them. `Cat`/`Dog`/`Mouse` each take a separate `sizeScale` constructor parameter (defaults to `scale` if omitted) used only for size/display fields, while `scale` alone drives speed. `GameScreen.computeLayout()` exposes this as `characterScale`, also used for the spawn-clearance approximations so they stay accurate to the characters' real size.

### Hitbox tightening — catching, walls, furniture, mouse-hole entry (`GameScreen.js`, `Dog.js`, `Escape.js`)
Four related fixes from one round of live feedback ("you can catch other characters from pretty far away… check chars can go all the way to furniture and walls… the mouse can escape by just being near a mouse hole, can it be that the mouse has to actually enter it?"). All four were confirmed by direct pixel-gap measurement, not just reasoning about the scale math.

1. **Catching from too far away** — `checkCollision()`/`Dog.isColliding()` used `cat.size` (the oversized logical box, see `Cat.js` above) instead of the cat's real sprite. Fixed by switching both to `cat.displayWidth`/`displayHeight`; `mouse.size` was already correctly sized so it was untouched. `catHasLineOfSightToMouse()`'s own use of `cat.size` was deliberately *not* touched — a wider perception lane isn't the same bug.
2. **The cat's wall clamp could clip into the wall** — the old "position can dip below `WALL_OFFSET` by up to `cat.size`" formula assumed `cat.size` exceeded the true footprint enough to never push the visible sprite past the edge. Fixed by switching to the same strict-containment shape `Dog.js`'s wall clamp already used successfully.
3. **The dog clipped into furniture horizontally and stopped short vertically** — its furniture-collision check used a square `this.size` against a non-square sprite (`frameWidth`/`frameHeight`). Fixed by bypassing `Furniture.isColliding()` (same reason `Cat.js`'s own check bypasses it) and calling `aabbOverlap()` directly with `frameWidth`/`frameHeight` in both `Dog.tryMove()` and `GameScreen.tryMoveDog()`.
4. **Mouse escape triggered on mere proximity** — `Escape.isMouseInside()` is a loose "any overlap" AABB test, still needed elsewhere exactly as-is (it exempts the cat/dog's wall clamp near the escape gap). A second, stricter `Escape.hasMouseEntered()` was added for the actual escape trigger, and went through several rounds of live-reported over/under-tuning before landing on its current behavior:
   - Requiring the mouse's *center* inside the hole was geometrically impossible (the hole is shallower than the mouse's own half-width) — reversed to requiring the mouse's box to fully *cover* the hole instead, which is achievable since the mouse is always bigger than the hole.
   - That alone still ran the check every tick regardless of what the mouse was doing, so merely loitering in the (small but real) catch zone escaped — fixed by tying the check to the mouse's actual wall-hit event (`wallHitCallback`) instead of a continuous per-tick check.
   - Then reported too hard ("taking a step either way... goes too far") — fixed with a separate `BASE_ESCAPE_HITBOX_MARGIN` (20, → `layout.escapeHitboxMargin`) that widens the *mouse's* effective box for the containment check only (widening the hole itself would have made containment *harder*, the opposite of intuition, since `window = mouse.size - escape.width`), plus re-checking on every tick spent sliding along a wall already in contact (not just the tick that first caused contact).
   - That sliding fix then let a fast pass-through past a hole (never stopping) also trigger escape — fixed by moving the check off the "moving" path entirely onto the "not moving" path: `movePlayerMouse()` only calls the escape check when the player *isn't* pressing a movement key that tick, requiring an actual stop.
   - Rapid direction-tapping (release gaps between taps) satisfied that "not moving" condition without a deliberate stop — fixed with a `MOUSE_STOP_DEBOUNCE_MS` (150ms) requiring real elapsed idle time, plus an explicit exception: pressing the direction that faces *into* whichever wall the mouse currently rests against also triggers the check immediately (a deliberate "turn to enter" gesture, which a parallel "running by" slide can never satisfy on its own).
   - The autonomous mouse (Cat/Dog mode) needed its own separate `escapeCheckCallback` wiring (fired from `Mouse.js`'s bounce blocks) once the escape check was removed from the player path's "moving" branch — autonomous mode bounces immediately off a wall rather than sliding, so it never had the "running by" exploit and was untouched otherwise.

## Currency & economy system (`kpground-api`, `js/utils/api.js`, `GameScreen.js` HUD/doobers/rewards, `js/utils/storeModal.js`)
KatTrap's coin/level/XP economy is backed by a separate Django REST API (`kpground-api`, sibling repo, OAuth2 bearer-token auth) with one `CharacterWallet` row per `(user, character)` — Cat/Mouse/Dog each earn and spend independently, gated entirely on `isLoggedIn()`. `js/utils/api.js` wraps the endpoints (`getWallets()`, `submitRound()`, `purchaseItem()`, etc.). `GameScreen` fetches the controlled character's wallet once, fire-and-forget, in `init()` — `this.wallet` stays `null` (HUD/store button/reward breakdown all skip drawing entirely) if never logged in or the fetch fails — and refreshes it from `submitRound()`'s own response at round end rather than re-fetching.

### HUD (`GameScreen.drawHud`, `HUD_STATS`, `getHudLayout`)
A wide, horizontally-centered bar at the top of the board (not a top-left corner box) — one emoji+value "chip" per wallet stat (`HUD_STATS`: 🪙 Coins, ⭐ Level, ✨ XP) in a single row over a full-width XP progress bar, with a "Store" button centered just below. `getHudLayout()` computes the shared box/row geometry once and backs three separate consumers (`drawHud()` itself, `getHudCoinTargetPosition()` — the doober popup's flight target, below — and the hover hit-test), so all three agree on where the HUD actually sits without recomputing, and risking drift between, the same math three times over.

- **Coins uses a real icon, not an emoji** — `drawHudCoinStatText()` draws a small crop of `assets/doober_coin.png` (the same art the doober itself uses) followed by the value, as one unit centered together (an icon plus text can't be a single `fillText()` call). Shared with the game-over modal's reward-breakdown row (below) via a `fontSize` param, so the icon scales to whatever text it's sitting next to rather than always assuming the HUD's own size.
- **Hover tooltips**: each chip records its own hit box in `this.hudStatAreas` (rebuilt every `drawHud()` call); a `mousemove` listener (`handleMouseMove()`) tracks `this.hoveredHudStatIndex`, and `drawHudTooltip()` draws a label + word-wrapped description popover under whichever chip is hovered. The description genuinely word-wraps (`wrapText()`, a generic greedy-wrap helper) against a max width clamped to a fraction of the live canvas width — more lines at the same legible font size on a narrow canvas, not a fixed-width box that either overflows or has to shrink its text to fit.

### In-gameplay "doobers" (`GameScreen.js` — `spawnDoober`/`updateDoobers`/`drawDoober`, `DOOBER_TYPES`)
Collectible coin drops that spawn on the board during a round, separate from the round-completion reward — this game's own term, borrowed from FrontierVille. `MAX_ACTIVE_DOOBERS = 1` on the board at once, visible for up to `DOOBER_CATCH_DURATION` (10s) before vanishing, with a real `DOOBER_SPAWN_INTERVAL` (7s) minimum gap before the next one can appear. Collected only by whichever character the player controls (autonomous entities never pick these up), tallied in `this.coinsCollectedThisRound`, sent once in `submitRound()` at round end rather than as its own network call per doober. Generalized via a `DOOBER_TYPES` registry (only `'coin'` exists today, each entry supplying its own `draw()`/`onCollect()`) so a future non-coin type is one registry entry, no changes to the shared spawn/expiry/collision machinery. A glowing arrow (`drawDooberArrow()`) points at every landed doober, shown only the first time a player sees each type per page session (`dooberArrowShownForType`, module-level, survives "Play Again," resets only on reload).

- **A real timing bug, not just "the interval was too short"**: `updateDoobers()` used to reset `lastDooberSpawnTime` on every tick the interval check passed, *regardless of whether a doober actually spawned* (`spawnDoober()` silently no-op'd once already at capacity) — decoupling the cooldown from the doober's real lifecycle and letting doobers reappear faster than the configured interval. Fixed by only resetting the timer at a genuine disappearance moment (expiry or collection), with the `MAX_ACTIVE_DOOBERS` capacity check moved into the caller.
- **"+N" flies from the doober to the HUD** (`spawnDooberCollectPopup`/`updateDooberPopups`/`drawDooberPopup`): an ease-in flight over `DOOBER_POPUP_DURATION` (700ms) from the collected doober's board position to `getHudCoinTargetPosition()`. **The HUD's coin count itself increments only when the popup lands, not the instant the doober is grabbed** — a deliberate optimistic local wallet update timed to the animation finishing, not the trigger. `BASE_DOOBER_POPUP_FONT_SIZE` (38, up from an original 22) plus a gold `shadowBlur` glow and a thick dark outline, after the original size/stroke read as a small, easy-to-miss flick against a busy kitchen board.
- **Landing triggers a "crash"**: the instant a popup's flight finishes, `spawnHudCoinImpact()` fires an expanding/fading gold ring plus radiating spark lines right at the HUD (`drawHudCoinImpact()` — `drawShockwave()`'s expanding-ring technique, recolored) and `playCoinLandSound()` (`audio.js`, synthesized — a 3-note bright glissando, a high-passed metallic "clink" burst, and a soft shimmer tail) plays. Deliberately a *different* sound from `playDooberSound()`'s 2-note pickup ding — pickup and landing are two different moments roughly 700ms apart, not the same event fired twice.

### Game-over modal reward breakdown (`GameScreen.endGame`, `displayGameOverModal`, `drawRewardsBreakdown`, `drawRewardChipBox`)
Once `this.wallet` has loaded, the win/lose modal (see Game-over modal above) grows to show a "here's everything you earned" section: coins, plus a level-up or XP line if applicable. **Each item gets its own individually-bordered box with a visible gap between them** — "ice cubes in a tray," not shared/floating text inside one box, which is what an earlier version drew and was explicitly rejected live. `drawRewardChipBox()` draws one bordered/filled compartment, sized to its own content, for each item.

- **The backend never returns a reward breakdown, only the updated wallet** — `kattrap/services.py`'s `submit_round()` in `kpground-api` computes coins/XP server-side and returns just the resulting `CharacterWallet`. Rather than a backend change, `endGame()` diffs a `this.walletAtRoundStart` snapshot (captured once, the moment `getWallets()` first resolves in `init()`) against the wallet `submitRound()` returns. `this.coinsCollectedThisRound` is already exact, so `baseCoinsGained = totalCoinsGained - dooberCoins` isolates the flat win/loss reward without ever duplicating the backend's own reward constants client-side. XP is only shown as a plain number when no level-up happened that round — `CharacterWallet.add_xp()`'s carry/reset behavior at the level boundary isn't duplicated client-side, so a raw `xp` diff would be wrong across one.
- **Reserves the section's height synchronously, before the async response arrives**: `this.roundRewardBreakdown = { status: 'pending' }` is set in `endGame()` immediately, not after `submitRound()` resolves, so the taller card doesn't resize/jump once the real numbers fill in a moment later.
- **Modal top-spacing bug, worth remembering for any future "make this modal taller" change**: title/subtitle were originally positioned as `centerY ± baseModalHeight*fraction` — correct for the modal's original fixed height, but once the card grows to fit this section, its top edge (`modalY = centerY - modalHeight/2`) moves further up while a centerY-relative title position doesn't move with it, opening a growing gap of dead space above the headline. Fixed by re-deriving the same fractions relative to `modalY` (the card's actual top edge) instead of `centerY` — mathematically identical position when the card isn't grown (so a logged-out player's modal is untouched), but the title now tracks the top edge at any height.
- **Overflow bug from fixed-fraction text positions**: an early version positioned the coins block and the level-up/XP block at fixed `centerX ± fraction` offsets, which overflowed (or ran into each other) once a string was long enough — e.g. the coins text with a doobers breakdown folded in. Fixed by measuring each block's actual rendered width (`measureHudCoinStatBlock()`, shared with `drawHudCoinStatText()` so the icon/gap sizing ratios can't drift between the two) and centering the *group*, never guessing a fixed split. **General lesson for any future side-by-side canvas text**: measure, don't guess a fraction — the same root mistake (a fixed layout position with no regard for actual content width) independently broke this modal and, in the same round, the credits modal's ear shape used the analogous wrong tool (`border-radius` instead of `clip-path`, see Credits above) — worth checking both together if either resurfaces.

### Store modal (`js/utils/storeModal.js`, `#storeModal`)
A real DOM modal (not canvas-drawn) opened from the HUD's Store button — per-item buy buttons and dynamic owned/locked/affordable states are much simpler as DOM than hand-rolled canvas hit-testing per row. Same cream-card-plus-purple-accent visual language as the credits/login modals (see Settings menu & audio above).

## Mobile responsiveness (`js/utils/scale.js`, `orientationGate.js`, `touchControls.js`)
Milestone-scope mobile support: the game requires landscape (a full-screen gate blocks portrait) rather than reworking layout for both orientations, but *within* landscape it scales correctly at any canvas size — every size in the game (furniture scale, wall thickness, character size/speed, floor tile size, UI chrome) used to be a fixed pixel value tuned against a desktop-sized canvas, which broke badly on a narrow mobile canvas (a single stove alone ate ~40% of board height on a 350px-wide canvas).

- **Four separate scale functions**, all derived from `base = canvasWidth / REFERENCE_WIDTH` (1280), each applying its own multiplier once `isTouch()` (`window.matchMedia('(pointer: coarse)').matches`, exported and reused everywhere a mobile-vs-desktop decision is needed) reports a touch device:
  - `getScale()` — character speed, wall/floor chrome, spawn clearance. `MOBILE_ASSET_MULTIPLIER = 1.5` on touch, no-op on desktop.
  - `getUIScale()` — buttons/messages/cutscene modal. `MOBILE_UI_MULTIPLIER = 2` on touch, no-op on desktop.
  - `getFurnitureScale()` — furniture only. `DESKTOP_FURNITURE_MULTIPLIER = 2` on desktop; `MOBILE_FURNITURE_MULTIPLIER = DESKTOP_FURNITURE_MULTIPLIER / MOBILE_ASSET_MULTIPLIER` (≈1.333) on touch, derived (not eyeballed) so furniture occupies the identical fraction of canvas width on both device classes — added after a design-director pass found the touch branch was a plain no-op, a real cross-device inconsistency (furniture occupied 33% more of the board's width on desktop than touch).
  - `getCharacterScale()` — character on-screen/collision size only, not speed (kept separate so a display-size change can never affect movement speed — see Character selection & playable modes above). `DESKTOP_CHARACTER_SIZE_MULTIPLIER = 1.95` on desktop; `MOBILE_CHARACTER_SIZE_MULTIPLIER = 1.9771375` on touch, bumped four times on explicit "N% bigger" requests stacked on the *current* value each time (not re-derived from the original baseline) — **if another "N% more" request lands, apply it to whatever the constant currently is, not back to any earlier step.** The original desktop-parity derivation no longer holds exactly after these bumps, and that's intentional. **Not yet checked live for wall/furniture clearance fallout at this size** — worth a live mobile pass if clipping is ever reported, given `Dog.js`'s own size-bump history showed a bigger character can start clipping once containment math (keyed off the same size fields) has less real margin than before.

  Treat these constants as tuned-by-eye values arrived at via try/review-on-device/adjust, not settled physics, except where one is still explicitly *derived* from another (furniture's mobile multiplier) — expect another round of retuning if the art or device mix changes again.
- `GameScreen` computes `this.layout = computeLayout(canvas.width)` once in its constructor (canvas size is fixed for a `GameScreen`'s lifetime — live mid-game resize is a known open gap, see Known rough edges) and every `BASE_*` constant is multiplied by whichever of `scale`/`uiScale`/`furnitureScale`/`characterScale` fits its category — methods read `this.layout.X`, never a bare module constant. `Cat`/`Dog`/`Mouse` each take both `scale` (speed) and `sizeScale` (size/display), but neither touches `frameWidth`/`frameHeight` used for sprite-sheet *source*-rect slicing, which must stay at native pixel dimensions regardless of display scale.
- **`Cat`/`Dog`/`Mouse` expose `displayWidth`/`displayHeight` getters** giving each character's actual on-screen size regardless of internal representation — `Cutscene.js` and `GameScreen`'s `handlePunch()`/`drawRedOutline()` read these rather than re-deriving the size themselves.
- **The landscape gate** (`orientationGate.js`) is a full-screen overlay shown whenever `window.innerHeight > window.innerWidth` — a real aspect-ratio check, not a device/breakpoint media query, so a narrow desktop window triggers it too. The game loop keeps running underneath (not paused); the overlay's z-index just makes the board unreachable.
- **Canvas width reserves more side margin on touch devices** (`resizeCanvas()`): `maxCanvasWidth = window.innerWidth * widthFraction`, `0.8` on touch vs `0.9` on desktop — only matters when the canvas is width- rather than height-constrained (squarish windows, and a standard iPad's ~4:3 landscape aspect). Added after the default 10% margin left as little as ~50px of gutter on an iPad, not enough for a usable d-pad.
  - **A design-director pass found even this wasn't a hard guarantee** — the d-pad's shrink-to-fit could still collapse it to ~70-125px on some real devices. **First fix attempt caused a real regression**: capping `maxCanvasWidth` unconditionally (before checking whether the device would even be width-constrained) shaved width off ordinary height-constrained phones too, reintroducing a previously-fixed "gap above the board" bug (since canvas height derives from width to hold the 4:3 ratio). **Fixed by computing the natural fraction-only fit first, and only reaching for the extra cap if that natural gutter falls short of `MIN_TOUCH_CONTROL_GUTTER`** — a targeted fix instead of a blanket one. **General lesson: a fix for a width-constrained-only problem must check that the current device is actually in that regime before applying, or it silently regresses the (larger) height-constrained-device population.**
- **Touch controls** (`touchControls.js`): an on-screen D-pad and punch/toot/meow action buttons (map to the same `p`/space/`m` keys as desktop). Positioned by `layoutTouchControls()`, called on load/resize/orientationchange.
  - `#dpad` displays an actual reference photo (`assets/dpad_cross.png`) as its background rather than a CSS-drawn shape — a hand-tuned CSS approximation was tried first and read as amateurish next to a real photo. The four `<button>` hit zones are invisible, absolutely-positioned at percentages measured off the source photo's own pixels.
  - **Horizontal position is edge-anchored, not pure gutter-centering** — `edgeAnchoredOffset()` prefers a fixed thumb-reach distance from the nearest viewport edge (`EDGE_ANCHOR_MARGIN = 20` plus half the control's current size), falling back to splitting the gutter evenly only when the gutter's too tight for that to fit without creeping toward the canvas. Replaced a pure gutter-centering approach that read as floating in empty space once the gutter was much wider than the control needed.
  - **Shrink-to-fit sizing**: natural sizes (`DPAD_NATURAL_SIZE = 210`, `ACTION_BTN_NATURAL_SIZE = 76`) scale down via a `--dpad-scale`/`--action-scale` CSS custom property (`transform: scale(...)`) whenever the gutter is narrower than natural size. **The d-pad has a hard floor the action buttons deliberately don't**: `MIN_DPAD_SCALE = 0.62` (130px) — a d-pad divides one disc into 4 direction zones, so shrinking it too far makes hitting the *specific direction* meant unreliable, unlike simple one-shot action-button taps. `MIN_TOUCH_CONTROL_GUTTER` (used by `resizeCanvas()` above) is computed from this same floor, so the floor and the board-width reservation guaranteeing it can never drift out of sync.
  - Each button dispatches a real `KeyboardEvent` on `window` — `InputHandler.js` is completely unaware touch controls exist.
- **`index.html`'s `body` uses `justify-center`, not `justify-start`.** On squarish viewport aspect ratios the canvas becomes width- rather than height-constrained and shorter than the viewport; `justify-start` dumped all leftover vertical space below the canvas instead of splitting it, which also broke the touch controls' `top: 50%` vertical centering (which depends on this).
- **Not covered by this pass**: actual portrait layout (deliberately out of scope), and live-resize (furniture/spawn positions are computed once at generation time from `canvas.width`/`canvas.height` and never re-laid-out if the canvas resizes mid-game).

## iOS "Add to Home Screen" hint (`js/utils/homeScreenHint.js`)
A slim dismissible banner pinned to the top of the viewport, shown for an iPhone/iPod on any iOS browser not already launched from a home-screen icon. No iOS browser has a `beforeinstallprompt`-style API (WebKit doesn't implement it, and every browser on iOS is required to render on WebKit) — this manual banner pointing at Share > Add to Home Screen is the only available workaround. The payoff is real: WebKit only implements the Fullscreen API on iPadOS, never iPhone, so a home-screen launch is the only way to reclaim toolbar space on an iPhone.

- **Detection covers Chrome/Firefox/Edge/Opera on iOS too, not just Safari** — an earlier version excluded them by user agent on the assumption only Safari's home-screen launch went standalone, which was confirmed live to be wrong (Chrome-iOS does get a genuine standalone-ish launch from its own home-screen icon). Detection: `/iPhone|iPod/` on `navigator.userAgent` (deliberately **not** a broader "any iOS device" regex — iPadOS 13+ reports a Mac-style user agent and already gets the real Fullscreen API, so it doesn't need this hint), and `isStandalone()` checking **two** signals — `window.navigator.standalone === true` (Apple's own property) **or** `window.matchMedia('(display-mode: standalone)').matches` (the standard cross-browser signal) — since `navigator.standalone` isn't guaranteed set by every other iOS browser's own standalone launch even when genuinely standalone.
- Shown pre-game, hidden automatically once gameplay starts (`body.in-game #homeScreenHint { display: none }`).
- **Dismissal counts rather than a single permanent flag** — `kattrap_homeScreenHintDismissCount` (`localStorage`) increments per dismiss, reappearing on later visits until `MAX_DISMISSALS` (10) is reached; a single reflex dismissal isn't the same as "never show me this again." Reading/writing the count is wrapped in `try`/`catch` so restricted storage (some private-browsing configs) degrades to "the hint reappears next load" rather than throwing and blocking `main.js`'s `init()`.

## Viewport frame & mouse-escape danger indicator (`styles.css`, `GameScreen.updateEscapeDangerIndicator`)
A retro handheld-console bezel drawn as a fixed, non-interactive overlay around the whole viewport (`body::after` for the frame, `body::before` for a small "power LED" dot top-left) — not a real layout border, since `resizeCanvas()` sizes the canvas off raw `window.innerWidth`/`innerHeight` and an actual border would silently eat into that budget. Both rules are gated behind `@media (pointer: coarse)` (two earlier attempts were corrected after live feedback: one framed the canvas instead of the viewport, one showed unconditionally on desktop too).

The LED is a live mouse-escape-danger meter. `GameScreen.updateEscapeDangerIndicator()` (called every frame from `updateMouse()`) measures the mouse's distance to the nearest `Escape`'s center and sets `document.body.dataset.mouseDanger` to `'low'`/`'medium'`/`'high'` against `BASE_ESCAPE_DANGER_DISTANCE`/`BASE_ESCAPE_WARNING_DISTANCE` (90/220, scaled via `getScale()`). `styles.css` recolors the LED green/amber/red accordingly with a short CSS transition. `GameScreen.cleanup()` deletes the `mouseDanger` dataset attribute so a fresh game doesn't inherit a stale color.

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this pattern rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB (axis-aligned bounding box) checks via the shared `aabbOverlap` helper — no physics library.

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage currently exists for any collision, movement, or game-state logic.
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, layout scaling, and procedural level generation in one ~1000-line class — a strong refactor candidate.
- `styles.css` now holds the orientation-gate/touch-controls/viewport-frame CSS — everything else is still Tailwind utility classes in `index.html`.
- **Four scale functions (`getScale`/`getUIScale`/`getFurnitureScale`/`getCharacterScale`), each with its own device-dependent multiplier, and two of them (`getFurnitureScale`, `getCharacterScale`) boost *desktop* rather than touch** — easy to reach for the wrong one when adding a new `BASE_*` constant; check whether the new size is a character-speed/wall/floor thing, a button/message thing, furniture, or character size before picking which scale multiplies it.
- **Touch-vs-desktop detection is done purely via `window.matchMedia('(pointer: coarse)')`** (`isTouch()`) — a Windows/ChromeOS convertible used with a mouse would read as desktop even with a touchscreen present, and vice versa. Accepted as good enough for this game's audience; revisit if that assumption stops holding.
- **White box on initial load (fixed) — root cause was a script/stylesheet ordering rule, not just the canvas's own CSS.** Two things compounded: (1) `<canvas class="bg-white">` showed a stark white box against the dark body background for anything left unpainted; (2) `<script type="module">` doesn't execute until every preceding stylesheet finishes loading, and Tailwind's CDN `<link>` was a 2.9MB uncompressed stylesheet — slow enough on mobile to stall the entire game boot. Fixed with `async` on the script tag (which doesn't wait for stylesheets, unlike plain `type="module"`) and dropping `bg-white` from the canvas. `async` also meant `main.js`'s top-level `document.getElementById('gameCanvas')` could theoretically run before `<body>` exists, so `main.js` now wraps init in a `document.readyState` check rather than assuming parse order.

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- Every screen (`SetupScreen`, `CharacterSelectScreen`, `GameScreen`) that adds `document`/`canvas` listeners or a `requestAnimationFrame` loop should expose a `cleanup()` — `ScreenManager.setScreen()` calls the outgoing screen's `cleanup()` automatically (if present) before swapping, so this is the one teardown path that actually gets invoked on every screen transition, not just the ones a screen happens to call manually before transitioning itself.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest), not assume one is already there.
- Reuse `isTouch()` (`js/utils/scale.js`, exported) for any new mobile-vs-desktop behavior rather than inventing another device-detection heuristic — it's already the single source of truth behind touch-control visibility, the viewport-frame bezel, `resizeCanvas()`'s width margin, and all four scale functions. Keeping them all on the same signal means they can never disagree with each other.
- Before shipping a mobile/responsive-layout change, check the actual `resizeCanvas()`/`computeLayout()` math by hand (or a quick throwaway script) across a real spread of device dimensions — not just a few manually-resized desktop-browser windows. That narrower kind of testing missed real bugs twice in this project's history (see Planned work's mobile-responsiveness entry) that a numeric sweep across common desktop/laptop/tablet/phone sizes caught immediately.
- If you add a new size for a character (`Cat`/`Dog`/`Mouse`), decide whether it's a *display/collision size* (use `sizeScale`/`getCharacterScale()`) or *movement speed* (use `scale`/`getScale()`) before wiring it in — conflating the two was a real bug (`Cat.move()` silently ignoring a passed-in speed override, see Character selection & playable modes above), and cost several rounds of tuning a constant that had no actual effect until it was caught.
