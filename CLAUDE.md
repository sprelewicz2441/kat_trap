# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). You control a cat chasing a mouse around an arena, while a dog wanders randomly and catches the cat if they collide. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step.

## Architecture

**Entry point:** `js/main.js`
- Grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, and starts on `SetupScreen`.
- Runs a single `requestAnimationFrame` game loop that calls `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — a simple state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render` to whichever screen is active. Screens are swapped via `setScreen()`, which calls the new screen's `init()`.
- `SetupScreen.js` — animated title/start screen. Draws a background image over an animated gradient, defines a clickable "Start Game" hit-box (`startButtonArea`) computed as a percentage of the background image's position, and transitions to `GameScreen` on click.
- `GameScreen.js` (**~950 lines — by far the largest file, and the one most likely to need review before extending**) — owns the actual gameplay: creating the cat/mouse/dog/escapes/furniture, the input-driven cat movement, dog-vs-cat and cat-vs-mouse collision checks, the punch/toot/meow input reactions and punch shockwave animation, procedural kitchen-furniture layout, sound playback, win/lose messaging, and a "play again" button. Also kicks off cutscenes at the start via `CutsceneManager`.

**Entities** (`js/classes/`) — each is a small, mostly self-contained class with `update()`/`draw(ctx)`:
- `Cat.js` — player-controlled; `move(direction)` is called from `GameScreen` based on `InputHandler` state. Handles its own sprite-sheet animation.
- `Dog.js` — moves randomly on a timer (`moveInterval`), respects an obstacle list (currently the `furniture` array, still named `boundaries`/`this.boundaries` internally, a naming leftover from before furniture existed) and `escapes` when deciding valid moves, barks on a random interval, and exposes `isColliding(entity)`.
- `Mouse.js` — moves with pseudo-random velocity, bounces off canvas walls, fires a `wallHitCallback` on bounce. Intentionally **not** blocked by furniture (mouse has no pathfinding, so a real collision would risk it getting stuck against furniture corners); instead `GameScreen.render()` draws the mouse *before* furniture so furniture visually paints over it wherever they overlap, giving the effect of the mouse ducking under furniture while passing through unobstructed.
- `Escape.js` — a mouse hole; collision (`isMouseInside()`) is still a plain AABB rectangle, but `draw()` renders a rotated arch shape, not a rectangle — see Wall band & mouse holes below.
- `Furniture.js` — kitchen/dining obstacle (counter modules, fridge, dining set). Takes `(x, y, type, spriteSrc, rotation = 0, spriteWidth = 32, spriteHeight = 64, scale = 1.5, cropX = 0, cropY = 0)`; every kitchen piece today passes explicit width/height/scale overrides rather than relying on those defaults, since none of the current sprites match them (the defaults are a leftover from an earlier asset generation). `spriteWidth`/`spriteHeight` are meant to describe the sprite's actual visible *content* size, not necessarily its file's full pixel dimensions — see `cropX`/`cropY` below. Rotation (0/90/180/270) swaps width/height and is applied via canvas transform in `draw()`, centered on the same pivot the collision box uses — now actually used, by the left/right wall cabinet runs (see Kitchen furniture below); rotation 180 remains unused anywhere. `cropX`/`cropY` (added when the current `kitchen_*.png` set turned out to have several pixels of transparent padding baked into every file) tell `draw()`'s `drawImage()` call where the real content starts within the source file, via a source-rect crop — this is what makes adjacent wall modules sit flush with no visible gap; both default to 0, which is a no-op for any sprite with no padding. Sets `ctx.imageSmoothingEnabled = false` before drawing — a leftover from when kitchen sprites were small pixel art that needed to stay crisp when scaled up; harmless no-op now that they're higher-res renders, but not worth removing. Draws a type-colored placeholder rect while the sprite loads. `isWallItem` is computed in the constructor but never read anywhere — dead property.
- `InputHandler.js` — tracks currently-held keys via `window` keydown/keyup listeners, exposes `getDirection()`; also dispatches custom `'toot'` (spacebar), `'punch'` (`p`), and `'meow'` (`m`) events for `GameScreen` to react to.

**Cutscenes** (`js/classes/cutscenes/`):
- `Cutscene.js` / `CutsceneManager.js` — sequenced intro scenes shown before gameplay starts, triggered from `GameScreen.startCutscenes()`.

**Utilities** (`js/utils/`):
- `collision.js` — exports `aabbOverlap(ax, ay, aWidth, aHeight, bx, by, bWidth, bHeight)`, the single shared axis-aligned bounding box overlap test. Used by `Escape.isMouseInside`, `Dog.isColliding`, `Furniture.isColliding`, and `GameScreen.checkCollision`. Takes raw coordinates rather than entity objects so each caller stays explicit about which field it's using per side (e.g. `Dog` uses its own `frameWidth`/`frameHeight` for itself but `entity.size` for whatever it's checking against) — don't refactor it to accept entities and guess the right field, since the same object (e.g. `Dog`) legitimately uses different box dimensions depending on which side of the check it's on.

## Floor background (`GameScreen.drawFloor`)
`render()` fills the whole canvas with a repeating two-tone tile pattern before drawing anything else. **This is canvas-drawn, not CSS** — `styles.css` only styles the orientation gate/touch controls chrome outside the canvas (see Mobile responsiveness below), nothing about the board itself; the floor is generated on an offscreen canvas at draw time (`drawFloor()`, cached on `this.floorPattern` via `ctx.createPattern(..., 'repeat')`) rather than loaded from an image, so there's no async load to wait on. Currently a small 24px flat white/off-white two-tone tile look (`COLORS.FLOOR_LIGHT` `#ffffff`/`FLOOR_DARK` `#f9f8f4`, a subtle near-white rather than a strongly-toned off-white/`FLOOR_GROUT`), sized like a fine modern kitchen floor tile relative to the furniture. Colors are deliberately **plain and neutral, not matched to the `kitchen_*.png` furniture's warm cream/tan/honey-oak palette** — two earlier versions of this floor (96px then 48px tiles, both in warm tones pulled from/complementary to the furniture, the first also with marble-vein texture) were each tried and rejected live for blending into the furniture instead of reading as floor beneath it; white/off-white reads as a distinct surface regardless of what furniture palette sits on top. This replaced (in order, largest tile to smallest) a 96px warm-toned veined tile → a 48px warm gray/taupe tile → a 40px warm cream/peach checker → an even earlier photographic floor crop cut from the same AI-generated kitchen photo the furniture used to be cropped from — see Kitchen furniture below for the furniture's parallel art-direction history.

## Wall band & mouse holes (`GameScreen.drawWalls`, `Escape.js`)
`render()` draws `drawWalls()` right after `drawFloor()` and before the escapes/mouse/furniture — a `WALL_BAND_THICKNESS` (16px) band flush against all four canvas edges, filled with `COLORS.WALL_FILL` and outlined with two `COLORS.WALL_TRIM` strokes (one at the canvas edge, one where the band meets the floor) so it reads as wall *thickness* rather than a flat painted stripe. This exists purely for presentation — it's unrelated to `WALL_OFFSET` (40px, used by `moveCat()` to clamp how close the cat can get to the edge) and to the old `WALL_THICKNESS`/`COLORS.WALL`/`drawWallBorders()` it replaced, which drew a single flat-color rect at `WALL_OFFSET` and was dead code (defined but never called from `render()`) before this change.

Furniture's *back* (the edge facing the wall) is aligned flush against the wall band's *front* face — `WALL_BAND_THICKNESS` in from the canvas edge, not the raw edge itself — on all four walls (see Kitchen furniture point 3 below); this was a deliberate fix after an earlier version of this feature placed furniture flush to the raw canvas edge, which meant furniture completely painted over the entire wall band (including its inner border line) wherever it existed, while non-furniture areas showed the full band — an inconsistent "sometimes there's a wall margin, sometimes there isn't" look. With back-alignment, the band's inner border is always visible as a consistent thin reveal around furniture everywhere, not just where furniture happens to be absent — corners, the gaps beside a centered wall run, the open stretch of left/right wall above/below the two-cabinet run, and — the reason this was added in the first place — the mouse-hole gap `generateKitchenFurniture()` already leaves in one wall's tile run (`this.wallGap`). Before any of this, `Escape` rendered as a flat black square floating on bare floor with nothing to be a hole *in*; now it has a wall band to sit inside, so it reads as an actual opening.

`Escape.draw()` was changed to match: instead of a filled rectangle, it draws a small rounded-arch cutout (flat bottom, domed top — the classic cartoon mouse-hole silhouette) filled with a black-to-dark-brown radial gradient and a faint highlight stroke, for a sense of depth rather than a flat color. The base shape assumes it's sitting in a horizontal wall with the opening facing down (correct for the top wall as-is); `Escape` now takes a `wall` param (`'top'`/`'bottom'`/`'left'`/`'right'`, defaulting to `'top'`) and rotates the whole shape around its own center (0°/180°/270°/90° respectively) so the opening always faces into the room regardless of which wall it's on. `GameScreen.generateEscapes()` passes this through for every escape it creates, both the guaranteed `wallGap` one (using `gap.wall`, already `'top'`/`'bottom'`) and the `count - 1` randomly-placed ones (mapped from the existing `0-3` wall index). Collision (`isMouseInside`) is untouched — still a plain AABB rect using `this.width`/`this.height`, since the visual rotation doesn't change the (square) bounding box.

## Kitchen furniture (`GameScreen.generateKitchenFurniture`)
Procedurally lays out `Furniture` instances each game reset from `assets/kitchen_*.png` (`cabinet`/`sink`/`stove`/`fridge`/`table`/`chair`). This is the **fourth complete art direction** for kitchen furniture — see "Art direction history" below before reaching for a flat sprite pack, a full AI-scene crop, or reusing the previous photorealistic-object round's dimensions; all three were tried and superseded for specific, non-obvious reasons, and the dimensions below are specific to *these* image files (read directly off disk — don't assume they match any earlier round's `MODULE_SPECS`/`FRIDGE_SPEC`/`TABLE_SPEC`/`CHAIR_SPEC` numbers).

**Art direction history (read this before touching kitchen art):**
1. **Crops from one whole AI-generated scene** (`kitchen_reference_scene.jpg`, still in git history) — individually-cropped appliances reassembled with computed offsets (cut edges didn't align to real object boundaries), then one whole strip per wall (fixed alignment, but a strip can never have a gap, so a mouse hole was always hidden behind solid furniture), then natural-seam tiles per wall (restored the gap, kept the alignment). All of this iteration was solving alignment problems *within* a photorealistic-scene style — but stepping back further, a photorealistic scene never matched `cat.png`/`dog_medium.png` (a bold flat-color cartoon mascot and a simple side-view pixel sprite, respectively — neither photorealistic, neither strict top-down) in the first place.
2. **PtPt's free flat-cartoon "Cute Pixel Cooking" pack** — genuinely modular sprites with real dimensional depth (Overcooked/Stardew-style), chosen specifically to match the mascot-style characters. This fixed the alignment problem for good (real modular tiles can't be cut off mid-object) and the layout mechanics from this round carried forward unchanged. But once the user saw it in place, the actual ask turned out to be different: "I want the game board kitchen to look **as realistic as possible**" — the user is a game engineer building this for his daughter and explicitly did not want to "vibe code" the art, so flat cartoon shading wasn't going to satisfy that regardless of how well it matched the layout.
3. **Individually-generated photorealistic objects** (`assets/realistic_*.png`, since removed) — reused the modular wall-building/gap mechanism from the PtPt round with photorealistic renders instead. **Rejected after being reviewed live.** Verbatim user feedback: "the images are way too big and out of scale with the characters. The 3/4 tilt doesn't work in this view as the kitchen board isnt. The counters dont conect to eah other. the images look realistic, but the scene/board doesnt." Concretely: the renders were scaled to fit the wall/interior geometry rather than to match character proportions; each render baked in its own 3/4 camera angle that clashed with the flat top-down board (a risk flagged and accepted before building, but one that reads as obviously wrong once the art is photorealistic, unlike with flat cartoon shading); and each render was a fully-modeled freestanding object rather than a slice of built-in cabinetry, so edge-to-edge placement showed a seam between boxes instead of one continuous countertop run. Net effect: individual images looked realistic in isolation but the composed board didn't read as a believable kitchen. **This is why the current round doesn't reuse that round's approach uncritically** — the scale (`MODULE_SCALE`) was deliberately dropped, and dimensions were re-read from scratch rather than reused.
4. **Current: `assets/kitchen_*.png`.** Same modular wall-building/gap mechanism again (it was never actually a rendering-style problem), rescaled and extended to all four walls (see Layout below) rather than just top/bottom.

Layout, per reset:
1. **Top and bottom walls are built from wall-module renders** (`cabinet` 832×497, `sink` 980×669, `stove` 981×703 — see `MODULE_SPECS`) placed edge-to-edge via `buildWall()`. These are **content** dimensions, not the raw file dimensions (847×512/1000×690/1000×719) — every `kitchen_*.png` file has ~7-11px of transparent padding baked in around the actual object (confirmed by scanning each file's alpha channel), so `MODULE_SPECS`/`FRIDGE_SPEC`/`TABLE_SPEC`/`CHAIR_SPEC` all store the trimmed content size plus a `cropX`/`cropY` offset, and `Furniture.draw()` source-rect-crops to just that region (see `Furniture.js` above) — without this, two modules placed bounding-box-to-bounding-box would still show a visible gap between their actual painted content. Each render has its own native size (not a shared grid), so `buildWall()` computes each piece's own scaled width and advances a cursor by that amount. `TOP_WALL_ORDER`/`BOTTOM_WALL_ORDER` give each wall a fixed sequence (`cabinet` doubles as filler — no separate plain-counter render exists).
2. **Left and right walls (new this round):** `buildWallVertical()` places `LEFT_WALL_ORDER`/`RIGHT_WALL_ORDER` (currently `cabinet` reused twice each, the same filler role it plays on top/bottom) edge-to-edge *vertically*, rotated 90°/270° via `Furniture`'s existing rotation support so each module's long edge runs along the wall instead of the floor. Confined strictly to the band between `TOP_WALL_HEIGHT` and `canvas.height - BOTTOM_WALL_HEIGHT` (not flush to the canvas corners) so they can never overlap the top wall's fridge or the bottom wall's run. Back-aligned to the wall band's front face (`x = WALL_BAND_THICKNESS` for left, `x = canvas.width - WALL_BAND_THICKNESS - depth` for right — see point 3). Rotation 90 vs. 270 (which side visually "faces" into the room) is a cosmetic choice, not verified live — flip `LEFT_WALL_ROTATION`/`RIGHT_WALL_ROTATION` if it looks wrong.
3. **Back-to-wall alignment on all four walls, not a floor baseline.** `makeModule()`/`buildWallVertical()` place every module's *back* (the edge facing the wall) flush against the wall band's front face — `WALL_BAND_THICKNESS` in from the canvas edge — rather than aligning a shared front/floor edge. This was a deliberate change from an earlier version of this layout that baseline-aligned each wall's modules by their *front* (floor-facing) edge instead — that kept front edges flush but let a shorter piece's back stop short of the wall, leaving a visible strip of bare floor between the piece and the wall (worse once `drawWalls()` added an actual wall band to fall short of — see Wall band & mouse holes above). The tradeoff: since these renders have different native heights, front edges (the room-facing side of the counters) now vary slightly per piece instead of lining up — accepted as the smaller visual cost of the two.
4. **One random gap, unchanged mechanic:** each reset, one of the **top/bottom** walls is picked at random (`gapWall`), one module slot within it is left empty instead of drawn — recorded as `this.wallGap` (`{x, y, width, height, wall}`) — and `generateEscapes()` places the first escape exactly centered in that gap. Left/right walls are **not** in the gap pool — they're solid runs every game, since `generateEscapes()`'s x/y math only handles horizontal walls today. This mechanism has now survived three full art-direction changes unmodified, since it was never actually a rendering-style problem.
5. **Fridge** (384×696 content, cropped from a 400×710 file): placed immediately after the last top-wall module, back-aligned like the counters (`y = WALL_BAND_THICKNESS`) so its top edge sits flush with the wall the same way theirs does, rather than floating or sinking. Unlike the previous (rejected) asset round, this fridge is **not** the tallest single piece by a wide margin — it's roughly the same height as the sink/stove — so `TOP_WALL_HEIGHT` is no longer hardcoded off the fridge specifically (see below).
6. **Dining set**: a table (958×651 content, from a 977×665 file) and **one** chair (565×615 content, from a 581×629 file) placed side by side, freestanding in open floor space (random-search placement avoiding furniture and spawn points) — not front/back chairs flanking the table. Side-by-side only needs the height of the taller piece, which is what made this fit reliably in the previous round; unchanged this round since the underlying constraint (a single-angle chair render, limited interior floor height) hasn't changed.

**Spawn points must stay clear of wall collision boxes:** `TOP_WALL_HEIGHT`/`BOTTOM_WALL_HEIGHT` are `WALL_BAND_THICKNESS` plus the **max scaled height among whatever's actually placed on that wall** (`Math.max(...order.map(...), FRIDGE_SPEC.height)` for top), not hardcoded off any one piece — this round's fridge/sink/stove are all close in height, unlike the previous round where the fridge was unambiguously tallest and could be hardcoded as the source of truth. The `WALL_BAND_THICKNESS` term matters because every module's back is now flush against the wall band's front face rather than the raw canvas edge (see point 3 above) — clearance has to cover the band too, not just the furniture depth. Similarly `LEFT_WALL_WIDTH`/`RIGHT_WALL_WIDTH` (`WALL_BAND_THICKNESS` plus the rotated depth into the room — native *height* × scale, since rotation swaps the axes) keep the dining-set search area and spawn points clear of the new side walls. This is the same class of bug hit twice already in this project's history (a cat/dog spawn landing inside a wall's collision box, unable to move in any direction) — see git history for the earlier incidents; `SPAWN_CLEARANCE` is what `resetGameObjects()` uses on top of the wall-height constants. The mouse's fixed spawn (100, 100) stays exempt since it doesn't collide with furniture at all (see `Mouse.js` above).

- The `tabletop_*`/`*_corner`/`wallframes`/`wallknife` assets from the very first WIP commit are **not a dining table** — closer inspection shows they're a pool table (green felt top, wood rail) plus a wall knife/dart rack and framed art. Still unused; don't reach for these for kitchen/dining furniture.

## Punch mechanic
- `p` → `InputHandler` dispatches a `'punch'` custom event on `document`.
- `GameScreen` listens for `'punch'` in `init()`, plays `SOUND_KEYS.PUNCH`, and calls `handlePunch()`, which knocks the dog `PUNCH_DISTANCE` (40px) away from the cat (clamped to canvas bounds) and starts a purple `shockwave` ring centered on the cat, drawn by `drawShockwave()` for `PUNCH_SHOCKWAVE_DURATION` (200ms).
- `m` → dispatches a `'meow'` event, which just plays the meow sound (no gameplay effect).

## Mobile responsiveness (`js/utils/scale.js`, `orientationGate.js`, `touchControls.js`)
Milestone-scope mobile support: the game requires landscape (a full-screen gate blocks portrait) rather than reworking layout for both orientations, but *within* landscape it now scales correctly at any canvas size. Confirmed live before this existed: on a 350px-wide mobile canvas, a single stove alone ate ~40% of the board height, because every size in the game (furniture scale, wall thickness, character size/speed, floor tile size, UI chrome) was a fixed pixel value tuned by eye against a desktop-sized canvas.

- **The scale factor** (`js/utils/scale.js`, `getScale(canvasWidth) = canvasWidth / 1280`) is the single source of truth — 1280 is `resizeCanvas()`'s (`js/main.js`) desktop width cap, i.e. the size everything was originally tuned against. `GameScreen` computes `this.layout = computeLayout(canvas.width)` once in its constructor (canvas size is fixed for a `GameScreen`'s lifetime — live mid-game resize is a separate, still-open gap, see Known rough edges) and every `BASE_*` constant (`BASE_MODULE_SCALE`, `BASE_WALL_BAND_THICKNESS`, `BASE_ESCAPE_SIZE`, `BASE_SPAWN_CLEARANCE`, etc.) is multiplied by it inside `computeLayout()` — methods read `this.layout.X`, never a bare module constant, for anything that used to be a fixed pixel size. `Cat`/`Dog`/`Mouse` each take their own `scale` param (derived the same way, since they already receive `canvasWidth`) and apply it to size/speed — but **not** to `frameWidth`/`frameHeight` used for sprite-sheet *source*-rect slicing, which must stay at the sprite's real native pixel dimensions regardless of display scale. `Dog` additionally exposes `nativeFrameWidth`/`nativeFrameHeight` for this since its native frame size was previously reused directly as the draw destination size too (no `/4` divisor like `Cat` has). `Cutscene.js` has its own `this.scale` (same `getScale()` call) for its modal/text/button sizing — this was a real bug hit live (long cutscene text overflowing its modal on a small canvas) fixed by the same mechanism, not just a furniture-specific concern.
- **`Cat`/`Dog`/`Mouse` expose `displayWidth`/`displayHeight` getters** giving each character's actual on-screen size regardless of how each class internally represents it (`Cat`'s `frameWidth/4 * scale`, `Dog`'s already-scaled `frameWidth`, `Mouse`'s `size`) — `Cutscene.js` reads these (falling back to raw `frameWidth`/`frameHeight`) to center each character correctly, and `GameScreen`'s `handlePunch()`/`drawRedOutline()` use `cat.displayWidth`/`displayHeight` instead of re-deriving `frameWidth/4` themselves.
- **The landscape gate** (`orientationGate.js`) is a full-screen overlay (`#orientationGate` in `index.html`, styled in `styles.css`) shown whenever `window.innerHeight > window.innerWidth`, checked on load/`resize`/`orientationchange` — this finally gives `styles.css` a purpose (see Known rough edges below). It's a real aspect-ratio check, not a device/breakpoint media query, so a narrow desktop window triggers it too. The game loop keeps running underneath it (not paused) — the overlay's `z-index` just makes the board unreachable, which was judged sufficient for this milestone rather than also pausing `update()`.
- **Touch controls** (`touchControls.js`): an on-screen D-pad (`#dpad`) and punch/toot/meow buttons (`#actionButtons`), anchored to the *viewport's* corners via `position: fixed`, not the canvas. This works because `resizeCanvas()` locks the canvas to 4:3 while landscape phones are reliably wider than that, so there's always empty margin beside (or, on a less-wide viewport, below) the canvas for these to sit in without overlapping the board — confirmed at a few tested sizes, not exhaustively. Each button dispatches a real `KeyboardEvent` (`keydown`/`keyup` for the D-pad, a single `keydown` for the action buttons) on `window` — `InputHandler.js` is completely unaware touch controls exist; it just sees the same events a physical keyboard would send. Visibility is CSS-only: `@media (pointer: coarse)` keeps them off desktop, and `body.in-game` (toggled by `GameScreen.init()`/`cleanup()`) keeps them off the setup screen.
- **Not covered by this pass:** actual portrait layout (deliberately out of scope — see the gate above), and the pre-existing live-resize gap (furniture/spawn positions are computed once at generation time from `canvas.width`/`canvas.height` and never re-laid-out if the canvas resizes mid-game — unchanged by this work, still tracked in Planned work below).

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this pattern rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB (axis-aligned bounding box) checks via the shared `aabbOverlap` helper — no physics library.

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage currently exists for any collision, movement, or game-state logic.
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, layout scaling, and procedural level generation in one ~950-line class — a strong refactor candidate.
- `styles.css` now holds the orientation-gate/touch-controls CSS (see Mobile responsiveness above) — everything else is still Tailwind utility classes in `index.html`.

## Planned work
- **NEXT UP — mobile/landscape in-game assets are too small; need to roughly double.** Reviewed live on an actual mobile device in landscape (not just the desktop-browser-resized testing the scaling system itself was verified with — see Mobile responsiveness above): furniture and characters read as too small on a real phone. The scaling system to adjust is `js/utils/scale.js`'s `getScale(canvasWidth) = canvasWidth / REFERENCE_WIDTH` (`REFERENCE_WIDTH = 1280`), consumed as `this.layout` in `GameScreen`'s constructor and as a `scale` param in `Cat`/`Dog`/`Mouse`/`Cutscene`. Likely candidates, to discuss before picking one: (a) lower `REFERENCE_WIDTH` so the same canvas width yields a larger scale factor, (b) apply a flat extra multiplier (e.g. ×2) on top of the existing scale specifically when in the mobile/landscape path (vs. desktop), or (c) add a minimum-scale floor so small canvases never go below some in-game-readable size. Whichever approach is picked, re-check that furniture/character proportions *relative to each other* still hold (the whole point of the scale system was keeping that ratio constant across canvas sizes — see Mobile responsiveness above for the full rationale) and that spawn-clearance math (`TOP_WALL_HEIGHT`/`BOTTOM_WALL_HEIGHT`/etc., also scale-derived) doesn't end up leaving too little open floor if assets get bigger.

Future rooms (living room, bathroom, etc. for later stages) will need their own set of renders in whatever this direction turns out to be; nothing kitchen-specific here carries over, though the *mechanism* (modular baseline/edge-aligned wall pieces with a random gap for a mouse hole, now on all four walls) generalizes to any room.
- **Mobile responsiveness — landscape done, portrait and live-resize still open.** See Mobile responsiveness above for what's implemented (canvas-relative scaling, a landscape-only gate, an on-screen D-pad/action buttons). Explicitly out of scope so far: an actual portrait layout (the gate just blocks it rather than adapting to it), and making entity/furniture positions re-derive from canvas size on resize instead of going stale — furniture (like everything else in `GameScreen`) computes its position once from `canvas.width`/`canvas.height` at generation time and never re-lays-out if the canvas resizes afterward (e.g. a browser window resize, or a phone's on-screen keyboard/browser chrome changing the viewport, mid-game); positions go stale and can end up rendering partially off-canvas. Not new to furniture specifically — cat/mouse/dog spawn points have the same assumption. The D-pad/action button *positions* (anchored to viewport corners) were only checked at a handful of sizes — worth a wider check across real device aspect ratios.

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- `GameScreen.cleanup()` centralizes teardown of document/canvas listeners and the `InputHandler` — call it (or extend it) rather than adding new listeners without a matching removal path.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest), not assume one is already there.
