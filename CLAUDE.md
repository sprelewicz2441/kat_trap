# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). You control a cat chasing a mouse around an arena, while a dog wanders randomly and catches the cat if they collide. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step.

## Architecture

**Entry point:** `js/main.js`
- Grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, and starts on `SetupScreen`.
- Runs a single `requestAnimationFrame` game loop that calls `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — a simple state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render` to whichever screen is active. Screens are swapped via `setScreen()`, which calls the new screen's `init()`.
- `SetupScreen.js` — animated title/start screen. Draws a background image over an animated gradient, defines a clickable "Start Game" hit-box (`startButtonArea`) computed as a percentage of the background image's position, and transitions to `GameScreen` on click.
- `GameScreen.js` (**~765 lines — by far the largest file, and the one most likely to need review before extending**) — owns the actual gameplay: creating the cat/mouse/dog/escapes/furniture, the input-driven cat movement, dog-vs-cat and cat-vs-mouse collision checks, the punch/toot/meow input reactions and punch shockwave animation, procedural kitchen-furniture layout, sound playback, win/lose messaging, and a "play again" button. Also kicks off cutscenes at the start via `CutsceneManager`.

**Entities** (`js/classes/`) — each is a small, mostly self-contained class with `update()`/`draw(ctx)`:
- `Cat.js` — player-controlled; `move(direction)` is called from `GameScreen` based on `InputHandler` state. Handles its own sprite-sheet animation.
- `Dog.js` — moves randomly on a timer (`moveInterval`), respects an obstacle list (currently the `furniture` array, still named `boundaries`/`this.boundaries` internally, a naming leftover from before furniture existed) and `escapes` when deciding valid moves, barks on a random interval, and exposes `isColliding(entity)`.
- `Mouse.js` — moves with pseudo-random velocity, bounces off canvas walls, fires a `wallHitCallback` on bounce. Intentionally **not** blocked by furniture (mouse has no pathfinding, so a real collision would risk it getting stuck against furniture corners); instead `GameScreen.render()` draws the mouse *before* furniture so furniture visually paints over it wherever they overlap, giving the effect of the mouse ducking under furniture while passing through unobstructed.
- `Escape.js` — a static rectangle ("mouse hole"); `isMouseInside()` for collision.
- `Furniture.js` — kitchen/dining obstacle (counter modules, fridge, dining set). Takes `(x, y, type, spriteSrc, rotation = 0, spriteWidth = 32, spriteHeight = 64, scale = 1.5)`; every kitchen piece today passes explicit width/height/scale overrides rather than relying on those defaults, since none of the current sprites match them (the defaults are a leftover from an earlier asset generation). Rotation (0/90/180/270) swaps width/height and is applied via canvas transform in `draw()`, centered on the same pivot the collision box uses — currently unused (nothing in the kitchen rotates; see Kitchen furniture below for why) but kept working. Sets `ctx.imageSmoothingEnabled = false` before drawing — a leftover from when kitchen sprites were small pixel art that needed to stay crisp when scaled up; harmless no-op now that they're high-res photorealistic renders, but not worth removing. Draws a type-colored placeholder rect while the sprite loads. `isWallItem` is computed in the constructor but never read anywhere — dead property.
- `InputHandler.js` — tracks currently-held keys via `window` keydown/keyup listeners, exposes `getDirection()`; also dispatches custom `'toot'` (spacebar), `'punch'` (`p`), and `'meow'` (`m`) events for `GameScreen` to react to.

**Cutscenes** (`js/classes/cutscenes/`):
- `Cutscene.js` / `CutsceneManager.js` — sequenced intro scenes shown before gameplay starts, triggered from `GameScreen.startCutscenes()`.

**Utilities** (`js/utils/`):
- `collision.js` — exports `aabbOverlap(ax, ay, aWidth, aHeight, bx, by, bWidth, bHeight)`, the single shared axis-aligned bounding box overlap test. Used by `Escape.isMouseInside`, `Dog.isColliding`, `Furniture.isColliding`, and `GameScreen.checkCollision`. Takes raw coordinates rather than entity objects so each caller stays explicit about which field it's using per side (e.g. `Dog` uses its own `frameWidth`/`frameHeight` for itself but `entity.size` for whatever it's checking against) — don't refactor it to accept entities and guess the right field, since the same object (e.g. `Dog`) legitimately uses different box dimensions depending on which side of the check it's on.

## Floor background (`GameScreen.drawFloor`)
`render()` fills the whole canvas with a repeating two-tone checker pattern before drawing anything else. The pattern is generated on an offscreen canvas at draw time (two `fillRect` calls in `COLORS.FLOOR_LIGHT`/`FLOOR_DARK`, cached on `this.floorPattern` via `ctx.createPattern(..., 'repeat')`) rather than loaded from an image — there's no async load to wait on, and picking the colors directly guarantees they sit behind the furniture sprites' palette without a texture mismatch. This replaced an earlier photographic floor crop (`floor_tile.png`, cropped from the same AI-generated kitchen photo the furniture used to be cropped from) once that furniture was replaced — see Kitchen furniture below for why the photographic art direction was dropped entirely, floor included.

## Kitchen furniture (`GameScreen.generateKitchenFurniture`)
Procedurally lays out `Furniture` instances each game reset from `assets/realistic_*.png` — individually AI-generated photorealistic renders (one object per image, generated via yeri.ai/Stable Diffusion), each trimmed to its own content and given a transparent background by a pixel-processing pass (near-white pixels set to alpha 0 on an offscreen canvas — see the commit that introduced these assets for the exact script). This is the **third complete art direction** for kitchen furniture — see "Why the art direction changed twice" below before reaching for a flat sprite pack or a full AI-scene crop here; both were tried and superseded for specific, non-obvious reasons.

**Why the art direction changed twice (read this before touching kitchen art):**
1. **First: crops from one whole AI-generated scene** (`kitchen_reference_scene.jpg`, all still in git history) — individually-cropped appliances reassembled with computed offsets (cut edges didn't align to real object boundaries), then one whole strip per wall (fixed alignment, but a strip can never have a gap, so a mouse hole was always hidden behind solid furniture), then natural-seam tiles per wall (restored the gap, kept the alignment). All of this iteration was solving alignment problems *within* a photorealistic-scene style — but stepping back further, a photorealistic scene never matched `cat.png`/`dog_medium.png` (a bold flat-color cartoon mascot and a simple side-view pixel sprite, respectively — neither photorealistic, neither strict top-down) in the first place.
2. **Second: PtPt's free flat-cartoon "Cute Pixel Cooking" pack** — genuinely modular sprites with real dimensional depth (Overcooked/Stardew-style), chosen specifically to match the mascot-style characters. This fixed the alignment problem for good (real modular tiles can't be cut off mid-object) and the layout mechanics from this round carried forward unchanged. But once the user saw it in place, the actual ask turned out to be different: "I want the game board kitchen to look **as realistic as possible**" — the user is a game engineer building this for his daughter and explicitly did not want to "vibe code" the art, so flat cartoon shading wasn't going to satisfy that regardless of how well it matched the layout.
3. **Current: individually-generated photorealistic objects.** The key insight carried over from the *first* direction's failure: a photorealistic **whole scene** can't be cut apart without alignment problems, but photorealistic **individual objects** (one clean render per counter/appliance, generated and processed the same modular way the PtPt pack was) sidestep that entirely — nothing is ever cropped out of a larger composition, so nothing can be cut off mid-object. This keeps the exact same modular wall-building/gap mechanism from the PtPt round; only the asset source and the per-piece dimensions changed.

Layout, per reset:
1. **Top and bottom walls are built from wall-module renders** (`cabinet`, `sink`, `stove` — see `MODULE_SPECS`) placed edge-to-edge via `buildWall()`. Unlike the PtPt pack's uniform 64px-wide sprites, these renders each have their own native size (cropped tightly to their own content, not to a shared grid), so `buildWall()` computes each piece's own scaled width and advances a cursor by that amount — there's no fixed cell size to lean on. `TOP_WALL_ORDER`/`BOTTOM_WALL_ORDER` give each wall a fixed sequence (`cabinet` doubles as filler, the role `counter` played in the PtPt pack, since no separate plain-counter render exists this round).
2. **Baseline alignment, not top alignment:** `makeModule()` aligns every module to a shared baseline (the floor line) by computing `y = baselineY - height`, the same principle as the PtPt round — these renders have different native heights (817/797/703 for sink/cabinet/stove), and aligning by a shared top would float the shorter pieces above the floor.
3. **One random gap, unchanged mechanic:** each reset, one wall is picked at random (`gapWall`), one module slot within it is left empty instead of drawn — recorded as `this.wallGap` (`{x, y, width, height, wall}`) — and `generateEscapes()` places the first escape exactly centered in that gap. This mechanism has now survived two full art-direction changes unmodified, since it was never actually a rendering-style problem.
4. **Fridge**: placed immediately after the last top-wall module, its top flush with the wall's top edge. It's the tallest single piece by far (957 native vs. ~700-820 for the counter modules) — see the `TOP_WALL_HEIGHT` note below for why that matters beyond just how it looks.
5. **Dining set**: a table and **one** chair placed side by side (not front/back chairs flanking the table like the PtPt round) — this photorealistic chair render only exists from a single angle (no matching "seen from the back" render), and more importantly, stacking chair+table+chair vertically needs their combined height to fit the interior floor band, which doesn't work at this scale (confirmed live: it fit roughly 1 game in 4 before this was changed). Side by side only needs the height of the *taller* of the two pieces, which reliably fits — confirmed live at 20/20 across repeated resets.

**Spawn points must stay clear of wall collision boxes:** `TOP_WALL_HEIGHT` is deliberately derived from the **fridge's** height (957 native × `MODULE_SCALE`), not from the counter modules — the fridge sits on the top wall and is taller than any counter module, so sizing clearance off the counters alone would let the cat/dog spawn land inside the fridge's collision box. This is the same class of bug hit twice already in this project's history (a cat spawn landing inside a wall's collision box, unable to move in any direction) — see git history for the earlier incidents; `TOP_WALL_HEIGHT`/`BOTTOM_WALL_HEIGHT` and `SPAWN_CLEARANCE` are what `resetGameObjects()` uses to keep the cat/dog spawn points clear of whatever is tallest on each wall. The mouse's fixed spawn (100, 100) stays exempt since it doesn't collide with furniture at all (see `Mouse.js` above).

**Asset source:** `assets/realistic_*.png` were generated one object at a time via yeri.ai (a Stable Diffusion-based generator, formerly branded stablediffusionweb.com — same site the very first reference photo in this project's history came from), each prompted individually for a consistent "dark matte modern cabinetry, white marble countertop" style so the pieces would read as one kitchen rather than mismatched furniture — the same mismatch risk documented in the very first furniture attempt in this project's history when different asset packs were combined. Each raw generation was then processed (crop to content bounding box + near-white-to-transparent) before being wired in; the raw un-processed generations aren't kept in the repo. Everything from the PtPt round (`ptpt_*.png`, the flat-cartoon sprites) was removed in the same commit that wired in these renders — there are no PtPt-descended pieces left in the current build.
- The `tabletop_*`/`*_corner`/`wallframes`/`wallknife` assets from the very first WIP commit are **not a dining table** — closer inspection shows they're a pool table (green felt top, wood rail) plus a wall knife/dart rack and framed art. Still unused; don't reach for these for kitchen/dining furniture.

## Punch mechanic
- `p` → `InputHandler` dispatches a `'punch'` custom event on `document`.
- `GameScreen` listens for `'punch'` in `init()`, plays `SOUND_KEYS.PUNCH`, and calls `handlePunch()`, which knocks the dog `PUNCH_DISTANCE` (40px) away from the cat (clamped to canvas bounds) and starts a purple `shockwave` ring centered on the cat, drawn by `drawShockwave()` for `PUNCH_SHOCKWAVE_DURATION` (200ms).
- `m` → dispatches a `'meow'` event, which just plays the meow sound (no gameplay effect).

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this pattern rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB (axis-aligned bounding box) checks via the shared `aabbOverlap` helper — no physics library.

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage currently exists for any collision, movement, or game-state logic.
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, and procedural level generation in one ~725-line class — a strong refactor candidate.
- `styles.css` exists but is currently empty — all styling is Tailwind utility classes in `index.html`.

## Planned work
- **Furniture asset rework — kitchen redone with individually-generated photorealistic renders, other rooms still to do.** See Kitchen furniture above for the current approach and the full history of why it changed art direction twice (photorealistic AI-scene crops → PtPt's flat-cartoon pack → individually-generated photorealistic objects). Remaining for the kitchen specifically: only 3 distinct wall-module renders exist (cabinet/sink/stove — no separate plain-counter render), so `TOP_WALL_ORDER`/`BOTTOM_WALL_ORDER` are fixed sequences rather than randomized among alternatives, and every game's wall composition looks the same modulo which single slot has the mouse-hole gap; there's no dedicated trashcan or other small accent piece this round (dropped rather than reused from a mismatched-style pack). Future rooms (living room, bathroom, etc. for later stages) will need their own set of individually-generated, consistently-prompted renders — nothing kitchen-specific here carries over, though the *mechanism* (modular baseline-aligned wall pieces with a random gap for a mouse hole) generalizes to any room.
- **Mobile responsiveness.** Not addressed yet. Canvas sizing (`resizeCanvas` in `js/main.js`) and all movement/collision math currently assume keyboard input (`InputHandler` only listens for arrow keys, space, `p`, `m`) — touch input and layout would both need work. This should also cover making entity/furniture positions re-derive from canvas size on resize instead of going stale — furniture (like everything else in `GameScreen`) computes its position once from `canvas.width`/`canvas.height` at generation time and never re-lays-out if the canvas resizes afterward (e.g. a browser window resize mid-game); positions go stale and can end up rendering partially off-canvas. Not new to furniture specifically — cat/mouse/dog spawn points have the same assumption.

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- `GameScreen.cleanup()` centralizes teardown of document/canvas listeners and the `InputHandler` — call it (or extend it) rather than adding new listeners without a matching removal path.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest), not assume one is already there.
