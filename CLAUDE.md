# KatTrap

## What this is
A browser-based canvas game built in vanilla JavaScript (ES modules, no framework, no build step). Before each game, you choose which character to control — Cat (chase the mouse), Mouse (escape the cat), or Dog (pause the cat to help the mouse escape) — while whichever of the other two you're not playing behaves autonomously. Colliding with the dog always pauses the cat, regardless of who's playing. The mouse can escape through one of several "mouse holes." Styled with Tailwind (via CDN) on top of a single `<canvas>` element.

Open `index.html` directly in a browser (or serve the folder statically) to run it — there is currently no build/bundle step.

## Architecture

**Entry point:** `js/main.js`
- Grabs the canvas, sizes it responsively (`resizeCanvas`), creates a `ScreenManager`, and starts on `SetupScreen`.
- Runs a single `requestAnimationFrame` game loop that calls `screenManager.update()` then `.render()` each frame.

**Screens** (`js/classes/screens/`) — a simple state-machine pattern:
- `ScreenManager.js` — holds `currentScreen`, forwards `update`/`render` to whichever screen is active. Screens are swapped via `setScreen()`, which calls the outgoing screen's `cleanup()` (if it has one) before swapping, then the new screen's `init()` — the automatic-cleanup call was added after `SetupScreen`'s animated-background loop and a stray listener turned out to run forever with nothing ever tearing them down.
- `SetupScreen.js` — animated title/start screen. Draws a background image over an animated gradient, defines a clickable "Start Game" hit-box (`startButtonArea`) computed as a percentage of the background image's position, and transitions to `CharacterSelectScreen` on click (previously went straight to `GameScreen` — see Character selection below). Has its own `cleanup()` (stops the `animateBackground()` `requestAnimationFrame` loop via a `running` flag, removes its `mousemove` listener — previously anonymous and unremovable).
- `CharacterSelectScreen.js` — lets the player pick which character they control before gameplay starts: Cat, Mouse, or Dog, all three enabled. Canvas-drawn like `SetupScreen`, same self-contained-screen shape (`init`/`render`/`cleanup`). Picking one constructs `GameScreen` with a `controlledEntity` of `'cat'`, `'mouse'`, or `'dog'` — see Character selection & playable modes below. Each option renders as an "animal-ear card" — a rounded rect with two ears poking up from the top edge, reading as a head silhouette — but not all three wear the *same* ears: `EAR_SHAPES` maps each `option.entity` to its own `{card, inner}` pair from `canvasShapes.js` (`drawCatEarCard`/`drawCatEarInner` for cat, `drawMouseEarCard`/`drawMouseEarInner` for mouse, `drawDogEarCard`/`drawDogEarInner` for dog), all three sharing the exact same call sites in the render loop so adding a shape for a hypothetical 4th character is a one-line `EAR_SHAPES` addition, not a render-loop change. The cat's own shape is the third this screen has used overall: a plain flat-rectangle version, then a mouse-hole-arch version (shaped like `Escape.js`'s wall cutout, rejected live as off-brand for a game named "Kat Trap" — "mouse hole seems out of place"), now the pointed-ear one — see `canvasShapes.js` below for the mouse/dog shapes' own, considerably longer design history (both went through multiple rejected attempts before landing). Each card is filled with its own full saturated gradient (`THEMES`: cat gold-to-orange, mouse lilac-to-purple, dog sky-blue-to-blue) rather than a shared neutral fill — a cream/parchment version matching Cutscene's modal was tried so the two screens shared one card look, but that turned out not to be the actual ask: it made the *cards* resemble the cutscenes rather than the *backdrop* (see below), and crowded out the backdrop's own color by visual weight ("the cards should look like they were... the BACKGROUND should look like the cut scenes"). Dog is blue rather than the amber/brown an earlier version had — confirmed live that orange and brown/amber read as too close to tell apart at a glance ("the orange and brown color are too close"), which a completely different hue family sidesteps outright. White text with a dark drop shadow (not dark text) — needs to stay legible across each gradient's full light-to-dark range. Cards' two-tone inner ears (`drawCatEarInner`, a shared pale pink over each card's own colored outer ear — the classic cartoon-cat "pink inner ear," and a genuine visual match for the pink inner ears already visible on the title screen's own dog mascot) are unaffected by any of this — they sit on top of whatever the outer ear's own fill is. The screen's own backdrop — not the cards — is what actually matches Cutscene: a teal-to-gold diagonal gradient sampled directly off `assets/start_screen.jpg`'s own pixels (`#2fa8b8` to `#ffb238` — that image's sky teal and its "KAT TRAP!" lettering gold), not the muted kitchen-wood-oak gradient this briefly used before that (rejected live as "boring colors") or the blue/teal family `SetupScreen`'s animated background uses. This is the very next screen after the title screen, so it picks up *that* screen's own candy-bright palette rather than the game board's kitchen palette or a generic app gradient (see Cutscene below, which shares this same backdrop gradient — just the backdrop, not its card treatment). Each card shows a small live crop of that character's actual sprite sheet (`PORTRAITS`, native source-rect coordinates into `cat.png`/`mouse.png`/`dog_medium.png` — no new art) rather than text alone. `hoveredIndex`/`pressedIndex` (updated via `mousemove`/`mousedown`/`mouseup`/`mouseleave`) drive a small lift-on-hover / settle-on-press effect — hit-testing always uses each card's original (un-lifted) `buttonAreas` entry, so the hover lift itself can never push a card out from under the cursor. **`effectiveScale`, not `getUIScale()` directly, drives every size in this screen** — confirmed live that the naive 3-card row overflowed the canvas on touch devices (cards clipped off both edges), because `getUIScale()`'s touch multiplier (2x, tuned against a single centered button/message elsewhere in the game) applied to three side-by-side cards doesn't leave room in a canvas that's only modestly narrower than desktop's. `effectiveScale = uiScale * fitScale`, where `fitScale` shrinks the whole layout proportionally whenever the naive row width would exceed the canvas (checked against `BASE_CARD_WIDTH`/`BASE_CARD_GAP` before any card is actually drawn) — a no-op (`fitScale = 1`) in the common case, so desktop rendering is unaffected. If you add a new option to `OPTIONS` (a 4th character, say), this clamp is what keeps the row from overflowing again rather than needing a fresh round of manual tuning.
- `GameScreen.js` (**~1000+ lines — by far the largest file, and the one most likely to need review before extending**) — owns the actual gameplay: creating the cat/mouse/dog/escapes/furniture, cat movement (player-driven or autonomous, depending on `controlledEntity` — see below), dog-vs-cat and cat-vs-mouse collision checks, the punch/toot/meow input reactions and punch shockwave animation, procedural kitchen-furniture layout, sound playback, win/lose messaging, a "play again" button, and the live mouse-escape-danger indicator (see Viewport frame & mouse-escape danger indicator below). Also kicks off cutscenes at the start via `CutsceneManager`.

**Entities** (`js/classes/`) — each is a small, mostly self-contained class with `update()`/`draw(ctx)`:
- `Cat.js` — player-controlled in Cat mode; otherwise (Mouse or Dog mode) it's driven autonomously by the same AI instead (see Character selection & playable modes below), but all paths call the same `move(direction, speed = this.speed)`. `speed` is an optional override so `GameScreen`'s AI wander path can move at a different speed than the default — it's a parameter rather than always reading `this.speed` internally because an earlier version silently ignored any override (validated a proposed move at one speed, then always applied `this.speed` regardless of what was passed), so tuning the AI's wander-speed multiplier had no real effect on movement for several iterations before this was caught. Tracks `this.facingDirection` (`'up'`/`'down'`/`'left'`/`'right'`), updated on every `move()` call regardless of who's driving it — used by the Mouse-mode cat AI's line-of-sight check, and (see below) by `draw()`'s directional lean. Takes both a `scale` (movement speed) and a `sizeScale` (on-screen/collision size, defaults to `scale`) — kept separate so a display-size change can never accidentally change how fast the cat moves; see Mobile responsiveness below. Handles its own sprite-sheet animation. `cat.png` is a symmetric, front-facing portrait (matching ears/whiskers, centered face) — not a directional side-view sprite like `Dog.js`'s — so there's no left/right art to flip and no up/down art to swap to the way `Dog`/`Mouse` show direction. `applyDirectionalTransform()` fakes it instead: a small rotation leaning into the turn for left/right, a small vertical stretch/squash for up/down (taller reaching "up", shorter settling "down"), applied around the cat's own center. Deliberately small (`TILT_ANGLE`/`STRETCH_AMOUNT`, both module-level constants) since a literal 90° rotation of a round mascot head reads as broken, not directional. Gated behind `this.hasMoved` (set `true` the first time `move()` actually runs) so a `Cat` that's only ever been constructed and drawn — `Cutscene.js`'s preview, or the very first rendered frame of a new round — doesn't inherit a phantom squash from the arbitrary `'down'` default `facingDirection` starts at. `applyDirectionalTransform()` is exposed as its own method (not inlined in `draw()`) specifically so `GameScreen.drawRedOutline()` (see Punch mechanic / game-over sections below) can apply the identical transform to its outline silhouette and stay aligned with the real, now-tiltable sprite. **Furniture collision uses a separate, much smaller "legs" hitbox, not the full sprite.** `cat.png` is a big round head (with ears/whiskers sticking out to both sides) over a much narrower body/legs section — `this.size` (a square, `(originalWidth/3)*sizeScale`) is actually *bigger* than the full display sprite in both dimensions, let alone just its solid part, which meant `GameScreen.tryMoveCat()`'s furniture check stopped the cat well short of where it visually looked like it should (confirmed live via a screenshot: an obvious gap remained between the cat and a counter corner). `hitboxWidth`/`hitboxHeight` (35%/30% of `displayWidth`/`displayHeight`, ratios measured off the actual asset's alpha channel) and `getHitboxAt(x, y)` (an arbitrary position, not just `this.x`/`this.y` — `tryMoveCat()` needs the hitbox for a *proposed* position it hasn't committed to yet) give the collision box the legs' actual footprint instead, horizontally centered under the sprite and anchored to its bottom edge (where the legs are) rather than sharing the sprite's own top-left origin. `GameScreen.tryMoveCat()` calls `aabbOverlap()` directly with this rect rather than going through `Furniture.isColliding()` (which assumes a square `entity.size`), since this box isn't square. Originally scoped to just this one check — `this.size` also drove the wall-edge clamp and the cat-catches-mouse win check, neither of which had this complaint at the time. Both were fixed in a later pass once they *did* get the same complaint — see "Hitbox tightening" below; `this.size` is now only actually used for the AI's line-of-sight lane width, kept deliberately unchanged (a wider perception box isn't the same bug as catching from too far away).

  **`cat_v2.png` — a redrawn, "Disneyfied" sprite sheet, replacing the original `cat.png` art.** Per explicit direction ("I want to cartoon it up and modernize it, like on the splash screen... Disneyfy it some... I want it in a pink ballerina dress as well"): same character identity (white fur, coral/pink inner ears, purple hair-tuft/whisker accents, big grin) redrawn in a glossier, more polished cartoon style, now wearing a pink ballerina outfit. **Generated as a direct 6-frame sprite-sheet request to the image model, not six separate single-frame generations stitched together afterward** — the initial plan was a plain still-portrait prompt with a separate compositing step, but asking the model for the sheet directly (a vertical strip, one frame per row) turned out simpler and worked well: measuring each frame's own content bounding box on the raw 1024×1536 output showed left/right edges consistent within a few px across all 6 frames (left 415-419, right 615-617), i.e. the model kept the character aligned to the same column on every row without being told to. A low-resolution preview render of the raw output briefly looked like it had a soft glow/halo around the character — checked directly via pixel sampling (a horizontal scanline through the character plus a few explicit `getpixel` calls) before trusting that impression, which showed alpha=0 outside the character and a sharp jump to full opacity (~253) right at its edge — the "glow" was a preview-scaling artifact, not real baked-in halo content, so no special halo-removal step was needed.
  - **Processing** (one-off Python/PIL script, not part of the runtime): uniform crop box (408–624px, ~7px margin beyond the measured content extents on every frame) sliced out each of the 6 vertical bands, each resized to the target 118px width via Lanczos resampling (preserving aspect ratio, landing at ~140px tall), then pasted onto a transparent 118×150 canvas with a small top pad (matching v1's own per-frame content bbox, which filled nearly the full 150px height with only a few px of empty space at the very top) so the new art anchors the same way the old art did. Frame geometry (118×150 per frame, 6 frames, single vertical column) was kept **identical** to v1 on purpose — the new sheet was cropped/resized specifically to match those existing dimensions, so `Cat.js`'s `frameWidth`/`frameHeight`/`totalFrames` and the `HITBOX_WIDTH_RATIO`/`HITBOX_HEIGHT_RATIO` collision ratios (see above — measured off v1's alpha channel) didn't need to change for the swap to work; those hitbox ratios are carried over unmeasured against the new ballerina-pose silhouette rather than freshly re-measured, a known minor imprecision, not yet flagged as a problem live.
  - **Verified live** (character-select card, all three cutscenes, actual gameplay movement in all four directions, the cat-catches-mouse win modal): the new art renders cleanly with no halo/fringe, `applyDirectionalTransform()`'s tilt-for-left/right and stretch-for-up/down read correctly on the new silhouette exactly as they did on v1, and the walk-cycle animates through frames normally while moving.
  - Same "deprecate, don't delete" precedent as every other asset swap this project has done: `assets/cat.png` (v1) stays on disk, unreferenced, rather than being removed, in case of a rollback. `Cat.js`'s `this.spriteSheet.src` and `CharacterSelectScreen.js`'s `PORTRAITS.cat.src` both point at `cat_v2.png` now.
- `Dog.js` — in Cat/Mouse mode, wanders continuously (re-picking a random direction every `wanderDirectionChangeInterval`, 1500ms, or immediately on a blocked move via the shared `tryMove(direction, speed)` helper), the same per-tick-movement pattern `GameScreen`'s `wanderCat()` uses, not the once-every-`moveInterval`-hop design this replaced (see "Dog speed & movement history" below); in Dog mode, `GameScreen.movePlayerDog()` drives it directly from arrow-key input instead (per-tick, same granularity as `tryMoveCat()` — see Character selection & playable modes below), and `Dog.update()`'s own autonomous wander is bypassed entirely (only its `updateAnimation()`/`isColliding()` are still used directly by `GameScreen`). Barks on a random interval regardless of mode via `setNextBark()`'s self-rescheduling `setTimeout` chain, which `pauseBarking()`/`resumeBarking()` can suspend and restart (a fresh random delay each time, not resuming a saved remainder) — see "Dog bark persisting past pause/game-over" below for why plain `cleanup()` alone wasn't enough. Exposes `isColliding(entity)` (used both by the autonomous path's own collision check and directly by `GameScreen` in Dog mode). Takes both a `scale` (`speed`/`wallOffset`) and a `sizeScale` (`size`/`frameWidth`/`frameHeight`, defaults to `scale`) — same size/speed split as `Cat.js`; `wallOffset` deliberately stays tied to `scale`, not `sizeScale`, since it's a board-margin concept (how close to the canvas edge is allowed), not a function of how big the dog looks. **Wall/furniture containment (`tryMove()`'s own copy of the check, and `GameScreen.tryMoveDog()`'s matching copy for the player-controlled path) is strict containment** (`proposedX >= WALL_OFFSET && proposedX <= canvasWidth - WALL_OFFSET - frameWidth`, and the same for Y) — not the cat/mouse clamps' old "position can dip below `WALL_OFFSET` by up to `size`" convention, which assumed `size` exceeded the entity's true visual footprint enough that the allowance would never actually push the visible sprite past the edge. The dog's `frameWidth`/`frameHeight` (60/38 × `sizeScale`) are *larger* than `WALL_OFFSET` (40 × `scale`) at any scale, so the same permissive formula let the dog's sprite hang off the canvas edge entirely — confirmed live as "run off screen and the dog is gone," and only actually fixed once the near-edge bound was made just as strict as the far-edge one (a first attempt fixed only the far bound, using the correct `frameWidth` but the old permissive shape, and the dog could still vanish off the *other* edge). The cat's own wall clamp has since been switched to this same strict shape too — see "Hitbox tightening" below — once the *same* underlying assumption (`size` bigger than the real sprite) stopped holding for the cat as well. `dog_medium.png`'s 6x6 grid is entirely leftward-facing frames (confirmed by slicing the sheet into individual cells and inspecting the pixels — head/nose on the left, tail trailing right, in every populated cell; each column is a different gait/pose, not a different direction), so there's no right-facing source art; `facingLeft` (set on an actual left/right move, both in `Dog.update()`'s autonomous branch and `GameScreen.tryMoveDog()`) starts `true` and `draw()` mirrors the sprite via a canvas transform only when it's `false` (i.e. only when actually facing right, since that's the direction with no native art). Easy to get backwards without checking the actual pixels — an initial pass assumed the art faced right and flipped on the wrong branch, which looked like the dog always facing the opposite of its travel direction. Vertical-only movement leaves `facingLeft` unchanged — the sprite keeps whichever way it last actually faced, since there's no dedicated up/down art either.

  **`dog_v2.png` — a redrawn, "Disneyfied" walk-cycle sheet, replacing the original `dog_medium.png` art.** Same follow-up request as the cat's own v2 redraw (see `cat_v2.png` above): same husky identity (white/light-gray fur, black saddle patch over the back and head, black-tipped ears, black nose, bushy tail) redrawn in the same glossier Disney-style cartoon look, now wearing a purple ballerina tutu. Unlike `dog_medium.png` (a 6x6 grid where only column index 1 was ever actually read — see `this.column` above — the other 35 cells were dead weight the game never drew), `dog_v2.png` is a single column of 6 frames matching exactly what the game uses, generated directly as a walk-cycle strip rather than a full grid.
  - **Getting genuine per-frame pose variation took three rounds, not one — worth knowing if another character ever gets this treatment.** First attempt (a direct 6-frame "sprite sheet" request, styled after the cat's successful single-shot approach) came back with all 6 frames reading as the same running-leap pose repeated with only tiny leg-angle noise — no real gait cycle, confirmed by inspection (the whole point of 6 frames is 6 different poses). A second attempt, adding an explicit 6-phase gallop-cycle breakdown (gathered → extending → full stride → airborne/suspended → landing → gathering back in) to the prompt, **still** came back nearly pose-identical — explicit phase descriptions didn't fix it, suggesting the model converges on one "hero pose" per stacked-sheet generation regardless of how the phases are worded, not a wording problem. **Fix: lower the ambition, not fight the model.** Scaled back from a dramatic bounding gallop (with an airborne suspension extreme) to an ordinary walk cycle including an explicit standing/idle frame — a walk has much smaller pose deltas between frames to begin with, which turned out to be exactly what let the model actually vary them: the third attempt produced 6 genuinely distinct leg positions (measured content-bbox width per frame ranged 378-419px out of a shared crop, versus the earlier attempts' near-constant width), confirmed by direct inspection before wiring anything in.
  - **Processing** (one-off Python/PIL script, same pattern as `cat_v2.png`'s): verified real RGBA alpha (not the flat-opaque-RGB failure a few other assets this project hit) and clean edges (no near-zero fringe) before cropping. Used a **uniform crop box across all 6 frames** (297-730px x-range, full 256px band height) — i.e. the union of each frame's own content bbox plus a small margin, not a per-frame-tightest crop — specifically because the walk cycle's legitimate width variation (legs extended wider mid-stride) needs to stay anchored to the same reference frame across rows, or the character would visibly jitter left/right between frames on top of the intended leg motion. Resized to fit the target width (60px, matching `Dog.js`'s existing `nativeFrameWidth`) via Lanczos resampling, then pasted onto a transparent 60×38 canvas **bottom-anchored** (extra space from the aspect-ratio mismatch goes on top, not split evenly) — a walking character's feet should sit at a consistent height across every frame so the walk cycle doesn't bob up and down as a side effect of cropping, matching how a real ground-contact sprite sheet is normally laid out. Frame geometry (60×38, 6 frames) was kept identical to v1's own per-cell dimensions on purpose, so `Dog.js`'s `nativeFrameWidth`/`nativeFrameHeight` didn't need to change — only `this.column` (now `0`, since there's only one column to read instead of v1's column index `1`).
  - **A real bug slipped through the first two rounds of "fixing" this: 3 frames had tiny disconnected stray pixels baked into the file, misread at first as a live rendering/GPU-bleed bug.** Reported live as "you can see the pixels of the dog's paws from another frame above the dog" — confirmed genuinely visible in a screenshot, small gray fragments floating above the back with no connection to the dog's silhouette. Two rounds of *code*-side fixes were tried first and didn't help, because the bug wasn't in the code: (1) rebuilding the PNG with a bigger transparent margin per frame, (2) `ctx.imageSmoothingEnabled = false` in `Dog.js`'s `draw()` (and `Cat.js`'s, on the same theory) to rule out cross-texel bilinear bleed at large display scale. Both were reasonable hypotheses — the source image genuinely has zero blank separator rows between poses (confirmed by scanning for fully-transparent rows across the whole 1536px-tall raw generation: only the top/bottom 7-8px of the *entire* image were blank, nothing between poses) — but neither was the actual defect. **Root cause, found via `scipy.ndimage.label()` connected-component analysis on the actual shipped file**: frames 1 and 2 each had 3 isolated 2-4px islands of opaque pixels, plus a 1px speck in frame 4, none touching the main dog silhouette — a sliver of an adjacent pose's paw/ear apparently landed inside this frame's row-band at an x-position where *this* frame's own body isn't present, so it never merged into the main connected component and was never caught by the earlier "does this band have any opaque content" bbox checks (which can't distinguish one blob from several). Verifying this took building an isolated offscreen-canvas test (flat magenta background, exact per-pixel scan outside the real `dog.draw()` destination rect, including the cutscene's own pop-in transform) that came back clean — proving the *code path* was already correct and the defect had to be in the asset's own pixels, which the connected-component scan then found directly. **Fixed by stripping every connected component except the largest per frame** (`ndimage.label` + zero out anything that isn't the biggest island) — reduced every frame from up to 4 components down to exactly 1, confirmed by re-running the same analysis and by live in-browser re-verification across the natural animation cycle.
  - **Verified live** (character-select portrait, all three cutscenes including the dog's own pop-in animation, natural walk-cycle animation through all 6 frames): clean silhouette in every frame, no stray fragments, `node --check` syntax pass on every changed file.
  - Same "deprecate, don't delete" precedent as every other asset swap this project has done: `assets/dog_medium.png` (v1) stays on disk, unreferenced, rather than being removed, in case of a rollback. `Dog.js`'s `this.spriteSheet.src` and `CharacterSelectScreen.js`'s `PORTRAITS.dog.src` both point at `dog_v2.png` now (both cache-busted with a `?v=` query string, bumped each time the file or the importing module's *code* changes — see "Module-level cache-busting" below for why the image URL alone wasn't enough).
  - **Resolution redo — both sheets rebuilt at native (not upscaled/downscaled-from-tiny) resolution once the source images were re-supplied.** The original v2 builds above were cropped down to the *legacy* v1 pixel dimensions (60×38 dog, 118×150 cat), so any real on-screen display was an *upscale* from very little source detail — reported live as visibly softer/blockier than the source renders, "nowhere near" the source quality (also true of `Furniture.js`'s kitchen renders before its own fix, see below). Rebuilt both at their actual native crop resolution instead — dog 473×296, cat 256×296 (roughly 8x more linear resolution than before) — with **no resize/resampling step at all**, just a direct 1:1 pixel paste from the source crop, so zero interpolation quality loss going in.
    - **This required decoupling "pixel dimensions used to slice the source rect" from "the logical unit on-screen size is computed from," in both `Cat.js` and `Dog.js`** — previously one pair of numbers (`frameWidth`/`frameHeight` in `Cat.js`, `nativeFrameWidth`/`nativeFrameHeight` in `Dog.js`) served both roles, which only worked because v1's art happened to already be built at the logical display size. `Dog.js` now has a local `BASE_FRAME_WIDTH`/`BASE_FRAME_HEIGHT` (60/38, unchanged) driving `this.frameWidth`/`frameHeight` (on-screen size + collision box, untouched by the resolution bump), while `this.nativeFrameWidth`/`nativeFrameHeight` (now 473/296) are used only for source-rect slicing in `draw()`. `Cat.js` mirrors this with `this.baseFrameWidth`/`baseFrameHeight` (118/150, driving `displayWidth`/`displayHeight` via the existing `/4` divisor) versus `this.frameWidth`/`frameHeight` (now 256/296, native slicing only). Reusing the *native* size for on-screen display directly (the old approach) would have rendered both characters roughly 8x too big — confirmed this didn't happen via live zoomed screenshots at character-select, cutscene, and gameplay scale, all showing correct proportions and a visibly crisper sprite than before.
    - **`ctx.imageSmoothingEnabled = false` removed from both `Cat.js` and `Dog.js`'s `draw()`** — that was always a workaround for the *previous* round's bleed bug, not a real fix (the actual defect turned out to be baked-in stray pixels, see below), and at the new, much higher native resolution, every real on-screen draw is now a *downscale*, where nearest-neighbor sampling looks aliased/gritty instead of crisp — the exact same lesson `Furniture.js` had already learned. Left at the canvas default (smoothing on) in both.
    - **Safe margin this time added via padding, not cropping wider than the source band** — the same "no blank separator rows between poses" constraint from the first build still applies (re-confirmed on the re-supplied source images, byte-identical to the originals), so vertical margin can only safely come from pasting the *exact*, un-widened band crop onto a taller blank transparent canvas; only horizontal margin can be widened by cropping further left/right (safe, since that never crosses into a different frame's row).
    - **Even with careful margin-via-padding, both sheets still needed a real pixel-cleanup pass — margin size was never actually the fix.** A first pass reused the earlier session's "strip every connected component except the largest" cleanup (`scipy.ndimage.label`, alpha>128 threshold) and looked clean at a glance, but a closer inspection at 6x still showed faint marks — the threshold was too high to catch **dozens of very faint (alpha 5-50) sub-threshold stray fragments per dog frame**, invisible at a glance but real on inspection; re-run at alpha>3, all were caught and removed cleanly (verified: exactly 1 connected component per frame at alpha>3 afterward). The cat sheet exposed a *different*, harder case: a floating pink "ballet shoe" pair above the head in 3 frames that connected-component analysis reported as **genuinely part of the same single connected blob** as the head (not caught by any threshold, including alpha>3) — visualizing the raw alpha mask directly showed why: a real (if very thin and easy to miss by eye) pixel bridge connects them. A first attempt at forcing them apart via morphological erosion+dilation worked for the cat but was **far too aggressive on the dog**, clipping legitimate whisker/ear-tip/tail-tip detail across *every* frame including previously-clean ones (visually confirmed, reverted immediately). **Final approach, used only on the 3 affected cat frames**: per-row pixel-count profiling found a genuine local minimum ("neck") in each affected frame between the floating shoe-pair and the legitimate hair tuft below it, confirmed by comparing against clean frames' own (much shorter) narrow-region length — a precise, manually-verified single-row cutoff per frame, erasing only the rows above that neck. Confirmed via a final full re-verification pass (both sheets, all 12 frames, `ndimage.label` at alpha>3): exactly 1 component every time.

**Module-level cache-busting** (`GameScreen.js`'s `import Cat from '../Cat.js?v=3'` / `import Dog from '../Dog.js?v=3'`): a query string on an ES module *import specifier* forces the browser to treat it as a distinct module URL, bypassing any cached copy of the un-versioned URL — same idea as the `?v=` on the image `src` values above, just one level up the chain. Added after cache-busting the *image* URLs alone wasn't sufficient to resolve a live "still seeing the old bug" report: a stale cached `Dog.js` (not just a stale `dog_v2.png`) reproduces the exact same symptoms, since the module holding the fix (`imageSmoothingEnabled`, the wander-guard below) never gets a chance to run. **The version number has to be bumped by hand on every edit to the file** — a real gap hit mid-session, where `Dog.js` was edited again (the wander-fix below) without bumping its already-set `?v=2`, silently reintroducing the exact caching risk the first bump was meant to close. No automated safeguard against forgetting this again; if this file gets touched further, bump the query string.

  **Dog speed & movement history.** Originally `this.speed` (20 × `scale`) served *both* the autonomous wander (a hop once every `moveInterval` = 2000ms) *and* — via `GameScreen.tryMoveDog()` reading `this.dog.speed` directly — the player-controlled Dog-mode per-tick move, which meant the two could never be tuned independently: "the dog is too fast when playing as it, and too slow when playing as the others" was one field trying to serve two incompatible roles, not two separate bugs. That retuning went through two real mistakes worth knowing about if this ever needs adjusting again: (1) the once-every-2-seconds hop cadence itself read as "freezing then teleporting" no matter how far a single hop went, fixed by switching to the same continuous per-tick wander `wanderCat()` already uses (see above) — but (2) once movement was continuous, a first pass picked `this.speed` by eye in the same numeric range as `Cat`'s own per-tick speed (8 × `scale`), which was wrong by nearly 50x: going from "once every 2 seconds" to "every tick" (~60/sec) is itself roughly a 120x multiplier, so *any* per-tick value in a player-speed-like range was always going to feel wildly faster than the dog used to be, regardless of which one — confirmed live as "wayyyy too fast." **That bigger-character pass immediately surfaced two real, previously-invisible bugs, both confirmed live and fixed in the same round.** (1) **`CutsceneManager.playCutscene()` never stopped the *previous* cutscene's own self-scheduling `requestAnimationFrame` loop before starting a new one** — every loop just kept checking the same shared `this.isPlaying` flag, which only goes `false` once *all* cutscenes finish (`endCutscenes()`), not when advancing between them. By the 3rd (dog) cutscene, three separate loops were all clearing+redrawing the canvas every frame — confirmed by instrumenting `ctx.clearRect` directly (~3 calls/frame, not 1) — each painting a *different* cutscene's card/character in whatever order the browser happened to fire their independent callbacks. Invisible at the old, much smaller character size (the overlapping draws mostly agreed on the shared card/background, and a tiny sprite doubling was easy to miss) but reported live as the mouse "kind of bugging out" and the dog's ears looking cropped/duplicated once cutscene characters got much bigger. Fixed by tracking the active loop's handle (`this.animationFrameId`) and calling `cancelAnimationFrame()` on it before `playCutscene()` starts a new one (also cancelled in `endCutscenes()` for symmetry) — guarantees exactly one loop is ever active. (2) **`render()`'s `this.characterAnimation.update()` call (no arguments, meant to be animation-only — see the point above) was never actually safe for `Mouse`.** `Cat.update()` is animation-only by definition and `Dog.update()` bails to animation-only when its `timestamp` param is `undefined`, but `Mouse.update()` has no such guard: it unconditionally moves `this.x`/`this.y` by `speedX`/`speedY` and bounces off *canvas*-sized walls every call. That went unnoticed while `characterAnimation.x`/`y` were only set once (the old `init()`), but the sizing rework above now overwrites them every frame to a small, pre-scale-transform local origin near the canvas's own coordinate-space zero — wildly "past" `Mouse`'s real `canvasWidth`/`canvasHeight` bounds, so `Mouse.update()` read that as hitting a wall on *every single frame*, flipping direction/frame constantly. Fixed with `Cutscene.advanceAnimationOnly()`, a small helper that calls each class's own frame-only method directly instead of routing through `update()` — duck-typed since `Cat`/`Mouse` name theirs `updateAnimations()` and `Dog` names its `updateAnimation()` — so cutscenes can never trigger movement/AI logic regardless of what a given class's `update()` happens to do when called with no arguments. Side effect, not a bug: the cutscene mouse now holds a single fixed pose (whatever `currentDirection`'s constructor default, `'south'`, looks like) instead of whatever direction its accidental movement last happened to face.

Both were constrained by `CharacterSelectScreen`'s `BASE_CARD_GAP` (only 30px at `BASE_CARD_WIDTH`'s 240) — a first pass at the teardrop's bulge width (0.26 × card width) was never actually checked against that gap and peaked around 59px, nearly double the available space, which would have badly overlapped the neighboring card; caught only by computing the curve's real peak numerically (a quadratic Bézier's rendered extent isn't the same as its control point's raw offset) after the fact, not by eye. Both versions were ultimately rejected anyway — "hard to tell they are ears" — since a shape stuck onto the *side* of a rectangle doesn't read as "attached to a head" the way something poking up from the *top* does, no matter how the bulge itself is shaped.
  3. **Current: back to poking up from the top edge** (same convention as cat/mouse, and — since it doesn't extend past the card's own left/right edges — no `BASE_CARD_GAP` collision risk to re-litigate), but built from a `dogEarFlopCurve()` helper: a single cubic Bézier per ear (not the cat/mouse's quadratic) whose two independently-weighted control points let one side of the curve rise steeply (the ear's *inner*/attachment-facing side) while the other droops low (the *outer*/corner-facing side) within the same curve — a genuine asymmetric "flop," which a quadratic's single, symmetric control point can't produce. `peakNearStart` (a boolean) exists because the boundary path traverses the left ear outer→inner but the right ear inner→outer, so "which endpoint is the inner/rise side" flips between the two; shared by both the full outer ear and the smaller inset `drawDogEarInner` accent so their curves can't drift apart. **The nominal `peakHeight` parameter is not the curve's actual rendered peak** — a cubic Bézier pulled by two control points falls well short of either one's raw offset, confirmed only by simulating the curve numerically (sampling `t` from 0 to 1) rather than assuming: an initial value (`height * 0.22`) rendered to an actual peak of just ~29px, reading as a timid nub next to the cat/mouse ears' own ~52px presence; retuned to `height * 0.4`, which actually renders to ~51px — matching the cat ear's height while staying safely under `BASE_TITLE_GAP` (70). Even with this fix, the shape is a smooth single rise-then-droop, not a true two-stage fold (a real fold needs a local *minimum* between two rises, which turned out hard to engineer reliably via curve math alone without live visual feedback) — flagged as the best reasoned attempt at ship time, not a guaranteed-final shape.
- `audio.js` — two independent module-level mute flags (not per-screen state, so they survive "Play Again" and persist for the session): `isMusicMuted()`/`setMusicMuted()`/`toggleMusicMuted()` (starts `true`) and `isSfxMuted()`/`setSfxMuted()`/`toggleSfxMuted()` (starts `false`) — see Settings menu & audio below for why the two default differently. Each setter fires its own `document` event (`musicmutechange`/`sfxmutechange`) so anything with an already-playing looping sound (background music) can react immediately, not just future `playSound()` calls. Also exports the game's synthesized one-shot SFX (`playModalPopSound()`, `playWinSound()`/`playLoseSound()`, `playPlantKnockOverSound()` — see Plant knock-over reaction above), all gated on `isSfxMuted()` and all called directly by their own trigger sites rather than through `GameScreen.playSound()`, which only knows the file-backed `SOUND_KEYS` map.
- `settingsMenu.js` — wires up the in-game hamburger menu (`#settingsMenu` in `index.html`) — see Settings menu & audio below.

## Floor background (`GameScreen.drawFloor`)
`render()` fills the whole canvas with a repeating two-tone tile pattern before drawing anything else. **This is canvas-drawn, not CSS** — `styles.css` only styles chrome outside the canvas — the orientation gate, touch controls, and viewport frame (see Mobile responsiveness and Viewport frame & mouse-escape danger indicator below) — nothing about the board itself; the floor is generated on an offscreen canvas at draw time (`drawFloor()`, cached on `this.floorPattern` via `ctx.createPattern(..., 'repeat')`) rather than loaded from an image, so there's no async load to wait on. Currently a small 24px flat white/off-white two-tone tile look (`COLORS.FLOOR_LIGHT` `#ffffff`/`FLOOR_DARK` `#f9f8f4`, a subtle near-white rather than a strongly-toned off-white/`FLOOR_GROUT`), sized like a fine modern kitchen floor tile relative to the furniture. Colors are deliberately **plain and neutral, not matched to the `kitchen_*.webp` furniture's warm cream/tan/honey-oak palette** — two earlier versions of this floor (96px then 48px tiles, both in warm tones pulled from/complementary to the furniture, the first also with marble-vein texture) were each tried and rejected live for blending into the furniture instead of reading as floor beneath it; white/off-white reads as a distinct surface regardless of what furniture palette sits on top. This replaced (in order, largest tile to smallest) a 96px warm-toned veined tile → a 48px warm gray/taupe tile → a 40px warm cream/peach checker → an even earlier photographic floor crop cut from the same AI-generated kitchen photo the furniture used to be cropped from — see Kitchen furniture below for the furniture's parallel art-direction history.

## Wall band & mouse holes (`GameScreen.drawWalls`, `Escape.js`)
`render()` draws `drawWalls()` right after `drawFloor()` and before the escapes/mouse/furniture — a `WALL_BAND_THICKNESS` (16px) band flush against all four canvas edges, filled with `COLORS.WALL_FILL` and outlined with two `COLORS.WALL_TRIM` strokes (one at the canvas edge, one where the band meets the floor) so it reads as wall *thickness* rather than a flat painted stripe. This exists purely for presentation — it's unrelated to `WALL_OFFSET` (40px, used by `moveCat()` to clamp how close the cat can get to the edge) and to the old `WALL_THICKNESS`/`COLORS.WALL`/`drawWallBorders()` it replaced, which drew a single flat-color rect at `WALL_OFFSET` and was dead code (defined but never called from `render()`) before this change.

Furniture's *back* (the edge facing the wall) is aligned flush against the wall band's *front* face — `WALL_BAND_THICKNESS` in from the canvas edge, not the raw edge itself — on all four walls (see Kitchen furniture point 3 below); this was a deliberate fix after an earlier version of this feature placed furniture flush to the raw canvas edge, which meant furniture completely painted over the entire wall band (including its inner border line) wherever it existed, while non-furniture areas showed the full band — an inconsistent "sometimes there's a wall margin, sometimes there isn't" look. With back-alignment, the band's inner border is always visible as a consistent thin reveal around furniture everywhere, not just where furniture happens to be absent — corners, the gaps beside a centered wall run, the open stretch of left/right wall above/below the two-cabinet run, and — the reason this was added in the first place — the mouse-hole gap `generateKitchenFurniture()` already leaves in one wall's tile run (`this.wallGap`). Before any of this, `Escape` rendered as a flat black square floating on bare floor with nothing to be a hole *in*; now it has a wall band to sit inside, so it reads as an actual opening.

`Escape.draw()` was changed to match: instead of a filled rectangle, it draws a small rounded-arch cutout (flat bottom, domed top — the classic cartoon mouse-hole silhouette) filled with a black-to-dark-brown radial gradient and a faint highlight stroke, for a sense of depth rather than a flat color. The base shape assumes it's sitting in a horizontal wall with the opening facing down (correct for the top wall as-is); `Escape` now takes a `wall` param (`'top'`/`'bottom'`/`'left'`/`'right'`, defaulting to `'top'`) and rotates the whole shape around its own center (0°/180°/270°/90° respectively) so the opening always faces into the room regardless of which wall it's on. `GameScreen.generateEscapes()` passes this through for every escape it creates, both the guaranteed `wallGap` one (using `gap.wall`, already `'top'`/`'bottom'`) and the `count - 1` randomly-placed ones (mapped from the existing `0-3` wall index). Collision (`isMouseInside`) is untouched — still a plain AABB rect using `this.width`/`this.height`, since the visual rotation doesn't change the (square) bounding box.

**Art direction history (read this before touching kitchen art):**
1. **Crops from one whole AI-generated scene** (`kitchen_reference_scene.jpg`, still in git history) — individually-cropped appliances reassembled with computed offsets (cut edges didn't align to real object boundaries), then one whole strip per wall (fixed alignment, but a strip can never have a gap, so a mouse hole was always hidden behind solid furniture), then natural-seam tiles per wall (restored the gap, kept the alignment). All of this iteration was solving alignment problems *within* a photorealistic-scene style — but stepping back further, a photorealistic scene never matched `cat.png`/`dog_medium.png` (a bold flat-color cartoon mascot and a simple side-view pixel sprite, respectively — neither photorealistic, neither strict top-down) in the first place.
2. **PtPt's free flat-cartoon "Cute Pixel Cooking" pack** — genuinely modular sprites with real dimensional depth (Overcooked/Stardew-style), chosen specifically to match the mascot-style characters. But once the user saw it in place, the actual ask turned out to be different: "I want the game board kitchen to look **as realistic as possible**" — the user is a game engineer building this for his daughter and explicitly did not want to "vibe code" the art, so flat cartoon shading wasn't going to satisfy that regardless of how well it matched the layout.
3. **Individually-generated photorealistic objects** (`assets/realistic_*.png`, since removed) — reused the modular wall-building/gap mechanism from the PtPt round with photorealistic renders instead. **Rejected after being reviewed live.** Verbatim user feedback: "the images are way too big and out of scale with the characters. The 3/4 tilt doesn't work in this view as the kitchen board isnt. The counters dont conect to eah other. the images look realistic, but the scene/board doesnt." Concretely: the renders were scaled to fit the wall/interior geometry rather than to match character proportions; each render baked in its own 3/4 camera angle that clashed with the flat top-down board (a risk flagged and accepted before building, but one that reads as obviously wrong once the art is photorealistic, unlike with flat cartoon shading); and each render was a fully-modeled freestanding object rather than a slice of built-in cabinetry, so edge-to-edge placement showed a seam between boxes instead of one continuous countertop run. Net effect: individual images looked realistic in isolation but the composed board didn't read as a believable kitchen. **This is why the current round doesn't reuse that round's approach uncritically** — the scale (`MODULE_SCALE`) was deliberately dropped, and dimensions were re-read from scratch rather than reused.

## Plant knock-over reaction (`Furniture.startKnockOver`, `GameScreen.updatePlantBump`, `playPlantKnockOverSound`)
The plant's "bump" reaction planned for after its initial placement-only ship (see Kitchen furniture point 8 above): the cat or dog running into the plant tips it over with a short animated fall and a synthesized thump/scatter sound, replayable every time either one touches it — not a one-shot "knocked over forever" flag.

- **`Furniture.startKnockOver(timestamp)`** always (re)starts the fall from upright, even mid-animation or already-settled — deliberately *not* a one-shot toggle. `draw()` computes the current tilt from `performance.now() - this.knockStartTime` (an ease-out cubic from 0 to `KNOCK_OVER_ANGLE`, 75° — not a full 90°, since a plant landing perfectly flat reads as a broken transform snapping to an exact right angle, while stopping short of that reads as actually toppling and settling against the floor/its own pot), added on top of the piece's own base `rotation` so it stays additive and doesn't interfere with a wall-module's own rotation if this were ever reused on one of those. Because a fresh `startKnockOver()` call resets `knockStartTime`, bumping an already-tipped plant again visibly resets the animation from upright and replays the tip — a little "wobble" each time, not a static fallen prop.
- **`GameScreen.updatePlantBump()`** is a read-only overlap check (closer to `isHiddenByFurniture()`'s style than `Furniture.isColliding()`'s blocking one — the plant is in both `CAT_NON_BLOCKING_FURNITURE_TYPES` and `DOG_NON_BLOCKING_FURNITURE_TYPES`, see Kitchen furniture point 8, so this is a separate check entirely from movement collision) against the cat's and dog's full display boxes, run every tick regardless of `controlledEntity`. **Edge-triggered on `this.plantWasHit`, not fired on every tick of continuous overlap** — since `startKnockOver()` is replayable by design, without edge-detection here, simply standing on top of the plant for a few frames would restart the animation/sound every single tick and read as a stutter/buzz instead of one clean bump per approach. `plantWasHit` is reset to `false` in the constructor alongside `mouseEscaped` and the other per-round state, so a fresh "Play Again" round starts clean.
- **`playPlantKnockOverSound()`** (`js/utils/audio.js`) is synthesized like the game's other one-shot UI/event sounds (`playModalPopSound()`, `playWinSound()`/`playLoseSound()`) rather than a supplied file, since nothing in `sounds/` is a plant-pot thud: a low pitch-dropping sine "thud" (150Hz→55Hz over 0.18s) layered *simultaneously* with a brief high-passed noise burst (0.22s, for scattering dirt/leaves) rather than sequenced, since a real impact and its scatter happen at the same instant. Called directly from `updatePlantBump()` alongside `startKnockOver()`, not routed through `GameScreen.playSound()` (which only knows the file-backed `SOUND_KEYS` map) — mirrors how `playModalPopSound()` is already called directly by its own trigger sites rather than going through that map.

### Cart bump sound (`GameScreen.updateCartBump`, `sounds/cart_bump.mp3`)
Added on request ("add a sound for when the cat runs into the cart") — sound only at the time, no visual reaction, unlike the plant (the cart doesn't tip over, the cat just ducks under/past it — see `drawCatUnderFurnitureEffect()` above for that existing visual). A visual reaction was added in a later pass — see "Furniture shake reaction" below.

**Went through three synthesized attempts (square-wave knock + noise burst; oscillator "clink" cluster; bandpass-noise "rustle" cluster), each reworked live, none of them landing** — the last was reported as "still awful" after three tries. Rather than guess a fourth time, the project owner sourced a real recording (an AI-generated sound-effect prompt, refined once for duration) and supplied the file directly, matching how every *other* sound in this game already works. `sounds/cart_bump.mp3` (renamed from the tool's default export filename) is now loaded like `WALL_HIT`/`CAT_CATCH`/etc. via `SOUND_KEYS.CART_BUMP`/`loadSounds()` — the synthesized `playCartBumpSound()`/`playRustleClick()` in `js/utils/audio.js` were deleted as dead code once the file replaced them, not kept around unused.

**Not a fire-and-forget one-shot like the game's other SFX, though — a second request changed the playback model entirely: "it should only play for the duration of the cat being 'on' the shelf or in the hit zone... only advance sound if the cat is moving while inside the hit zone."** `updateCartBump()` drives the loaded `Audio` element's own `play()`/`pause()`/`currentTime` directly each tick instead of calling `GameScreen.playSound()` (which just restarts a clip from 0 and lets it run) — three states:
- **In the hit zone and moving** → playing, resumed from wherever it was if already paused (not restarted), so a brief stop-and-go while still in the zone doesn't keep jumping back to the start.
- **In the hit zone but not moving** → paused in place, not reset — holds its exact position, picks back up the instant movement resumes.
- **Out of the hit zone entirely** → paused *and* reset to 0, so the next approach starts the clip fresh rather than resuming mid-clip from an unrelated earlier one.

"Moving" here is `this.catMovedThisTick` (`GameScreen.js`), a new flag reset at the top of `update()` and set (OR'd, not overwritten — `updateCatAI()`'s `moveCatTowardMouse()` can fall back to `wanderCat()` within the same tick if the direct approach is blocked, so `tryMoveCat()` can run more than once per tick) from inside `tryMoveCat()` itself — deliberately not "is a direction key held," since a cat pressed into a wall/furniture with nowhere to go isn't actually moving even with input held, and the AI-driven cat (Mouse/Dog mode) has no "key held" concept to read in the first place; `tryMoveCat()`'s own return value is the one signal both control modes share. Confirmed live (forcing ticks directly against the loaded `Audio` element, with real `await`ed delays since pause state only means anything against wall-clock time): entering the zone while moving starts playback; stopping while still inside pauses without resetting (`currentTime` genuinely holds — confirmed it doesn't creep forward while "paused" over a real 300ms wait); resuming continues from that exact point, not from 0; leaving the zone entirely resets to 0.

### Shelf bump sound (`GameScreen.updateShelfBump`, `sounds/shelf_bump.wav`)
Added the same request-cycle as the cart's own bump sound above, once the shelf itself was made passable for the cat (see Kitchen furniture point 10). Skipped synthesis entirely — the cart's three rejected synthesized attempts (see above) already established that guessing at this particular kind of sound doesn't land, so the project owner sourced a real recording (from an AI-generated sound-effect prompt) on the first request rather than after a round of live-rejected placeholders. `sounds/shelf_bump.wav` (renamed from the tool's default export filename) is loaded via `SOUND_KEYS.SHELF_BUMP`/`loadSounds()`, same as `CART_BUMP`.

**Unlike the cart, this one is a plain fire-and-forget one-shot, not the cart's continuously-driven play/pause/currentTime model** — first shipped mirroring `updateCartBump()`'s three-state approach exactly, then simplified on request ("let's just play the full sound once on entry"): the cart's duration-tracking model was tuned for that piece's own feel, not a requirement every bump sound in this game has to follow. `updateShelfBump()` now matches `updatePlantBump()`'s shape instead — edge-triggered on `this.shelfWasHit` (reset to `false` in the constructor alongside `plantWasHit`/`mouseEscaped`) so a bump plays once per approach rather than every tick of continuous overlap, calling `playSound(SOUND_KEYS.SHELF_BUMP)` (which resets `currentTime` to 0 and plays) rather than driving the `Audio` element's `play()`/`pause()`/`currentTime` directly. Cat-only, same reasoning as the cart's own sound — the shelf blocks the dog outright (not in `DOG_NON_BLOCKING_FURNITURE_TYPES`), so there's nothing for the dog side to react to.

### Furniture shake reaction (`Furniture.startShake`, `updateTableBump`/`updateCartBump`/`updateShelfBump`)
Table joined `CAT_NON_BLOCKING_FURNITURE_TYPES` on request ("make the table passable for the cat with a shake animation") — same cat-only split as cart/shelf (not added to `DOG_NON_BLOCKING_FURNITURE_TYPES`, so the dog still collides with it normally), and gets the same generic under-furniture silhouette treatment `drawCatUnderFurnitureEffect()`/`drawCatSilhouette()` already give plant/cart/shelf for free, since both are driven off that one shared list rather than any per-type code.

**A dedicated shake reaction, not the plant's knock-over** — a dining table (four chairs, a full place setting baked into the sprite, see Kitchen furniture point 6) tipping over the way a small potted plant does would read as broken, not charming, so this needed its own animation rather than reusing `startKnockOver()`. `Furniture.startShake(timestamp)`/`this.shaking`/`this.shakeStartTime` mirror `startKnockOver()`'s own shape (replayable, not a one-shot — every fresh bump restarts the wobble from the beginning) but `draw()` computes a small decaying sine oscillation (`SHAKE_DURATION` 400ms, `SHAKE_MAX_ANGLE` 5°, `SHAKE_CYCLES` 3 back-and-forth swings, linear decay envelope) instead of an ease-out fall to a fixed tipped angle — added to the piece's own base `rotation` the same additive way `knockOverRotation` already is, so it composes cleanly with either a freestanding piece's `rotation: 0` or (hypothetically) a rotated wall module. Confirmed live: the table visibly rattles side-to-side and settles back to perfectly flat by the end of the animation, not left mid-wobble.

`GameScreen.updateTableBump()` is `updateShelfBump()`'s counterpart — cat-only, edge-triggered on `this.tableWasHit` (reset in the constructor alongside `plantWasHit`/`shelfWasHit`) — but calls `table.startShake(timestamp)` in addition to `playSound(SOUND_KEYS.TABLE_SHAKE)`, since a bump sound with no visible response would feel disconnected from something this size sitting in the middle of the room. Called from `update()` alongside `updatePlantBump()`/`updateCartBump()`/`updateShelfBump()`.

**`SOUND_KEYS.TABLE_SHAKE`/`sounds/table_shake.mp3` were wired (`SOUND_KEYS` entry + `loadSounds()`, same pattern as every other bump sound) before the actual recording was supplied**, confirming a real, previously-unhit gap along the way: a missing/unsupported source made `playSound()` throw *synchronously* (`sound.currentTime = 0` itself throws, not just `sound.play()`'s promise — confirmed live, an `EXCEPTION` in the console) rather than failing silently the way a normal "sound didn't play" gap would. `playSound()` now wraps the `currentTime`/`play()` pair in a `try`/`catch`, kept as a general safeguard rather than removed once the file arrived — the next sound wired ahead of its recording will hit the same gap. The recording itself took two rounds of prompting to land: a first attempt ("table shake" with a "wood creak" cue in the prompt) came back sounding like a creaky door opening, not dishware — the "wood creak" language was almost certainly what steered it there. Fixed by dropping that entirely and leading hard with the actual target sound instead: ceramic/metal/glass dishware clinking and rattling together, explicitly ruling out wood creak/door/crash/breaking-glass in the prompt itself. `sounds/table_shake.mp3` (renamed from the tool's own default export filename, same precedent as `cart_bump.mp3`/`shelf_bump.wav`/`gotcha.mp3`) confirmed live: loads (`readyState` 4), and actually plays (`paused: false`, `currentTime` advancing) when `updateTableBump()` fires.

Confirmed live on both: the cart and shelf visibly tilt and settle the same way the table does, and no console errors from either path.

## Settings menu & audio (`js/utils/audio.js`, `js/utils/settingsMenu.js`, `index.html`, `styles.css`)
A hamburger button (`#settingsToggle`, inside `#settingsMenu`) opens a dropdown panel (`#settingsPanel`) with two independent toggles — Music and Sounds — rather than a single mute. They default differently on purpose: music starts muted (`isMusicMuted()` → `true` in `js/utils/audio.js`) since a looping track starting unprompted on page load is worse than silence, while SFX starts unmuted (`isSfxMuted()` → `false`) since punch/toot/meow/etc. are short sounds tied directly to a player's own action — muting those by default would make actions feel like they're doing nothing. `GameScreen.playSound()` (all one-shot SFX) checks `isSfxMuted()`; the looping background track's start (see "Background music persistence" below for exactly where that is) and a live `musicmutechange` listener (so toggling mid-round affects a track that's already playing, not just future calls) check `isMusicMuted()`.

### Background music persistence (`js/utils/audio.js`, `GameScreen.startGame`/`restartGame`)
The background track (`sounds/you_can.mp3`, replacing an earlier `christmas_tree_farm.mp3` — that file stays on disk, unreferenced, same deprecate-don't-delete precedent as every swapped visual asset) is a **page-lifetime singleton Audio element in `js/utils/audio.js`** (`getBackgroundMusic()`/`getBackgroundMusicElement()`), not something each `GameScreen` instance owns and recreates. This was a deliberate change from the original design, on explicit request: *"can you have the song keep playing? It should run through even after a game over. The only thing that should start it over is a refresh. Dont start it until in game though."* Three separate behaviors had to change together to get this:

- **Where it starts.** Previously started unconditionally in `GameScreen.init()` — which runs the instant a `GameScreen` is constructed, *before* intro cutscenes finish (or even play, if `skipCutscenes`). That meant music could start playing during the "meet the characters" cutscenes, before the player was actually controlling anything. Moved to `startGame()` (the point `this.running` actually flips to `true`) and, since the `skipCutscenes` branch bypasses `startGame()` entirely, its own copy of the same `startBackgroundMusic()` call. `startBackgroundMusic()` itself is a no-op if the track is already playing (`.play()` on an already-playing `HTMLAudioElement` doesn't reset `currentTime`), so calling it from both entry points — or every subsequent round — is always safe.
- **Where it no longer stops.** `restartGame()` used to explicitly `.pause()` the track before tearing down the old `GameScreen` and building a fresh `CharacterSelectScreen` → `GameScreen`, on the assumption each instance owned its own `Audio` object that would otherwise leak. Since the track is now a shared singleton with no per-instance ownership to worry about, that pause call was removed outright — the track just keeps playing straight through the "Play Again" transition instead of being paused and then immediately resumed by the next round's `startGame()`.
- **Where it's aliased.** `loadSounds()`'s `SOUND_KEYS.BACKGROUND` entry no longer calls `this.loadSound(...)` (which would construct a brand-new `Audio` object per `GameScreen`, defeating the whole point) — it aliases `getBackgroundMusicElement()` directly, so every `GameScreen` instance's `this.sounds[SOUND_KEYS.BACKGROUND]` (used by `playSound()`'s generic path and the mute-toggle listener) points at the exact same element.

Confirmed live via direct module inspection (dynamic `import()` of `audio.js` from the browser console, reading `getBackgroundMusicElement().paused`/`.currentTime` at each step) rather than by ear, since the actual requirement is about *timing and continuity*, not the audio itself: silent through setup/character-select/cutscenes even after proactively unmuting early; starts the instant real gameplay begins; stays unpaused with `currentTime` advancing continuously through a forced `endGame()`; and stays unpaused with `currentTime` still advancing (never reset toward 0) all the way through a full `restartGame()` → character-select → pick-a-character → back-in-gameplay cycle. Only an actual page refresh (a fresh module evaluation, resetting `backgroundMusic` back to `null`) starts it over, matching the explicit request.

- **Positioning differs by device, both handled without JS-vs-CSS fighting each other.** Desktop anchors to the **board itself**, via pure CSS layout rather than any JS measurement — `<main>` (see `index.html`) is `relative inline-flex` specifically so it shrink-wraps tightly around the canvas instead of spanning the full viewport width the way a plain block element would, and `#settingsMenu` is now a DOM child of `<main>` (right after the canvas), positioned with `position: absolute; top: 20px; right: -60px`. Since `<main>`'s own box edges end up exactly matching the canvas's (it shrink-wraps to that one child), `#settingsMenu` tracks wherever the board actually ends up purely through the browser's layout engine — `right: -60px` (`-(DESKTOP_BUTTON_SIZE + DESKTOP_MARGIN)`, both in `js/utils/settingsMenu.js`) puts its left edge 20px past the canvas's right edge and its own right edge 60px past, i.e. sitting just outside the board in the gutter. Being a DOM descendant of `<main>` doesn't change anything for *touch*, which stays `position: fixed` (viewport-relative, unaffected by ancestor nesting since `<main>` has no transform/filter to establish a new containing block) with its own horizontal center set by `touchControls.js`.
  - **This is the third attempt**, after two JS-measured approaches were each flagged live as still overlapping the board in some environment this project couldn't fully reproduce or diagnose: (1) centered *within the gutter* the 90%-width canvas happened to leave (matching `touchControls.js`'s gutter-center formula for `#actionButtons`) — centering a 40px button in a gutter under 40px wide necessarily puts part of it on the canvas, and a narrower (still entirely ordinary, non-mobile) desktop window's natural ~5%-of-viewport gutter can be exactly that thin; (2) a fixed distance past `canvas.getBoundingClientRect().right`, recomputed via a `layoutSettingsMenuDesktop()` function on `resize`/`orientationchange` — reported live as *still* overlapping afterward. A leading theory for (2)'s failure: `index.html`'s Tailwind CDN stylesheet loads `async` (see that script tag's own comment) specifically so it doesn't block `main.js` — but that means the canvas's flex-centered position can still shift *after* Tailwind finishes applying (e.g. `body`'s `flex`/`items-center`/`justify-center` utility classes only taking effect once the stylesheet loads), and a stylesheet finishing has no reason to fire a window `'resize'` event, so a JS measurement taken before that point would go stale with nothing to ever correct it. (3), the current version, has no JS measurement to go stale *by construction* — there's no "measure, then position" step at all, so there's nothing for a load-order race to invalidate. `resizeCanvas()` (`js/main.js`) still reserves `MIN_DESKTOP_SETTINGS_GUTTER` (`js/utils/settingsMenu.js`, 80px = button + 2×20px margin) of clearance on every side unconditionally, so the negative offset always lands somewhere visible rather than off a very narrow window's edge — verified by replicating `resizeCanvas()`'s math directly across 153 width/height combinations spanning 400–2560px × 300–1080px, and confirmed live that `<main>`'s rendered box exactly matches the canvas's own bounding rect (not just approximately).
  - **Mobile (design-director pass): no longer an independent fixed top-right corner.** That used to be computed with no awareness of where `#actionButtons` actually ended up, and once the action-button cluster grew (see Mobile responsiveness below), it visibly overlapped the punch button live on-device. Mobile positioning lives entirely in `touchControls.js`'s `layoutTouchControls()` — `settingsMenu.js` itself has no positioning logic or `isTouch()` check left in it at all (desktop is the plain CSS rule described above, with no JS involved): `#settingsMenu` shares the *exact same* horizontal center as `#actionButtons` (both set from the same computed value in the same function, so they can't drift apart), the *exact same* on-screen size and shrink-to-fit scale (`#settingsToggle` bumped to 76px to match `.action-btn`, both driven by `--action-scale`), and sits a fixed `SETTINGS_TOP_MARGIN` (20px) from the viewport's top edge rather than vertically centered — reading as its own thing above the action column, not a fourth member of it. `#actionButtons` still defaults to true vertical centering (styles.css's `top: 50%`), but `layoutTouchControls()` computes both groups' actual on-screen edges and pushes the action-button cluster down (never up) from that default whenever true centering would put it within `ICON_GROUP_GAP` (24px) of the hamburger — a no-op on any normal-height viewport, and the thing that specifically guarantees the overlap can't quietly come back on some future short viewport.
- **Opening the menu pauses gameplay.** `settingsMenu.js` dispatches a `settingsmenutoggle` event (`{open: bool}`) from every path that opens/closes the panel (the toggle click, and clicking outside to close). `GameScreen` listens for it: on open, stashes the current `this.running` into `this.wasRunningBeforeMenu` and sets `running = false`; on close, restores that stashed value instead of unconditionally resuming — so opening the menu mid-cutscene or after game-over can't accidentally kick gameplay into motion just because the menu happened to be open at the time. The same handler also calls `this.dog.pauseBarking()`/`stopDogBarkSound()` on open and `this.dog.resumeBarking()` (only if play is actually resuming, not if the menu was opened from an already-game-over screen) on close — see "Dog bark persisting past pause/game-over" below for why the dog's own bark schedule needed this and `this.running` alone wasn't enough to gate it.
- **Dog bark persisting past pause/game-over — two separate bugs, not one.** First: `Dog.js`'s `setNextBark()` runs on a raw `setTimeout` chain that was never tied to `this.running` at all, so a bark could keep firing while the settings menu sat open over a visibly paused board, or (since `playSound()` just calls `HTMLAudioElement.play()` with nothing to stop it) a bark already mid-playback could keep sounding right through `endGame()`. Fixed with `Dog.pauseBarking()`/`resumeBarking()` (a fresh random delay on resume, not a saved remainder — barks are ambient/decorative to begin with) plus `GameScreen.stopDogBarkSound()` (cuts off a clip already playing), wired into both the `settingsmenutoggle` handler above and `endGame()`.
  - **Second, the real root cause of it persisting even after that fix: `resetGameObjects()` gets called *twice* per fresh game** — once from the constructor, once again from `startGame()` once cutscenes finish — and it unconditionally did `this.dog = new Dog(...)` with no cleanup of whatever `this.dog` already was. The *first* Dog instance (the one `resetGameObjects()`'s initial call made, whose `setNextBark()` had already started) got silently orphaned the moment the second call replaced `this.dog` — nothing pointed at it anymore, so `pauseBarking()`/`cleanup()`/`endGame()` calls on the "current" `this.dog` were all operating on the *second* instance while the *first* one's bark timer kept firing forever, completely invisible to `this.running`, the settings-menu pause, or game-over. This is the same class of leaked-listener bug `ScreenManager.setScreen()`'s automatic `cleanup()` call exists to prevent (see Architecture above), just one level down — `resetGameObjects()` replaces `this.dog` the same way `setScreen()` replaces `currentScreen`, so it needed the same "clean up what you're about to replace" guard. Fixed by adding `if (this.dog) this.dog.cleanup();` to the top of `resetGameObjects()`, right alongside the identical existing guard for `this.inputHandler` on the very same line — that guard already existed for exactly this reason, just not yet extended to the dog. Caught by instrumenting (temporary `console.log`s in `setNextBark()`/`pauseBarking()`/`playSound()`, removed before shipping) and watching two full, independent `setNextBark scheduled` chains running concurrently — not something a live playtest alone would have surfaced, since both the reachable and orphaned dog render/bark identically until you're specifically listening for a *second* schedule.
- **Credits** (`#creditsBtn` inside `#settingsPanel`, `#creditsModal` in `index.html`): a small "who made this" card, deliberately styled *unlike* the plain dark `#settingsPanel` dropdown it's launched from — that one's utility chrome (toggle switches), credits is a genuine cute moment, so it reuses the cream-gradient-card-plus-purple-border-plus-cat-ears visual language this game already has for its other special moments (`Cutscene.js`'s intro cards, `CharacterSelectScreen`'s character cards) rather than inventing a fourth look. The two ear shapes (`.credits-ear` in `styles.css`) are CSS's version of `canvasShapes.js`'s `drawCatEarCard`/`drawCatEarInner` — same 16%-inset/22%-width proportions as that function's `earGeometry()`, so they land in the same place relative to the card at any width, and specifically clear `#creditsCloseBtn`'s fixed 32px corner button rather than needing a separately-tuned pixel offset that could drift into it. Text: "Created by, Imagineered by & Produced by / **Kathryn Hodges**" (the actual star billing, in a gradient-filled display treatment) then a smaller "Engineered by Daddy (Scott Prelewicz)" supporting line.
  - **Swaps for the settings panel rather than stacking on top of it.** Clicking Credits hides `#settingsPanel` and shows `#creditsModal` directly — doesn't call the shared `setOpen(false)` helper, since the game should stay paused (exactly as if the settings panel were still open) until credits itself is actually closed, not resume the instant you navigate into it. Closing (the × button, clicking the dimmed backdrop, or Escape) hides the modal and *does* call `setOpen(false)`, which is what actually resumes gameplay and resets the hamburger's `aria-expanded` state.

## Character selection & playable modes (`CharacterSelectScreen.js`, `GameScreen.js`)
Before gameplay starts, `CharacterSelectScreen` asks the player to choose Cat, Mouse, or Dog — all three enabled. The choice becomes `GameScreen`'s `controlledEntity` (`'cat'`, `'mouse'`, or `'dog'`, defaulting to `'cat'`). **"Play Again" returns to character select rather than replaying with the same `controlledEntity`** — `GameScreen.restartGame()` hands off to a fresh `CharacterSelectScreen` (the same `screenManager.setScreen()` call `SetupScreen`'s own "Start Game" button makes) instead of directly constructing another `GameScreen`, so a player can pick a different character each round rather than being locked into whatever they picked at the start of the session. **Intro cutscenes are skipped on that replay path, but not moved** — re-watching "meet the characters" every round once Play Again started routing back through character select was flagged live as unwanted, but relocating the cutscenes to play before character select (so they'd only ever show once per session) was explicitly deferred rather than done now. Threaded through as a boolean rather than restructuring the flow: `CharacterSelectScreen` takes an `isReplay` param (`restartGame()` passes `true`; `SetupScreen`'s "Start Game" click passes nothing, defaulting `false`), forwarded to the `GameScreen` it constructs as `skipCutscenes` — a deliberately different name at that boundary, since what it actually controls there is specifically the cutscenes, not "is this a replay" in some broader sense. `GameScreen.init()` branches on it: skip straight to `running = true` (the layout `resetGameObjects()` already built earlier in `init()` is used as-is) instead of `startCutscenes()` → `startGame()`'s own second `resetGameObjects()` call. Exactly one entity reads player input at a time; the cat (whenever it isn't the one being played) runs the same AI in both Mouse and Dog mode, and the mouse (whenever it isn't the one being played) runs the same passive autonomous wander in both Cat and Dog mode — everything else (collision checks, furniture, the dog-pauses-cat rule) behaves identically across all three modes.

- **Cat mode** (default, original behavior): `moveCat()` reads `InputHandler` and calls `tryMoveCat(direction)`; the mouse wanders autonomously via `Mouse.update()`; the dog wanders autonomously via `Dog.update()`, an incidental hazard to the cat.
- **Mouse mode**: `movePlayerMouse()` reads `InputHandler` directly and moves the mouse (ignoring furniture, same as autonomous mode — see `Mouse.js` above); the cat instead runs `updateCatAI()` every tick; the dog still wanders autonomously, same incidental hazard as Cat mode.
- **Dog mode**: the 8-year-old-designed one — the dog's job is to run into the cat on purpose and pause it, buying the mouse time to escape. `movePlayerDog()` reads `InputHandler` directly and calls `tryMoveDog(direction)` (same per-tick furniture/wall rules as `tryMoveCat()`, though the wall-clamp math itself is stricter — see `Dog.js` above); the cat runs the same `updateCatAI()` as Mouse mode (it has to actually be chasing the mouse for "pause it" to mean anything); the mouse wanders autonomously, same as Cat mode. `updateDog(timestamp)` is what switches between this and the normal autonomous `Dog.update()` path based on `controlledEntity`. The dog-pauses-cat collision check (`handleDogCollisionIfReady()`, unchanged from Cat/Mouse mode) still runs every tick — playing as the dog doesn't change the *rule*, just who's steering into it on purpose instead of it happening by chance. Punch and Toot (see Punch mechanic below) both shove the dog away from the cat, which would fling the player's own character away from the thing they're trying to reach — `handlePunch()`/`handleToot()` no-op (position-wise; the sound still plays) whenever `controlledEntity === 'dog'`.

**Player-controlled speed is unified across all three characters.** `tryMoveDog()` uses `layout.dogPlayerSpeed` (`BASE_DOG_PLAYER_SPEED = 10`), `movePlayerMouse()` uses `layout.mousePlayerSpeed` (`BASE_MOUSE_PLAYER_SPEED`, raised from `8` to `10` in the same pass), and `tryMoveCat()` uses `Cat.speed` (`10 * scale`, unchanged) — all three now the exact same per-tick value, deliberately, so piloting any of the three characters feels identical regardless of which one you picked. This was a direct fix for "the dog is too fast when playing as it" (`tryMoveDog()` used to read `this.dog.speed` directly, which is the *autonomous*-wander field — see `Dog.js` above for why that coupling was the actual bug) and an explicit ask that mouse match too, not just dog-matches-cat. Only the *player-controlled* speed is unified — each character's own *autonomous* speed (Cat's `wanderCat()`/chase, Mouse's `speedX`/`speedY`, Dog's own `this.speed`) is untouched and deliberately still tuned independently per character.

**Win/lose semantics don't change between modes — only which outcome is good news for the player does, and the dog is on "team mouse."** `checkCollision(cat, mouse)` → cat catches mouse; `checkMouseEscaped()` → mouse reaches an `Escape`. These two triggers and their narration messages (`MESSAGES.CAT_CAUGHT_MOUSE`/`MESSAGES.MOUSE_ESCAPED`) are identical regardless of `controlledEntity` — the game's win/lose structure is already symmetric (cat-side wins by catching, mouse-side wins by escaping). `endGame(message, soundKey, isWin)` takes an explicit `isWin` flag, computed at both trigger sites from `controlledEntity`: cat catches mouse → win iff you're playing Cat (loss for both Mouse *and* Dog, since the dog failed its one job); mouse escapes → win iff you're *not* playing Cat (both Mouse and Dog succeed together, even though the dog never touches the mouse directly). This lets the game-over modal (see below) show an unambiguous "You Win!"/"You Lose!" headline on top of the narration text rather than relying on the player to infer which side they were rooting for.

### Game-over modal (`displayGameOverModal`, `endGame`)
Replaces the old plain-text end screen — `this.message` drawn directly on top of the live board, which was sometimes hard to read depending on what was rendered behind it — with a proper modal: a dimming scrim (`COLORS.MODAL.SCRIM`) over the whole canvas, then a rounded gradient card that pops/scales in over `MODAL_POP_IN_DURATION` (250ms — same `performance.now()`-diff pattern as `drawShockwave()`'s animation). `this.gameOverIsWin` (set by `endGame()`, see Win/lose semantics above) picks both the headline — "You Win!"/"You Lose!" in a bold `Impact`/`'Arial Black'`/sans-serif stack with a dark outline stroke so it pops against either background — and the card's color scheme: a gold gradient for a win, a bright teal/blue gradient for a loss, both deliberately playful rather than switching to somber tones on a loss (this is a kids' game). The narration message still shows as a smaller subtitle beneath the headline. `drawRoundedRect()` is a small shared path-builder (doesn't fill/stroke itself) reused by both the card and the "Play Again" button. The transient (non-game-over) "Dummy caught Mia!" pause message during active play is drawn separately, via `displayMessage()` (see `render()`'s `if (this.gameOver) { modal } else if (this.message) { displayMessage() }` branch) rather than this modal, since gameplay is still visibly running underneath there and a full modal takeover would feel wrong mid-round — see "Dog-pauses-cat stun moment" below for its own, later presentation pass.

- **Win/loss sound** (`playWinSound()`/`playLoseSound()`, `js/utils/audio.js`): `endGame()` plays one of these, keyed off its own `isWin` parameter, *in addition to* the `soundKey` event sound it already played (a meow, a mouse squeak) — that event sound alone was never a real "you won" cue, since the same event (cat catches mouse, mouse escapes) means opposite things depending on `controlledEntity` (see Win/lose semantics above), so it sounded identical on a win and a loss. Both are synthesized (oscillators + note envelopes, same Web Audio approach `playModalPopSound()` uses, just musical instead of noise-based) rather than supplied audio files, since nothing in `sounds/` fit either. Win is a short ascending major arpeggio (C5-E5-G5-C6, triangle wave) into a held final note with a soft high shimmer layered under it. Loss is three descending, pitch-bent notes (sawtooth through a lowpass filter for warmth) — a cartoon "womp womp womp," deliberately *not* a somber tone, matching the modal's own still-playful teal/blue loss palette. Both gated on `isSfxMuted()` like every other SFX.

### Dog-pauses-cat stun moment (`handleDogCollision`, `displayMessage`, `drawStunBurst`/`drawStunStars`)
The "Dummy caught Mia!" moment used to be a single plain `fillText` plus a static red silhouette outline around the cat for the whole `DOG_PAUSE_DURATION` (2000ms) — flagged live as underwhelming. Replaced with a bolder message treatment plus a genuinely animated "impact, then daze" effect, all still fired from `handleDogCollision()` and gated by `this.catPaused`; the dog's own knockback shove was explicitly out of scope and untouched — this was originally a presentation-only pass. `DOG_PAUSE_DURATION` itself was retuned twice after that, both times on request: 2000ms → 8000ms (4x, giving the mouse a real window to actually use the pause to escape), then 8000ms → 4000ms (halved again — net 2x the original). `drawStunStars()`'s orbit and `displayMessage()`'s banner both just keep running for however long `this.catPaused` stays true, so neither retune needed any separate change beyond the one constant; the burst (`DOG_COLLISION_BURST_DURATION`, still 400ms) is deliberately unaffected either time, since it's meant to read as a quick hit, not stretch to match the pause length.

- **Message pop-in** (`displayMessage()`): pops/scales in (`DOG_COLLISION_MESSAGE_POP_IN_DURATION`, 250ms, ease-out-cubic scale+fade — same pattern as `displayGameOverModal()`'s own pop-in, keyed off `this.dogCollisionStartTime` rather than a fresh timestamp of its own) instead of a static `fillText`. **First version was a bold purple `fillText` with a dark stroke and no backdrop — flagged live as still amateurish/hard to read**, since floating text with nothing behind it is at the mercy of whatever the board happens to be drawing right there (a light floor tile, dark furniture, a character). ### Cat AI (`updateCatAI`, `catHasLineOfSightToMouse`, `moveCatTowardMouse`, `wanderCat`)
Runs whenever the cat isn't player-controlled — Mouse mode and Dog mode both (see Character selection & playable modes above). Each tick: if the cat has line of sight to the mouse, it moves one cardinal step directly toward it (`moveCatTowardMouse`); otherwise (or if that move is blocked — see below) it wanders (`wanderCat`). No memory of the mouse's last-known position — once sight is lost it's pure wander until the cat's facing direction happens to line up with the mouse again, by design, not a pathfinding gap to fix.

- **`Cat.facingDirection`** (see `Cat.js` above) is the cat's last committed movement direction, updated inside `move()` regardless of whether the player or the AI is driving — this is what makes line-of-sight direction-aware without any Mouse-mode-specific state living on `Cat` itself.
- **`catHasLineOfSightToMouse()`**: true only if the mouse is strictly in the cat's facing direction (cardinal — up/down/left/right, not a cone) *and* no wall-mounted furniture (`cabinet`/`sink`/`stove`/`fridge` — freestanding `table`/`plant` never block sight) crosses the straight line between their centers. Implemented as two `aabbOverlap` checks rather than hand-rolled comparisons: the "facing" test builds a rectangle from the cat's own edge out to the canvas boundary (spanning the cat's cross-axis extent) and checks the mouse's box against it; the "occlusion" test models the cat-to-mouse sight line as a 1px-thick segment rectangle and checks each wall-furniture piece's box against that. Uses `cat.size`, not `cat.displayWidth`/`displayHeight` (the smaller render box) — an earlier version mixed the two, which could report "no sight" in situations where the cat's real collision footprint was already touching the mouse. **This is now the one place `cat.size` still governs anything perceptible to the player** — `checkCollision()`/`tryMoveCat()`'s own wall clamp both switched to `displayWidth`/`displayHeight` (see "Hitbox tightening" below); the wider lane here was left alone on purpose, since a bigger perception box only means the AI notices the mouse a little sooner, not that it can catch it from further away.
- **`moveCatTowardMouse()`**: picks whichever axis (x or y) has the larger gap to the mouse's center and moves one step that way via `tryMoveCat()`, matching the same single-direction-per-tick granularity as player movement (no diagonal movement). Returns `tryMoveCat()`'s result; if the move fails (e.g. the table sits in the path — freestanding furniture blocks movement even though it doesn't block sight), `updateCatAI()` falls back to `wanderCat()` for that tick instead of stalling in place.
- **`wanderCat()`**: actively searches rather than idly wandering — moves *every tick* (`Dog.js`'s own autonomous wander now follows this same continuous-per-tick pattern too, adopted later for the same reason — see `Dog.js` above) in a chosen direction, only re-picking that direction every `CAT_WANDER_DIRECTION_INTERVAL` (1200ms) or immediately if the current direction just hit a wall/furniture (via `tryMoveCat()`'s return value), so it doesn't sit stuck in a corner. Speed is `this.cat.speed * CAT_WANDER_SPEED_MULTIPLIER` (currently `0.5` — wandering/searching is deliberately slower than the direct chase). **History worth knowing:** `Cat.move()` used to silently ignore any speed override and always move at its own fixed `this.speed` regardless of what was passed in, so several rounds of tuning this multiplier (1.5 → 1.15 → 1.0) had *no actual effect* on movement distance; the "too fast" feeling during that tuning came entirely from wandering having just switched from a once-every-2-seconds hop to continuous per-tick movement. Once `Cat.move(direction, speed)` was fixed to honor the override, the multiplier started having a real effect for the first time and needed retuning down to `0.5` from that starting point.

### Mouse disappearing on escape (`GameScreen.mouseEscaped`)
Previously, once the mouse reached an `Escape` and the round ended, `render()` kept drawing it sitting at the hole for the rest of the (now-frozen) game-over screen. `checkMouseEscaped()` now also sets `this.mouseEscaped = true`, which `render()` and `drawMouseSilhouette()` check to stop drawing the mouse entirely. Applies regardless of `controlledEntity`.

### Cat silhouette under passable furniture (`GameScreen.drawCatUnderFurnitureEffect`/`drawCatSilhouette`)
Cat counterpart to the mouse's "ducks under furniture" treatment above, added on request ("when the cat goes in/under furniture, can it also be silhouetted like the mouse?... make it look cat like"). The cat is only ever actually walking *under* furniture for the small set of non-blocking types (`plant`/`cart` — see `CAT_NON_BLOCKING_FURNITURE_TYPES`), since it's still blocked by, and correctly drawn on top of, every other type — so unlike the mouse (which draws once, before *all* furniture, up front in `render()`), this doesn't move the cat's own `draw()` call earlier in the sequence, which would have also changed how it layers against the dog and against every furniture type it's actually stopped by (never asked for). Instead, after the cat draws in its normal spot in `drawGameObjects()`, `drawCatUnderFurnitureEffect()` re-draws just the specific overlapping non-blocking piece(s) on top of the cat's already-drawn sprite, then (only if something was actually re-drawn) calls `drawCatSilhouette()` — a smaller, targeted change rather than the mouse's up-front approach. `drawCatSilhouette()` is deliberately **not** a copy of the mouse's plain ellipse (per explicit direction to make the two distinguishable): a rounded head with two pointed ears (quadratic-curve tips, same soft-point technique `canvasShapes.js`'s cat-ear-card shapes use) drawn first, then the head ellipse on top so the ear bases blend into it rather than reading as separate shapes glued to the edge. Same faint translucent-black (`globalAlpha = 0.35`) treatment as the mouse's, so the two read as the same "hidden under furniture" visual language despite the different shape. Confirmed live (forced a single render with the cat's position hacked to sit exactly on the cart/plant, since this environment's `document.hidden` issue — see the cart placement section above — ruled out driving it there via real movement): clearly visible ear silhouette through the cart's flat wood top; present but subtler under the plant, whose busy leaf texture makes any faint overlay harder to see — not a bug, the same texture-dependent subtlety the mouse's silhouette already has under detailed furniture.

### Spawn safety (`resolveClearSpawn`, `isHiddenByFurniture`)
The cat's, mouse's, and dog's fixed spawns (bottom-center-ish for the cat, `(100, 100)`-ish for the mouse, `(200, topWallHeight + spawnClearance)`-ish for the dog) aren't checked against wall-mounted furniture the way the freestanding dining set is (see `blocksSpawn()` in `generateKitchenFurniture()`) — on some layouts a cabinet/fridge can land right on top of one. `resolveClearSpawn(preferredX, preferredY, size)` returns the preferred spot unchanged unless `isHiddenByFurniture()` says it's covered, in which case it random-searches `this.playableArea` (the same interior bounds the dining set already searches — exposed from `generateKitchenFurniture()` for this reuse) for a clear spot, using the same attempt-count pattern as the dining set's own placement search. `isHiddenByFurniture(x, y, size)` is the same "is this box under furniture" test used by `drawMouseSilhouette()` (see Wall band & mouse holes / Kitchen furniture above), so both share one definition of "hidden."

**History worth knowing:** the cat's spawn was originally left out of this protection — it spawns bottom-center, away from the wall furniture runs, and was assumed safe on that basis. That assumption broke once `getCharacterScale()` (see below) made desktop characters ~2x bigger without touching `spawnClearance` (a board-margin value, independent of character size): the cat's now-larger box could spawn already overlapping the bottom-wall furniture row, with `tryMoveCat()` rejecting every move out of it since the furniture-collision check fails from the very first frame. Same class of bug CLAUDE.md already tracked for the mouse/dog, just via a different trigger (a size change rather than a furniture-layout change) — the fix was simply routing the cat's spawn through `resolveClearSpawn()` too, same as the other two.

### Character size scale (`js/utils/scale.js`, `getCharacterScale`)
Characters read too small on a laptop-size desktop canvas even after the mobile-responsiveness pass below. `getCharacterScale()` is a fourth scale function (see Mobile responsiveness), same shape as `getFurnitureScale()`: a no-op on touch (mobile character sizing was already tuned via `getScale()`'s own multiplier), `DESKTOP_CHARACTER_SIZE_MULTIPLIER` (currently `1.95`, built up in two live-tuning passes — 1.5, then another 30% on top) on desktop. Deliberately **not** folded into `getScale()` itself, because `getScale()` also drives Cat/Dog/Mouse movement *speed* (each multiplies its own speed by the `scale` it's constructed with) — bumping that blanket value would have silently sped characters up along with resizing them, undoing the wander-speed tuning above. Instead, `Cat`/`Dog`/`Mouse` each take a separate `sizeScale` constructor parameter (defaults to `scale` if omitted) used only for their size/display fields (`size`, `displayWidth`/`displayHeight`, `frameWidth`/`frameHeight` for `Dog`), while `scale` alone keeps driving speed. `GameScreen.computeLayout()` exposes this as `characterScale`, also used for `catSizeApprox`/`mouseSizeApprox`/`dogSizeApprox` (the spawn-clearance approximations above) so those stay accurate to the characters' real, now-bigger size.

### Hitbox tightening — catching, walls, furniture, mouse-hole entry (`GameScreen.js`, `Dog.js`, `Escape.js`)
Four related fixes from one round of live feedback ("you can catch other characters from pretty far away… check chars can go all the way to furniture and walls… the mouse can escape by just being near a mouse hole, can it be that the mouse has to actually enter it?"). All four were confirmed by direct measurement — positioning entities via a temporary debug reference to the live `GameScreen` instance and reading back exact pixel gaps — rather than by reasoning about the scale math alone, which turned out to be necessary: several of these bugs only became visible once actual numbers were computed at real canvas/scale values, not obvious from reading the formulas in isolation.

1. **Catching from too far away — `checkCollision()`/`Dog.isColliding()` used `cat.size`, not the cat's real sprite.** `cat.size` (the oversized logical box also described in `Cat.js` above) was being reused for the cat-catches-mouse win check and the dog-pauses-cat check, not just the wall clamp/AI lane width it was documented as scoped to. Measured directly: with `DESKTOP_CHARACTER_SIZE_MULTIPLIER` at `1.95`, `cat.size` runs noticeably bigger than `cat.displayWidth`/`displayHeight` (the actual visible sprite) — enough that a mouse or dog placed just outside the cat's real sprite still registered a catch. Fixed by switching both checks to `cat.displayWidth`/`displayHeight`; `mouse.size` was left alone since it already equals the mouse's own display size (see `Mouse.js` above), never oversized to begin with. `catHasLineOfSightToMouse()`'s own use of `cat.size` for AI perception width was deliberately *not* touched — a wider lane only makes the AI notice the mouse sooner, it isn't the same bug as catching from further away.
2. **The cat's wall clamp could clip into the wall — `tryMoveCat()`'s old "position can dip below `WALL_OFFSET` by up to `cat.size`" formula.** This convention (see `Dog.js`'s own comment above for the fuller history of the same convention breaking for the dog) assumed `cat.size` exceeded the cat's true footprint enough that the allowance would never push the *visible* sprite past the edge. Measured with furniture removed (to isolate pure wall behavior): the cat could walk flush to the raw canvas edge on all four sides, clipping several pixels into the drawn wall band rather than stopping "at" it. Fixed by switching to the same strict-containment shape `Dog.js`'s wall clamp already used successfully (`x >= WALL_OFFSET && x <= canvasWidth - WALL_OFFSET - displayWidth`, and the same for Y) — confirmed after the fix to leave a small, consistent, non-negative gap on all four sides instead.
3. **The dog clipped into furniture horizontally and stopped short of it vertically — its furniture-collision check used a square `this.size` (50×`sizeScale`) against a sprite that isn't square (`frameWidth`/`frameHeight`, 60/38×`sizeScale`).** Present in both `Dog.tryMove()` (the autonomous path) and `GameScreen.tryMoveDog()` (the player-controlled path) — both called `Furniture.isColliding()` with `{ size: this.size }`. Measured against a synthetic furniture piece placed in open floor: approaching horizontally, the dog's sprite (94.9px display width from `frameWidth`, wider than the 79px square box) clipped ~15px into the furniture before being stopped; approaching vertically, the square box (79px, taller than the sprite's real 60px `frameHeight`) stopped the dog ~20px short of actually touching it. Fixed by bypassing `Furniture.isColliding()` in both places (same reason `Cat.js`'s own furniture check already bypasses it — see `collision.js`'s own comment) and calling `aabbOverlap()` directly with `frameWidth`/`frameHeight`, matching the box `Dog.isColliding()`/`draw()` already use. Confirmed after the fix: a clean ~1-3px gap (movement-step granularity, not a formula error) on both axes. `this.size` is still used elsewhere (the punch/toot knockback bound in `GameScreen.js`) — that's a coarse "stay on screen after being shoved" clamp, not a movement/collision concern, and wasn't part of this complaint.
4. **Mouse escape triggered on mere proximity — `Escape.isMouseInside()` is a loose "any overlap" test, and `checkMouseEscaped()` was using it directly.** Since AABB overlap fires on any edge-touching overlap, the mouse only had to brush the hole's bounding box, not actually reach it. `isMouseInside()` itself is still needed elsewhere exactly as-is — it's what exempts the cat/dog's wall clamp near the gap an escape leaves in the wall, where "any overlap, don't get stuck on the wall here" is the correct (loose) behavior. Added a second, stricter method, `Escape.hasMouseEntered()`, used only by `checkMouseEscaped()`.
   - **First version required the *mouse's own center* to fall inside the hole — shipped, then reported live as "the mouse can never enter the mouse hole."** Confirmed by direct measurement to be genuinely impossible, not just strict: the hole is only as deep as the wall band itself (`BASE_ESCAPE_SIZE = 15`, ~12px at typical scale), shallower than the mouse's own half-width (~25px+ at typical scale) — and since the mouse can never get closer to the wall than flush against it (position clamped to `>= 0`), its center could never get within the hole's depth even at the mathematically best possible position (checked directly: flush at the wall, x perfectly centered on the hole, still `false`).
   - **Second version reverses which box has to contain which: the hole must be fully covered by the mouse's own box**, not the mouse's center inside the hole. Since the mouse (~32px+ display size) is always bigger than the hole (~15px), this is the direction that's actually achievable — the mouse just needs to be positioned over the hole while flush against that wall. Confirmed: mouse flush at the wall and centered over the hole → escapes; mouse brushing just the hole's edge without covering it → doesn't; mouse aligned with the hole but not touching that wall at all → doesn't.
   - **Still reported live as too easy — "if the mouse gets anywhere near the hole, it escapes."** `checkMouseEscaped()` was being called every single tick regardless of what the mouse was actually doing, so once positioned in `hasMouseEntered()`'s catch zone (a real, if smaller, area — see above) it escaped the instant it got there and stayed escapable for as long as it happened to loiter in that zone, with no sense of *arriving* at the hole. **Fixed by tying the check to the mouse's actual wall-hit event instead of running it continuously.** `Mouse.js` already calls `this.wallHitCallback` at the exact moment of wall contact for both movement modes — the autonomous bounce in `Mouse.update()`, and the wall-clamp in `GameScreen.movePlayerMouse()` — and by the time it fires, the mouse's position has already been clamped flush to that wall, which is exactly the position `hasMouseEntered()` needs to mean anything. `checkMouseEscapeOnWallHit()` (`GameScreen.js`) now runs the escape check from inside that callback (alongside the existing wall-hit sound), and `updateMouse()` no longer checks escape on its own per-tick pass at all — only `checkCollision()` (cat catches mouse) still runs continuously there, since catching was never the part of this complaint. Confirmed: the mouse sitting in the catch zone for many ticks with no wall-hit event firing no longer escapes; an actual wall-hit event at that same position does; a wall-hit event elsewhere on the same wall (no hole there) doesn't.
   - **Then reported the opposite way — "now it's a little too hard sometimes... taking a step either way to get past it goes too far."** Two compounding causes, both fixed together:
     - **The catch window itself was tight, and a naive "make the hole bigger" fix would have made it *tighter*, not looser.** `hasMouseEntered()` requires the hole to be fully covered by the mouse's box — under that containment direction, a bigger hole is *harder* for a fixed-size mouse to fully cover, the opposite of the usual "bigger target = easier" intuition (confirmed by direct calculation before touching any code: `window = mouse.size - escape.width`, so `escape.width` and window size move in opposite directions). Widening `BASE_ESCAPE_SIZE` — the fix floated in discussion before this was caught — would have actively made the reported problem worse. Fixed instead with a separate constant, `BASE_ESCAPE_HITBOX_MARGIN` (20, → `layout.escapeHitboxMargin`), that expands the *mouse's* effective box for `hasMouseEntered()`'s check only, leaving the hole's own visual size (`BASE_ESCAPE_SIZE`) untouched — this direction does widen the window normally, since it's added on both sides of an already-correct containment test rather than shrinking the thing being contained.
     - **Only the tick that first caused a wall-clamp fired `wallHitCallback` (see the point above) — a player who first touched the wall short of the hole, then slid along it to line up, never got re-checked.** In player-controlled mode, `movePlayerMouse()`'s clamp-detection (`clampedX !== proposedX || clampedY !== proposedY`) is only true on the tick position actually gets pushed back — sliding sideways while already flush against a wall doesn't re-propose a value that needs clamping on that axis, so it silently stopped re-firing after the first contact. Fixed by adding a second, separate check in `movePlayerMouse()`: after every tick spent actively moving (this whole block already only runs while a direction key is held), if the resulting position is flush against *any* wall — not just the one that was clamped this tick — `checkMouseEscapeOnWallHit()` runs again. Kept as a second call alongside the wall-hit-sound path (not a replacement for it) so the sound still only plays once per real contact, not on every tick of a slide. Confirmed: mouse makes first contact 80px from a hole (correctly doesn't escape), then slides along the wall toward it without ever backing off — escapes mid-slide, a few ticks after crossing into the (now-wider) window, with no need to disengage and re-approach.
   - **That sliding fix immediately created a new problem: merely running/sliding past a hole, never stopping, now also escaped.** Reported live with a specific repro: "if I run to the top wall's non mouse hole block, and just turn straight left or right and run straight, just running by one escapes... I'd like you to have to stop at it and enter it." Root cause was structural, not a tuning number — checking escape on *every tick spent moving* (the previous fix) is inherently indistinguishable from checking on every tick of a fast pass-through, once the catch window is wide enough to be crossed within a few ticks (which the margin fix, directly above, had just made true). **Fixed by moving the player-controlled escape check off the "moving" path entirely and onto the "not moving" path instead** — `movePlayerMouse()`'s `if (direction) {...}` branch (movement, wall-clamp, sound) no longer calls `checkMouseEscapeOnWallHit()` at all, replaced by a new `else` branch that calls it exactly when the player *isn't* pressing a movement key this tick. This requires an actual stop: arriving at the wall (however that happened — straight-on, or slid into position along it) never escapes by itself anymore, only releasing input while correctly positioned does. Safe to call unconditionally on every idle tick — `checkMouseEscapeOnWallHit()`'s own `mouseEscaped`/`gameOver` guard makes repeat calls a no-op, and `hasMouseEntered()`'s own geometry already requires the mouse to be resting at a wall for it to ever return true, so idling in open floor is a correct no-op too.
     - **The autonomous mouse (Cat/Dog mode) needed its own separate wiring, not just having its old trigger deleted.** `wallHitCallback` used to do double duty — play the wall-hit sound *and* run the escape check — for both movement modes. Since the fix above needed to remove the escape check specifically from the *player*-controlled path while leaving `wallHitCallback` itself (sound) firing from both, the escape check for the autonomous bounce needed its own dedicated hook: `Mouse.js` gained a second callback, `escapeCheckCallback` (`setEscapeCheckCallback()`), fired from the same two bounce blocks in `Mouse.update()` that already call `wallHitCallback`, wired in `resetGameObjects()` to `checkMouseEscapeOnWallHit()` — the exact same function the player path now calls from its `else` branch, just triggered by a different event for each mode. Deliberately **not** touched otherwise: the autonomous mouse bounces immediately away from a wall rather than sliding along it, so it never had the "running by" exploit the player-controlled fix above was for, and this complaint was never about autonomous mode. Confirmed after the split: player-controlled mouse running straight past a hole while holding a direction the whole time never escapes (tested crossing a hole's full x-range in one continuous hold); releasing the key while correctly positioned does; the autonomous mouse still escapes correctly on a bounce timed exactly at a hole.
   - **Still reported live as escaping by "just running by," even after the idle-gated fix above — plus a request that "turning to enter it" should also work, not just a full stop.** The idle-branch fix was verified correct for a genuinely *held* key (a real browser never produces idle ticks in between while a key is actually held down), but that's not the only way players move — tapping the same direction repeatedly (a completely normal way for a kid to play) releases the key between every tap, and each of those brief release gaps was itself an "idle" tick under the previous fix, satisfying the escape check's trigger condition despite the player never having deliberately stopped. Two changes:
     - **A debounce, `MOUSE_STOP_DEBOUNCE_MS` (150ms).** `movePlayerMouse()` now tracks `this.mouseLastMovedAt` (a `performance.now()` timestamp, updated on every tick a direction key is held, regardless of whether that tick's move actually changed position). The idle branch only runs the escape check once at least 150ms has passed since a key was last held — long enough to clear a fast tap's release gap, short enough to still feel instant for an actual stop. Confirmed by simulating rapid tapping (16ms held / 40ms released, repeated) across a hole's full catch window with real elapsed time (`await`ed delays, not just back-to-back synchronous calls, since the debounce only means anything against real clock time): no escape, all the way through and past the window.
     - **"Turning to enter": pressing the direction that faces *into* whichever wall the mouse currently rests flush against also counts, even without releasing anything first.** Each wall has exactly one "into" direction (up for the top wall, left for the left wall, etc.) — sliding *parallel* to a wall (the "running by" motion) can never satisfy its own wall's "into" check, so this can't be exploited the same way, but a deliberate turn toward the hole no longer has to wait out the debounce either. Checked in the `if (direction)` branch itself (`enteringWall`, computed from the post-clamp position so it works whether this tick is what caused the mouse to reach that wall or it was already resting there), calling `checkMouseEscapeOnWallHit()` directly alongside the normal movement/sound handling for that tick. Confirmed: pressing the wall's own "into" direction while correctly positioned in the catch window escapes immediately, with no idle tick needed at all.

## Mobile responsiveness (`js/utils/scale.js`, `orientationGate.js`, `touchControls.js`)
Milestone-scope mobile support: the game requires landscape (a full-screen gate blocks portrait) rather than reworking layout for both orientations, but *within* landscape it now scales correctly at any canvas size. Confirmed live before this existed: on a 350px-wide mobile canvas, a single stove alone ate ~40% of the board height, because every size in the game (furniture scale, wall thickness, character size/speed, floor tile size, UI chrome) was a fixed pixel value tuned by eye against a desktop-sized canvas.

- **Four separate scale functions, not one** (`js/utils/scale.js`) — all derived from the same `base = canvasWidth / REFERENCE_WIDTH` (`REFERENCE_WIDTH = 1280`, `resizeCanvas()`'s desktop width cap), but each applying its own multiplier once `isTouch()` (`window.matchMedia('(pointer: coarse)').matches`, exported — this is the single signal reused everywhere a mobile-vs-desktop decision needs to be made, see "When working in this repo" below) reports a touch device:
  - `getScale()` — character movement *speed*, wall/floor chrome, spawn clearance. `MOBILE_ASSET_MULTIPLIER = 1.5` on touch, a no-op (`base`) on desktop.
  - `getUIScale()` — buttons and messages (play-again button, win/lose text, `Cutscene.js`'s modal/text/button, `CharacterSelectScreen`'s buttons). `MOBILE_UI_MULTIPLIER = 2` on touch, no-op on desktop — confirmed live to read fine bigger than the other mobile assets, so it deliberately keeps its own (larger) multiplier instead of following `getScale()`'s reduction.
  - `getFurnitureScale()` — furniture only (`GameScreen`'s `moduleScale`/`diningScale`, i.e. cabinet/sink/stove/fridge/table/plant/cart/shelf). `DESKTOP_FURNITURE_MULTIPLIER = 2` on desktop — the `kitchen_*.webp` asset swap (see Kitchen furniture below) came with new native pixel dimensions, and `BASE_MODULE_SCALE` was re-tuned against those without being checked live at full desktop size, so furniture read noticeably smaller than before once actually reviewed live. Touch used to be a no-op here (just `getScale()`'s own `MOBILE_ASSET_MULTIPLIER`, no furniture-specific term) — a design-director pass flagged that as a real cross-device inconsistency: ratio-wise that was `2 : 1.5`, i.e. furniture occupied 33% more of the board's width on desktop than on touch, which is exactly what "assets don't scale consistently with board size" looks like from the outside (a device-class jump, not a smooth function of canvas width — everything *within* one device class was already provably consistent, since every dimension is `BASE * a scale variable itself proportional to canvasWidth`). Fixed by adding `MOBILE_FURNITURE_MULTIPLIER = DESKTOP_FURNITURE_MULTIPLIER / MOBILE_ASSET_MULTIPLIER` (≈1.333) to the touch branch — derived the same way `MOBILE_CHARACTER_SIZE_MULTIPLIER` below already was, rather than picked by eye, so furniture now occupies the identical fraction of canvas width on both device classes.
  - `getCharacterScale()` — character on-screen/collision *size* only, not speed (see Character selection & playable modes above for why the two had to be split). `DESKTOP_CHARACTER_SIZE_MULTIPLIER = 1.95` on desktop, `MOBILE_CHARACTER_SIZE_MULTIPLIER = 1.9771375` on touch. Baseline was `1.3`, deliberately *derived* as `DESKTOP_CHARACTER_SIZE_MULTIPLIER / MOBILE_ASSET_MULTIPLIER` (i.e. 1.95/1.5) so characters occupied the same board-width fraction on both device classes; `getFurnitureScale()` above still follows that derived-not-eyeballed pattern. **Bumped four times on explicit request, overriding the derivation each time, each round applied to the current value rather than re-derived from 1.3**: `1.95` (1.3 * 1.5, "make mobile characters 50% bigger" — reported live as an overshoot) → `1.495` (1.3 * 1.15, "go back to last size, then make them 15% bigger") → `1.71925` (1.495 * 1.15, "15% more from the current values") → `1.9771375` (1.71925 * 1.15, "15% even more from the current values") — the last of these now exceeds `DESKTOP_CHARACTER_SIZE_MULTIPLIER`'s own `1.95` as a raw number, though the two were never directly comparable anyway (see below). If another "N% more" request lands, apply it to whatever `MOBILE_CHARACTER_SIZE_MULTIPLIER` currently is, not back to `1.3` or any earlier step. The desktop-parity rationale no longer holds exactly after these changes, on purpose; mobile characters are now noticeably bigger relative to their own canvas than desktop characters are relative to theirs (mobile's *effective* size also carries `MOBILE_ASSET_MULTIPLIER` from inside `getScale()`, so comparing the two raw multipliers directly is never quite apples-to-apples anyway). Not yet checked live for wall/furniture clearance fallout — `Dog.js`'s own size-bump history (see `dog_v2.png`'s "sized up 20%" entry above) flagged that a bigger character can start clipping into walls/furniture more than before since containment math is keyed off the same size fields that just grew; worth a live mobile pass if clipping gets reported.
  Treat these constants (`1.5`, `2`, `2`, `1.95`, `1.9771375`, and furniture's derived `≈1.333`) as tuned-by-eye values arrived at by trying a number, reviewing live on-device, and adjusting (or, for the mobile character multiplier as of the requests above, a direct percentage ask stacked incrementally on the *current* value each time — including one round of overshoot-and-correct) — not settled physics — except where a constant is still explicitly *derived* from another (furniture's mobile multiplier). A first mobile pass used a flat 2x for everything and had to be pulled back to 1.5x for in-game assets once it read as too big on an actual phone; `DESKTOP_CHARACTER_SIZE_MULTIPLIER` itself went through two live-tuning rounds (1.5, then +30% to 1.95) before it read right. If the art or device mix changes again, expect another round of the same — and if a *new* per-category multiplier is ever added, check whether it needs the same derived-mobile-counterpart treatment furniture (still) has, rather than assuming a bare `MOBILE_ASSET_MULTIPLIER` pass-through is correct by default.
- `GameScreen` computes `this.layout = computeLayout(canvas.width)` once in its constructor (canvas size is fixed for a `GameScreen`'s lifetime — live mid-game resize is a separate, still-open gap, see Known rough edges) and every `BASE_*` constant is multiplied by whichever of `scale`/`uiScale`/`furnitureScale`/`characterScale` fits its category inside `computeLayout()` — methods read `this.layout.X`, never a bare module constant. `Cat`/`Dog`/`Mouse` each take both a `scale` param (from `getScale()`, drives speed) and a `sizeScale` param (from `getCharacterScale()`, defaults to `scale` if omitted, drives size/display — see Character selection & playable modes above) — but neither touches `frameWidth`/`frameHeight` used for sprite-sheet *source*-rect slicing, which must stay at the sprite's real native pixel dimensions regardless of display scale. `Dog` additionally exposes `nativeFrameWidth`/`nativeFrameHeight` for this since its native frame size was previously reused directly as the draw destination size too (no `/4` divisor like `Cat` has). `Cutscene.js` uses `getUIScale()` (it's chrome, not a character or piece of furniture) for its modal/text/button sizing — this was a real bug hit live (long cutscene text overflowing its modal on a small canvas) fixed by the same mechanism.
- **`Cat`/`Dog`/`Mouse` expose `displayWidth`/`displayHeight` getters** giving each character's actual on-screen size regardless of how each class internally represents it (`Cat`'s `frameWidth/4 * sizeScale`, `Dog`'s already-scaled `frameWidth`, `Mouse`'s `size`) — `Cutscene.js` reads these (falling back to raw `frameWidth`/`frameHeight`) to center each character correctly, and `GameScreen`'s `handlePunch()`/`drawRedOutline()` use `cat.displayWidth`/`displayHeight` instead of re-deriving `frameWidth/4` themselves.
- **The landscape gate** (`orientationGate.js`) is a full-screen overlay (`#orientationGate` in `index.html`, styled in `styles.css`) shown whenever `window.innerHeight > window.innerWidth`, checked on load/`resize`/`orientationchange`. It's a real aspect-ratio check, not a device/breakpoint media query, so a narrow desktop window triggers it too. The game loop keeps running underneath it (not paused) — the overlay's `z-index` just makes the board unreachable, which was judged sufficient for this milestone rather than also pausing `update()`.
- **Canvas width reserves more side margin on touch devices** (`resizeCanvas()`, `js/main.js`): `maxCanvasWidth = window.innerWidth * widthFraction`, where `widthFraction` is `0.8` on touch (`isTouch()`) vs `0.9` on desktop. This only changes anything when the canvas is *width*-constrained rather than height-constrained — i.e. a viewport aspect ratio close to or narrower than the canvas's own 4:3 (squarish windows, and notably a standard iPad's landscape aspect, which is almost exactly 4:3). Most phones in landscape are height-constrained instead, where this fraction never binds, so they're unaffected — confirmed by recomputing `resizeCanvas()`'s formula by hand across a spread of real device sizes rather than just resizing a desktop browser window. Added after the default 10% margin left as little as ~50px of gutter beside the canvas on an iPad, not enough room for a usable d-pad.
  - **Design-director pass: this fraction alone wasn't a hard guarantee.** Hand-computing the old formula across a spread of real device widths showed the d-pad's old shrink-to-fit (see below) collapsing it to ~70-125px on an iPhone SE, a standard iPad landscape, and a touch laptop — well past comfortable, and the actual cause of a live "too much blank space… hard to press the right direction" report. Explicit product direction: the control must always stay playable, even at the cost of some board width.
    - **First attempt at this caused a real regression, live on an iPhone: a black gap reappeared above the board.** It capped `maxCanvasWidth` at `window.innerWidth - 2 * MIN_TOUCH_CONTROL_GUTTER` (`MIN_TOUCH_CONTROL_GUTTER`, exported from `touchControls.js`) *before* checking whether the device was even going to be width- or height-constrained — so on ordinary phones that were always going to end up height-constrained anyway (and already had a perfectly adequate natural gutter as a side effect of that), the cap still shaved width off, which shaved height off too (`canvasHeight` is always derived from `canvasWidth` to hold the 4:3 ratio) — reintroducing the exact "gap above the board" bug this repo had already fixed once before (see Known rough edges' white-box entry). Fixed by computing the natural (fraction-only, pre-existing) fit *first*, exactly as before, and only reaching for the extra width cap if that natural fit's own gutter actually falls short of `MIN_TOUCH_CONTROL_GUTTER` — which only happens on the width-constrained aspect ratios (iPad-like, or the very narrowest phones) this was meant to target in the first place. Verified by hand-computing across the same device spread: ordinary phones (iPhone 14 and larger) now get zero height loss; only the narrowest phones and iPad-like tablets still give up some board height, and by a bounded, much smaller amount than the first attempt (see `MIN_DPAD_SCALE` below for the matching floor adjustment).
- **Touch controls** (`touchControls.js`): an on-screen D-pad and punch/toot/meow buttons (`#actionButtons` — a purple-glow vertical stack of three round buttons; these map to the same keys as desktop, `p`/space/`m`, so touch users need direct access too, not just movement). Positioned and sized by `layoutTouchControls()`, called on load/`resize`/`orientationchange`:
  - **`#dpad` displays an actual reference photo, not a CSS-drawn shape.** `assets/dpad_cross.png` (320x320, cropped tightly from a supplied full-resolution reference image) is set as `#dpad`'s `background-image`; a hand-tuned CSS approximation (rounded-rect + `clip-path` shapes, gradients, shadows) was tried first and read as amateurish next to the real photo it was copying, and CSS shading can't reproduce a photoreal render's curvature/material anyway. The four `<button>` elements inside `#dpad` are invisible, absolutely-positioned hit zones (`.dpad-up`/`.dpad-left`/etc. in `styles.css`) at percentages measured directly from the source photo's own pixels, each growing along its own outer/inner axis only (not sideways, which would start overlapping a diagonal neighbor's zone) so they're easier to hit without becoming ambiguous near the center. No visible glyph content on the buttons — the arrows are baked into the image — `aria-label` alone carries the accessible name; `.dpad-btn:active` fakes a press with a soft radial-glow flash since the image itself can't change state.
  - **Horizontal position** comes from the canvas's actual `getBoundingClientRect()`, anchored within the "gutter" (the empty space between the viewport frame and the canvas edge) on each side — not a fixed offset from the viewport edge, since the gutter width changes with viewport size. `#dpad` on the left, `#actionButtons` on the right (mirrored): standard movement-left/actions-right split, and it leaves the *top* corners free for a future credits/settings/etc. icon row rather than competing with either cluster.
    - **Design-director pass: edge-anchored, not pure gutter-centering.** Previously always centered dead in the middle of the gutter (`rect.left / 2`), which reads as floating in empty space once the gutter is much wider than the control needs — roughly as far from the viewport's physical edge (where a thumb actually rests) as from the board, and the direct cause of the other half of the "too much blank space" report. `edgeAnchoredOffset()` now prefers a fixed, thumb-reach distance from the nearest viewport edge (`EDGE_ANCHOR_MARGIN = 20` plus half the control's current on-screen size) and only falls back to splitting the gutter evenly when the gutter's too tight for that to fit without the control creeping toward the canvas — which is also exactly what still guarantees it can never overlap the board. Net effect: a roomy gutter's leftover space now sits beside the board, not beside the viewport edge. Confirmed live (screenshotted at both a deliberately huge and a deliberately tight simulated gutter, since this sandbox's browser-resize tooling can't actually resize a real window) that both ends of that range look and behave correctly.
  - **Vertical position** is plain CSS `top: 50%` (viewport-center) — no JS needed, because `index.html`'s `body` uses `justify-center` rather than `justify-start` (see below), which keeps the canvas itself vertically centered in the viewport too.
  - **Shrink-to-fit sizing**: each control's natural size (`DPAD_NATURAL_SIZE = 210`, `ACTION_BTN_NATURAL_SIZE = 76` in `touchControls.js` — both bumped up in the same design-director pass, matching `styles.css`'s `width`/`height`) is scaled down via a `--dpad-scale`/`--action-scale` CSS custom property (applied as `transform: scale(...)`, so padding/gaps/icon sizes shrink together rather than a fixed-px interior cramming into a smaller box) whenever the gutter is narrower than that natural size. Confirmed necessary on tablets close to the canvas's 4:3 aspect even with the wider touch margin above.
    - **The d-pad now has a hard floor the action buttons deliberately don't.** `MIN_DPAD_SCALE = 0.62` (130px) — previously **no minimum floor at all**, which is exactly what let the d-pad shrink to the 70-125px range flagged above. A d-pad divides one disc into 4 direction zones, so shrinking it isn't just "a bit harder to tap," it makes hitting the *specific direction* meant unreliable — unlike the action buttons, which are simple one-shot taps and keep the old no-floor policy, and in practice always land at full size now anyway once the gutter satisfies the d-pad's larger requirement. `MIN_TOUCH_CONTROL_GUTTER` (exported for `resizeCanvas()`, see above) is computed from this same floor plus its safety margin, so the floor and the board-width reservation that guarantees it can never drift out of sync with each other. **0.62, not the rounder-looking 0.75 the first attempt used:** 0.75 (157.5px) demanded more gutter than an ordinary iPhone's *natural*, no-floor-at-all gutter already gave it (~150px, already perfectly reasonable) — costing that phone real board height (see the `resizeCanvas()` regression above) for a marginal, not-actually-needed gain. 0.62 still turns the genuinely-bad old cases (iPhone SE ~72px, a standard iPad ~96px) into a meaningfully bigger, comfortably-usable ~130px control, while landing below what ordinary phones already provide naturally — so it only ever costs board space on the handful of devices that actually need the help.
  Each button dispatches a real `KeyboardEvent` (`keydown`/`keyup` for the D-pad, a single `keydown` for the action buttons) on `window` — `InputHandler.js` is completely unaware touch controls exist; it just sees the same events a physical keyboard would send. Visibility is CSS-only: `@media (pointer: coarse)` keeps them off desktop, and `body.in-game` (toggled by `GameScreen.init()`/`cleanup()`) keeps them off the setup screen.
- **`index.html`'s `body` uses `justify-center`, not `justify-start`.** On viewport aspect ratios closer to square than 4:3, the canvas ends up width- rather than height-constrained and shorter than the viewport; `justify-start` dumped all of that leftover vertical space below the canvas instead of splitting it top/bottom, which looked visibly broken (confirmed live from a user-supplied screenshot of a squarish window) and also meant the touch controls' `top: 50%` didn't actually line up with the canvas's own vertical center. This one change fixed both at once — the touch-control vertical centering above depends on it.
- **Not covered by this pass:** actual portrait layout (deliberately out of scope — see the gate above), and the pre-existing live-resize gap (furniture/spawn positions are computed once at generation time from `canvas.width`/`canvas.height` and never re-laid-out if the canvas resizes mid-game — unchanged by this work, still tracked in Planned work below).

## iOS "Add to Home Screen" hint (`js/utils/homeScreenHint.js`)
A slim dismissible banner pinned to the top of the viewport, shown for an iPhone/iPod on **any** iOS browser, not already launched from a home-screen icon. This is the manual workaround every iOS-targeting PWA falls back to — no iOS browser has a `beforeinstallprompt`-style API at all (that's Chromium-desktop/Android only; WebKit doesn't implement it, and every browser on iOS is required to render on WebKit regardless of engine branding), so there's no way to trigger the real "Add to Home Screen" dialog or even detect it's available. The actual payoff (see Fullscreen support in Planned work below) is real: WebKit only implements the Fullscreen API on iPadOS, never iPhone, so a home-screen launch (which hides the browser's toolbar entirely) is the only way to reclaim that space on an iPhone — but nothing tells a player that's an option unless they already know to dig into Share > Add to Home Screen themselves.

- **First version excluded Chrome/Firefox/Edge/Opera on iOS by user agent, on the assumption only Safari's home-screen launch actually went standalone — confirmed live to be wrong.** The project owner tested adding to home screen via Chrome-iOS directly and reported it *does* get a real standalone-ish launch from that icon, not just an ordinary bookmark reopening inside Chrome's normal browser chrome. Detection is now just two checks: `/iPhone|iPod/` on `navigator.userAgent` (deliberately **not** a broader "any iOS device" regex — iPadOS 13+ requests desktop sites by default and its Safari reports a Mac-style user agent, but iPadOS already gets the real Fullscreen API and doesn't need this hint at all), and `isStandalone()` excluding a player who's already added it. `isStandalone()` itself checks **two** signals, not one — `window.navigator.standalone === true` (Apple's own non-standard property) **or** `window.matchMedia('(display-mode: standalone)').matches` (the standard, cross-browser media feature) — since `navigator.standalone` isn't guaranteed to be set by every other iOS browser's own standalone launch even when it genuinely is running standalone; checking only that property would have kept nagging a Chrome-iOS player already using their home-screen icon.
- **Shown pre-game, hidden automatically once gameplay starts.** Nothing else occupies the top of the screen before gameplay (the settings menu and touch controls are both gated to `body.in-game` too — see Settings menu & audio and Mobile responsiveness above), so there's no conflict to place around; a `body.in-game #homeScreenHint { display: none }` rule in `styles.css` hides it the moment gameplay begins so it never has to compete with the board.
- **Dismissal counts rather than a single permanent flag.** `kattrap_homeScreenHintDismissCount` (`localStorage`) increments each time the × is tapped; the hint keeps reappearing on later visits and only stops for good once it's actually been dismissed `MAX_DISMISSALS` (10) times — a single reflex dismissal on a day the player doesn't feel like fiddling with Share > Add to Home Screen isn't the same as "never show me this again." (An earlier version used a plain boolean, permanently gone after the first dismiss — the counter replaced it entirely, under a new key name, rather than trying to migrate the old boolean value into a number.) Reading/writing the count is wrapped in `try`/`catch` so a restricted-storage environment (some private-browsing configs) degrades to "the hint reappears next load" instead of throwing and blocking the rest of `main.js`'s `init()`.
- Styled as this game's own chrome (dark, rounded, the same purple accent used for the settings menu/action buttons/punch shockwave) with a small inline SVG share-icon glyph (an upward arrow breaking out of a box, matching iOS's own Share icon shape) rather than relying on an emoji that might not render as anything recognizable.

## Viewport frame & mouse-escape danger indicator (`styles.css`, `GameScreen.updateEscapeDangerIndicator`)
A retro handheld-console bezel drawn as a fixed, non-interactive overlay around the whole viewport (`body::after` for the frame, `body::before` for a small "power LED" dot in the top-left corner) — not a real layout border, since `resizeCanvas()` sizes the canvas off raw `window.innerWidth`/`innerHeight` and an actual border would silently eat into that budget and risk overflow. The frame itself is a thin, *directionally* beveled border (lighter top-left, shadowed bottom-right, like a real molded-plastic edge catching light unevenly) rather than a uniform ring. Both rules are gated behind `@media (pointer: coarse)` — a console bezel only makes sense framing an actual touch device, so the whole thing is invisible on desktop. (Two earlier attempts were corrected after live feedback: one framed the canvas itself instead of the viewport, and a later one showed unconditionally on all devices including desktop.)

The LED isn't just decorative — it's a live mouse-escape-danger meter. `GameScreen.updateEscapeDangerIndicator()` (called every frame from `updateMouse()`) measures the mouse's distance to the nearest `Escape`'s center and sets `document.body.dataset.mouseDanger` to `'low'`/`'medium'`/`'high'` against `BASE_ESCAPE_DANGER_DISTANCE`/`BASE_ESCAPE_WARNING_DISTANCE` (90/220 — scaled via `getScale()`'s `scale`, like any other board distance, so "close" means the same relative thing at any canvas size). `styles.css`'s `body[data-mouse-danger="..."]::before` rules recolor the LED green/amber/red accordingly, with a short CSS transition rather than a hard snap. This runs regardless of device (harmless on desktop, since the CSS it targets is hidden there via the same `pointer: coarse` gate above) — and `GameScreen.cleanup()` deletes the `mouseDanger` dataset attribute so a fresh game doesn't inherit a stale color left over from the last one.

## Conventions actually in use
- ES modules throughout (`import`/`export default`), one class per file.
- Constants (colors, fonts, sizes, sound keys, messages) are hoisted to the top of `GameScreen.js` in `UPPER_SNAKE_CASE` objects — follow this pattern rather than inlining magic numbers/strings if you add to that file.
- Sprite sheets are single `Image` objects sliced via `drawImage` source-rect math (`frameWidth`/`frameHeight`/`currentFrame`); animation speed is throttled with a manual `frameCounter` vs `frameSpeed`, not `setInterval`.
- Collision detection is hand-rolled AABB (axis-aligned bounding box) checks via the shared `aabbOverlap` helper — no physics library.

## Known rough edges (worth knowing before you extend this)
- **No tests at all.** Zero test coverage currently exists for any collision, movement, or game-state logic.
- **No README.**
- `GameScreen.js` mixes rendering, game state, input-response, collision logic, layout scaling, and procedural level generation in one ~1000-line class — a strong refactor candidate.
- `styles.css` now holds the orientation-gate/touch-controls/viewport-frame CSS (see Mobile responsiveness and Viewport frame & mouse-escape danger indicator above) — everything else is still Tailwind utility classes in `index.html`.
- **Four scale functions (`getScale`/`getUIScale`/`getFurnitureScale`/`getCharacterScale`), each with its own device-dependent multiplier, and two of them (`getFurnitureScale`, `getCharacterScale`) boost *desktop* rather than touch** — see Mobile responsiveness above. Easy to reach for the wrong one when adding a new `BASE_*` constant to `GameScreen.js`'s `computeLayout()`; check whether the new size is a character-speed/wall/floor thing, a button/message thing, furniture, or character size before picking which scale multiplies it.
- **Touch-vs-desktop detection is done purely via `window.matchMedia('(pointer: coarse)')`** (`isTouch()` in `js/utils/scale.js`) — a Windows/ChromeOS convertible used with a mouse as its primary pointer would read as desktop even with a touchscreen present, and vice versa for an unusual desktop setup with only a touchscreen. Accepted as good enough for this game's actual audience; revisit if that assumption stops holding.
- **White box on initial load (fixed) — root cause was a script/stylesheet ordering rule, not just the canvas's own CSS.** Reported on mobile as a 1-3 second white box on the canvas before the game appeared. Two things were compounding: (1) `<canvas id="gameCanvas" class="bg-white">` gave the raw element a white CSS background against `body`'s dark `bg-gray-900`, so anything left unpainted showed as a stark white box rather than blending in; (2) `main.js`'s `<script type="module">` — confirmed empirically with a throwaway test page (an artificially slow stylesheet + inline module script, checked via console-logged timestamps) — doesn't execute until *every* stylesheet before it in the document has finished loading, per spec, regardless of whether the script actually touches anything that stylesheet affects. `index.html`'s Tailwind CDN `<link>` turned out to be a 2.9MB uncompressed stylesheet (confirmed by fetching it directly; ~255KB compressed) — slow enough on mobile to stall the *entire game* from booting, not just delay a style. Fix: the script tag now has `async` (verified via the same test page that `async` skips the stylesheet-blocking wait entirely, unlike plain `type="module"` which behaves like `defer`), and the canvas dropped `bg-white` so the remaining gap before first paint shows the page's own dark background instead of white. `async` changes one real thing that needed a matching fix in `main.js`: unlike `defer`, it doesn't wait for the document to finish parsing before running, so `main.js`'s top-level `document.getElementById('gameCanvas')` could theoretically run before `<body>` exists — `main.js` now wraps its init in a `document.readyState` check (runs immediately if the DOM's already there, otherwise waits for `DOMContentLoaded`) rather than assuming parse order. This is the same class of bug already fixed once for `Cutscene.js` (see above — that screen used to leave the canvas uncleared between frames, also showing this same white CSS background).

## When working in this repo
- Prefer matching the existing per-class, no-framework style — don't introduce a build tool or framework without discussing it first.
- If you touch collision code, use `aabbOverlap` from `js/utils/collision.js` rather than reimplementing the check inline.
- Every screen (`SetupScreen`, `CharacterSelectScreen`, `GameScreen`) that adds `document`/`canvas` listeners or a `requestAnimationFrame` loop should expose a `cleanup()` — `ScreenManager.setScreen()` calls the outgoing screen's `cleanup()` automatically (if present) before swapping, so this is the one teardown path that actually gets invoked on every screen transition, not just the ones a screen happens to call manually before transitioning itself.
- There's no test runner configured yet — if you add tests, that's a setup decision to make explicitly (e.g. Vitest/Jest), not assume one is already there.
- Reuse `isTouch()` (`js/utils/scale.js`, exported) for any new mobile-vs-desktop behavior rather than inventing another device-detection heuristic — it's already the single source of truth behind touch-control visibility, the viewport-frame bezel, `resizeCanvas()`'s width margin, and all four scale functions. Keeping them all on the same signal means they can never disagree with each other.
- Before shipping a mobile/responsive-layout change, check the actual `resizeCanvas()`/`computeLayout()` math by hand (or a quick throwaway script) across a real spread of device dimensions — not just a few manually-resized desktop-browser windows. That narrower kind of testing missed real bugs twice in this project's history (see Planned work's mobile-responsiveness entry) that a numeric sweep across common desktop/laptop/tablet/phone sizes caught immediately.
- If you add a new size for a character (`Cat`/`Dog`/`Mouse`), decide whether it's a *display/collision size* (use `sizeScale`/`getCharacterScale()`) or *movement speed* (use `scale`/`getScale()`) before wiring it in — conflating the two was a real bug (`Cat.move()` silently ignoring a passed-in speed override, see Character selection & playable modes above), and cost several rounds of tuning a constant that had no actual effect until it was caught.
